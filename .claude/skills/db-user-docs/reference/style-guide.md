# 執筆スタイルガイド（実践ユーザーガイド）

対象は「その機能を**使う**エンジニア」。内部実装ではなく、**何ができて・どう使うか**を、
読者が手を動かしながら理解できる形で書く。db-internals-docs が「ソースコードで裏づける
内部構造の解説」なのに対し、こちらは「**実際に動かして裏づける使い方の解説**」である。

## 最上位の狙い：読んで手を動かせば「8割わかる」

このガイドのゴールは、読者が **上から順に読み、示されたコマンドを実際に実行していけば、
その機能のおおよそ8割を自力で使えるようになる**こと。これを達成するために全編で次を守る。

1. **動かして理解させる**：概念の説明より先に「まず動く例」を出す。すべての操作に
   **入力（実行するコマンド）と期待される出力をセット**で示し、読者が自分の画面と照合できるようにする。
2. **前提を毎回明示する**：バージョン・拡張・権限・サンプルデータなど「これさえ揃えば再現できる」
   条件を各章の冒頭に書く。読者が詰まる最大の原因は前提のズレなので、コピペで用意できる形にする。
3. **最短の成功体験を早めに**：序盤の章で最小の end-to-end 例（Hello World 相当）を成功させ、
   「動いた」という手応えを与えてから詳細へ進む。
4. **段階的に積み上げる**：各章は前章で作った環境をそのまま引き継ぎ、機能を少しずつ足していく。
   章をまたぐたびに環境を作り直させない。
5. **ゴールとチェックポイント**：各章の冒頭に「この章でできるようになること」、末尾に
   「チェックポイント（読者が自分で確認できる問い／チェックリスト）」を置く。
6. **落とし穴を先回りする**：よくあるエラーメッセージと対処を、その操作の直後に書く。
7. **最後に早見表**：最終章にコマンド・構文・オプションのチートシート（表）を置き、
   読み終えた後の実務リファレンスにする。

## 全体構成（章立ての雛形）

トピックに合わせて増減してよいが、次の流れを基本とする（既定 5〜7 章）。

1. **この機能でできること** — 解決する課題／典型ユースケース／向き・不向き。ここで全体像の図を1枚。
2. **準備** — 動作環境・必要な拡張やパラメータ・サンプルデータを、コピペで再現できる形で用意する。
3. **まず動かす（最短ルート）** — 最小の end-to-end 例を1本通し、成功を確認する。
4. **基本操作** — 主要な操作を1つずつ。各操作は「何をするか→入力→出力→読み方」の順。
5. **実践シナリオ** — 現実に近いまとまったシナリオを通して、複数の操作を組み合わせる。
6. **つまずきポイントと対処** — よくあるエラー・誤解・アンチパターンと、その回避／復旧手順。
7. **まとめとチートシート** — 要点の再確認と、構文・オプションの早見表。

各章は 3〜5 節（`N.1`, `N.2`…）に分ける。1節＝1つのまとまった操作や概念にする。

## 1章の典型パターン

1. **この章のゴール**（`.goal`）— 読み終えると何ができるようになるかを箇条書きで2〜4項目。
2. **前提**（`.prereq`）— 前章から引き継ぐ状態・追加で必要なもの。
3. 概念の**ごく短い**説明（2〜4文）＋必要なら**ワークフロー図**（Mermaid）。
4. **ハンズオン**（`.handson`）— 番号付きステップ。各ステップに入力（`pre`）と期待出力（`.example`）。
5. 出力の**読み方**：どの列・どの値に注目すべきかを一言添える。
6. **落とし穴**（`.pitfall`）— この操作で典型的に出るエラーと対処。
7. **チェックポイント**（`.checkpoint`）— 読者が自分の環境で確認できるチェックリスト。

## 文体

- 常体（である調）で簡潔に。ただし読者に手を動かさせる指示は「〜する」「〜を実行する」と明確に。
- 専門用語は初出で一言定義する。内部実装の詳細には立ち入らない（必要なら
  「仕組みの詳細は内部構造ドキュメントを参照」と誘導する）。
- 「たぶん」「はず」で書かない。**実際に動かして確認した挙動・出力**を書く。未確認・環境依存の点は明示する。
- 出力例は実行結果を貼る。列幅や行数は本物に合わせ、読者が照合できるようにする。

## 図（Mermaid）の使いどころ

内部データ構造ではなく、**使う人の視点の流れ**を描く。

- **全体像／登場人物**: `flowchart`。コンポーネントやコマンドの関係を1枚で。
- **操作の手順・データの流れ**: `flowchart` または `sequenceDiagram`。
- **状態のライフサイクル**: `stateDiagram-v2`（例: レプリケーションスロットやジョブの状態遷移）。
- すべての図に `図 N.M: 説明` のキャプションを付け、本文から「図 N.M のように」と必ず参照する。
- 1枚に詰め込みすぎない。手順が長いならステップ図を複数に分ける。

## 例（コマンド／出力）の示し方

- **入力と出力を必ずペア**で示す（`.example` のラベル `入力` / `出力`）。
- 実行可能・再現可能な最小例にする。前提のスキーマ・データも本文かハンズオン内に含める。
- プロンプト記号やコメントで「どこで実行するか」を示す（`psql` 内か、シェルか）。
- 破壊的・不可逆な操作（`DROP`, `pg_terminate_backend` 等）は `.pitfall` か `.tip` で必ず注意喚起する。

## 品質チェック

- 章・節・図番号が連番で、本文の参照と一致しているか。
- すべての内部リンク（サイドバー・前後ナビ・章カード・節アンカー）が実在ファイル／id を指すか。
- **各章のハンズオンを最初から順に実行すると、実際に最後まで通るか**（環境の引き継ぎが途切れていないか）。
- 出力例が実際の実行結果と一致しているか（列名・値・件数）。
- Mermaid 構文が壊れていないか（ノード ID 重複・未閉じの括弧など）。
- チェックポイントの各項目が、その章の内容だけで確認できるか。
