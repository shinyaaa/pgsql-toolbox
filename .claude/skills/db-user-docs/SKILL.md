# db-user-docs

PostgreSQL をはじめとするソフトウェアの**機能の使い方**を、**読んで手を動かせばおおよそ8割
理解できる**実践的な日本語ユーザーガイドとして、**静的HTMLサイト**で生成するスキル。

内部実装を解き明かす [db-internals-docs] の姉妹スキル。あちらが「ソースコードで裏づける内部構造」
なら、こちらは「**実際に動かして裏づける使い方**」を扱う。両者は同じサーバ（ポート 30002）の
ドキュメント一覧に載るが、**タブが別**（こちらは「ユーザドキュメント」タブ）で、
**ティール色の見た目と「ユーザーガイド」バッジ**でも区別される。

## 成果物の形

`pgsql-toolbox/internals/user_docs/<スラッグ>/` 以下に生成する。一覧ページ（`http://127.0.0.1:30002/`）は
ディレクトリでタブを分けており、`user_docs/` に置いたものが「**ユーザドキュメント**」タブに並ぶ
（`docs/` に置くと内部構造ドキュメントのタブに混ざってしまうので注意）。公開 URL は
`http://127.0.0.1:30002/user/<slug>/` になる。

```
internals/user_docs/<slug>/
├── index.html        ← トップページ（リード文＋章カード目次）
├── ch01.html         ← 第1章
├── ch02.html         ← 第2章
├── …
└── css/style.css     ← スタイルシート（assets/style.css をコピー）
```

- 各ページは左に**共通サイドバー目次**、本文末に**前後ナビ**を持つ。
- **全ページのヘッダ左端**に、ドキュメント一覧（`http://127.0.0.1:30002/`）へ戻る
  `← ドキュメント一覧` リンクを置く（テンプレートに組み込み済み）。
- ヘッダにはティール色の背景と**「ユーザーガイド」バッジ**が入り、内部構造ドキュメント（青系）と一目で区別できる。
- 図は **Mermaid**（CDN 読み込み）で、使う人の視点の「流れ」を描く。`図 N.M: 説明` のキャプションを付ける。
- 本文は日本語・常体。ただし**コマンドの入力と期待される出力を必ずセット**で示す。

### ★ doc-kind メタは必須（区別表示の要）

一覧ページは各ドキュメントの `index.html` にある `<meta name="doc-kind" content="user">` を読んで、
ユーザーガイドとして区別表示する（このタグが無いドキュメントは従来どおり内部構造扱いになる）。
`assets/index-template.html` / `assets/page-template.html` には組み込み済み。**削除しないこと。**

## このガイドの狙い：「読んで動かせば8割わかる」

すべての判断は、この一点に照らして行う。詳細は `reference/style-guide.md` 冒頭を必ず読む。

1. **動かして理解させる** — 概念より先に「まず動く例」。全操作に**入力と期待出力をセット**で示す。
2. **前提を毎回明示** — バージョン・拡張・権限・データを、各章冒頭にコピペ再現できる形で書く。
3. **最短の成功体験を早めに** — 序盤で最小の end-to-end 例を成功させてから詳細へ。
4. **段階的に積み上げる** — 各章は前章の環境を引き継ぐ。作り直させない。
5. **ゴールとチェックポイント** — 章頭に「できるようになること」、章末に確認用チェックリスト。
6. **落とし穴を先回り** — よくあるエラーと対処を操作の直後に置く。
7. **最後に早見表** — 最終章にコマンド／構文のチートシート。

## 前提リソース

このスキルディレクトリ内の以下を必ず参照・利用する。

- `assets/style.css` … 完成済みスタイルシート。**そのまま `css/style.css` にコピー**する（編集不要）。
- `assets/page-template.html` … 章ページの雛形（`{{...}}` を置換）。`doc-kind` メタ組み込み済み。
- `assets/index-template.html` … トップページの雛形。`doc-kind` メタ組み込み済み。
- `reference/style-guide.md` … 章構成・文体・図と例の作法・「8割わかる」原則。**着手前に必ず読む**。
- `reference/html-snippets.md` … ゴール／前提／ハンズオン／入力出力例／チェックポイント等の HTML 部品集。

## 正確性の担保：ソースではなく「実際に動かして」裏づける

db-internals-docs がソースコードを一次情報にするのに対し、本スキルは**実行結果**を一次情報にする。

- 記載するコマンドは、可能な限り**実際に PostgreSQL 上で実行し、その出力を貼る**。
  出力例は列名・値・件数まで本物に合わせ、読者が自分の画面と照合できるようにする。
- 実行環境が用意できない場合は、公式ドキュメントに基づいて出力を再現し、**未実行である旨を明示**する。
- **推測で書かない**：確認した挙動のみを本文に反映し、環境依存・未確認の点は明示する。
- 破壊的・不可逆な操作（`DROP`, `pg_terminate_backend`, ファイル削除等）は必ず注意喚起を添える。

対象バージョンの機能仕様は公式ドキュメント（`https://www.postgresql.org/docs/`）で確認する。
必要なら `postgres/` サブモジュールで挙動の裏取りをしてもよいが、本文は「使い方」に徹する。

## ワークフロー

### 0. リソース確認・対象バージョン確定

`reference/style-guide.md` と `reference/html-snippets.md` を読み、構成・原則・HTML 部品を把握する。

対象バージョンを確定し、`{{VERSION_INFO}}` を決める。形式は `"PostgreSQL <version>"`（例: `"PostgreSQL 18"`）。
一覧ページはこの `version-badge` の値をそのまま表示するので、**先頭を `PostgreSQL <major>` に揃える**
（末尾に日付を足してもよい: `"PostgreSQL 18 · 2026-07-25"`）。

```sh
# 参考: 手元の PostgreSQL バージョン確認
psql -tAc 'select version();' 2>/dev/null || echo '手元インスタンスなし（公式ドキュメントで確認）'
date '+%Y-%m-%d'
```

### 1. 要件確認
ユーザーから次を確認する（不明点のみ簡潔に質問。妥当な既定があれば提案して進める）。
- **トピック**（例: 「論理レプリケーションの使い方」「パーティショニング入門」「pgvector で類似検索」）。
- **対象バージョン**（例: PostgreSQL 18）。明示なければ最新安定版を仮定し冒頭に明記。
- **想定読者**（例: 「SQL は書けるがこの機能は未経験」）。`{{AUDIENCE}}` に反映する。
- **章数の目安**（既定: 5〜7 章）。
- **出力先スラッグ**（既定: `internals/user_docs/<slug>/`）。内部構造ドキュメントとスラッグが衝突しないようにする。

### 2. 機能調査＋実際に動かす
公式ドキュメントで機能仕様・構文・オプションを把握し、**代表的な操作を実際に実行して出力を採取**する。

- 「最短で動く最小例」を最初に自分で通し、前提（拡張・パラメータ・権限・データ）を洗い出す。
- 主要な操作それぞれについて、入力と出力のペアを採取する。
- つまずきやすい点（典型的なエラーメッセージと原因）を書き留める。
- 実行できない環境では公式ドキュメントに基づいて再現し、未実行を明示する。

### 3. 目次設計
`style-guide.md` の章立て雛形に従い、**章→節**の目次を作る。
- 「できること → 準備 → まず動かす → 基本操作 → 実践 → つまずき → まとめ／チートシート」を基本に、トピックへ合わせて調整。
- 各章にタイトル・1行説明・節リスト（`N.1`, `N.2`…）を割り当てる。
- 確定した目次をユーザーに提示し、合意を得てから本文生成へ進む。

### 4. 共通パーツ生成
- **サイドバー TOC**（`html-snippets.md` 参照）の HTML を1つ作り、全ページで使い回す。
  各ページ生成時に、現在の章 `<li>` と節 `<a>` に `class="current"` を付けたバリエーションにする。
- `css/style.css` を `assets/style.css` のコピーで用意する（**編集しない**）。

### 5. 各章ページ生成
`assets/page-template.html` をベースに、章ごとに `chNN.html`（ゼロ埋め2桁）を生成する。
`style-guide.md` の「1章の典型パターン」に従う:
**ゴール（`.goal`）→ 前提（`.prereq`）→ 短い概念説明＋図 → ハンズオン（`.handson`、入力/出力ペア）→
出力の読み方 → 落とし穴（`.pitfall`）→ チェックポイント（`.checkpoint`）**。

- 節見出しには `id="sec-N-M"` を付け、サイドバーから飛べるようにする。
- 図は本文から必ず「図 N.M のように…」と参照する。
- **すべてのコマンドに入力と期待出力をセット**で付ける（`.example` のラベル `入力` / `出力`）。
- 各章のハンズオンは、**前章の状態を引き継いで最初から順に実行すると最後まで通る**ように書く。
- `{{PAGER}}` に前後章リンクと中央のトップページ（目次）リンクを入れる（順序は prev → up → next）。
  先頭章は prev を、末尾章は next を、それぞれ `pager-spacer` に置き換える。

**章を書き終えたら、ファイルに書き出す前に必ず 5a を実施する。**

### 5a. Mermaid 構文チェック（各章・書き出し前に必須）

章内のすべての `<pre class="mermaid">` ブロックを1つずつ確認する。
以下の項目を**すべてパスしてから**ファイルに書き出す。

| チェック項目 | 良い例 | NG 例 |
|---|---|---|
| ノードIDは英数字・アンダースコアのみ | `sub_slot` | `sub slot`、`sub(slot)` |
| 日本語はラベル内のみ | `A["購読側"]` | `購読側["..."]` |
| 矢印の種類がダイアグラム型と一致 | flowchart で `-->` | flowchart で `->>` |
| `subgraph` に対応する `end` がある | `subgraph X\n...\nend` | `end` 抜け |
| 同一ダイアグラム内でノードIDが重複しない | — | `A` が2箇所で定義 |
| 括弧・クォートが対応して閉じている | `["label"]` | `["label"` |

問題が見つかった場合は修正してから次の章へ進む。

### 6. トップページ生成
`assets/index-template.html` をベースに `index.html` を生成。`{{AUDIENCE}}` に対象読者、`{{LEAD}}` に
「このガイドで何ができるようになるか・前提・所要時間の目安」を書き、全章ぶんの章カードを並べる。
**`<meta name="doc-kind" content="user">` が残っていることを確認する。**

### 7. 検証
- すべての内部リンク（サイドバー・前後ナビ・章カード・節アンカー）が実在ファイル／id を指すか確認。
- 章・節・図番号が連番で本文参照と一致しているか確認。
- **各章のハンズオンを順に実行すると実際に通るか**（環境の引き継ぎが途切れていないか）を確認。
- 出力例が実行結果と一致しているか（列名・値・件数）を確認。
- `index.html` に `doc-kind` メタが入っているか確認。
- 簡易チェック例:
  ```sh
  # 章ファイルの一覧と index からの参照漏れ確認
  ls internals/user_docs/<slug>/ch*.html
  grep -o 'href="ch[0-9]*\.html' internals/user_docs/<slug>/index.html | sort -u

  # doc-kind メタの確認（user が返れば OK）
  grep -o 'doc-kind" content="[a-z]*"' internals/user_docs/<slug>/index.html

  # 全章の Mermaid ブロック数を確認
  grep -c 'class="mermaid"' internals/user_docs/<slug>/ch*.html
  ```
- 可能なら `http://127.0.0.1:30002/user/<slug>/` を開いて、「ユーザドキュメント」タブに
  ユーザーガイドとして並ぶか確認する。

## 重要な原則

- **8割わかるが最優先**: 読んで手を動かせば使えるようになることを、全判断の基準にする。
- **入力と出力は必ずペア**: 読者が自分の画面と照合できることが、理解と自信につながる。
- **実行で裏づける**: 出力は実測を貼る。創作で埋めない。未実行・環境依存は明示する。
- **前提を毎回書く**: 読者が詰まる最大の原因は前提のズレ。各章冒頭で潰す。
- **一貫性**: 番号体系・リンク・スタイルを全ページで揃える。`style.css` は編集せずそのまま使う。
- **段階的合意**: 目次を提示して合意を得てから本文を書く。大量生成の手戻りを防ぐ。
