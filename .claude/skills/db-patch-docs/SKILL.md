# db-patch-docs

**git のパッチシリーズ**を対象に、読者がそのパッチを**レビューできる状態**になるまで解き明かす
日本語ドキュメントを生成するスキル。[db-internals-docs] が「ソースコードで裏づける内部構造」、
[db-user-docs] が「実際に動かして裏づける使い方」を扱うのに対し、こちらは
**「なぜこの実装でないと壊れるのかを、コミットで裏づけて説明する」**を扱う。

3 つのスキルは同じサーバ（ポート 30002）のドキュメント一覧に載るが、**タブが別**で
（こちらは「Patch」タブ）、**バイオレット色の見た目と「パッチ解説」バッジ**
でも区別される。

## 成果物の形

`pgsql-toolbox/internals/patch_docs/<スラッグ>/` 以下に生成する。公開 URL は
`http://127.0.0.1:30002/patch/<スラッグ>/`。

```
internals/patch_docs/<slug>/
├── index.html        ← 本体（全パッチ＋理解度チェックの1枚もの）
├── content.json      ← 素材。これを直して build.py を再実行すれば再生成できる
└── css/style.css     ← assets/style.css のコピー
```

ドキュメントディレクトリの中身はすべてサーバから読めるので（`/patch/<slug>/content.json` も返る）、
公開したくないメモはここに置かない。

- **1 ドキュメント = 1 パッチシリーズ**、**1 コミット = 1 章**。章の順序は適用順（0001, 0002, …）。
- 章は 5 節固定: **問題 / 設計 / 仕組み / 落とし穴 / テスト**（節見出しの目印は 問題・設計・仕組み・注意・検証）。
- 左サイドバーに全章と各節へのアンカー、末尾に理解度チェック（1 章あたり 4 問）。
- 図は **Mermaid**（CDN、`theme: 'base'`）。テンプレートに組み込み済み。
- 本文は日本語・常体。

### ★ 一覧ページに正しく載るための約束

一覧ページは各ドキュメントの `index.html` を正規表現で読む。テンプレートに組み込み済みなので
**消さないこと**。

| 要素 | 効果 |
|---|---|
| `<meta name="doc-kind" content="patch">` | カードに「パッチ解説」バッジとバイオレットの縁がつく |
| `<span class="version-badge">…</span>` | カードのバージョン行になる。**1 行・タグを含めない**。先頭の `PostgreSQL ` は一覧側で落とされる |
| ディレクトリ名 | **カードのタイトルそのもの**。HTML の `<title>` ではない。読める slug を選ぶ（例: `pgbench-tpcc-patches`） |

## 前提リソース

このスキルディレクトリ内の以下を使う。

- `assets/build.py` … `content.json` → `index.html` の生成器。**これを実行して生成する**（HTML を手書きしない）。
- `assets/index-template.html` … ページ雛形。ヘッダ・サイドバー・Mermaid 初期化・採点スクリプトを含む。
- `assets/style.css` … 完成済みスタイル。**編集せず** `css/style.css` にコピーされる（build.py が行う）。
- `reference/style-guide.md` … 章構成・各節に何を書くか・文体・正確性の担保。**着手前に必ず読む**。
- `reference/quiz-rules.md` … 設問の作り方、選択肢と解説の規則、検証項目。**クイズを書く前に必ず読む**。
- `reference/content-schema.md` … `content.json` の形式と、生成器が面倒を見る範囲。

## ワークフロー

### 1. 対象の確定

ユーザーに次を確認する（不明点のみ簡潔に質問し、妥当な既定があれば提案して進める）。

- **対象コミット範囲**（例: `git log --oneline base..HEAD` の 5 本、あるいは特定の 1 コミット）。
- **リポジトリのパス**（既定: 今いる worktree）。
- **スラッグ**（既定: ブランチ名から作る。カードのタイトルになるので読める名前にする）。
- **バージョン表記** `version_info`（既定: `<製品名 バージョン> · <ベースコミット> · <日付>`）。
  一覧のカードにそのまま出る。PostgreSQL なら `PostgreSQL 19devel · abc1234 · 2026-07-28`
  （先頭の `PostgreSQL ` は一覧側で落ちる）。PostgreSQL 以外のリポジトリなら製品名とバージョンを
  そのまま書く（`pgbouncer 1.24 · abc1234 · 2026-07-28`）。

```sh
git -C <repo> log --oneline <base>..<head>
git -C <repo> show --stat <commit> | tail -5     # 章ヘッダの事実表に使う
git -C <repo> rev-parse --short <base>           # version_info のベースコミット
cat <repo>/src/include/pg_config.h | grep -m1 PG_VERSION_STR   # PostgreSQL の場合
date '+%Y-%m-%d'
```

素材 `content.json` は作業リポジトリの `work/tmp/` などスクラッチに書き、確定してから
生成先へコピーする（生成先に置いたものは配信される）。

### 2. 素材の抽出（コミットごと）

`reference/style-guide.md` を読んでから、コミット 1 本につき次を集める。**差分だけを見て書かない**。
周辺コードを読み、なぜその位置・その順序なのかが説明できるまで理解する。

- **問題**: パッチ前の挙動。**パッチ前のバイナリで実際に再現し、端末出力を採取する**。
  再現できない場合（パッチ前がビルドできない、端末に何も出ない種類の不具合など）は、
  **端末出力を創作しない**。`repro` を空にして本文で挙動を述べ、「未再現」であることを明示する。
- **設計**: 採用した設計と、**却下した案がなぜ壊れるか**。コミットメッセージ、設計メモ、レビュー
  スレッドがあれば読む。却下案が見つからない設計判断は、無理に作らない。
- **仕組み**: コミット後のファイルからの逐語引用を 3〜5 断片（各 20 行程度まで）。機構を示す図が
  役に立つなら Mermaid を 1 つ。
- **落とし穴**: 読者が踏む罠、他モード・境界値との相互作用、**レビューで実際に見つかった欠陥と修正**。
  レビュー履歴が無いシリーズなら、その項目は無くてよい（無いものを作らない）。
- **テスト**: どのテストが何を固定しているか（ファイル名とケース名つき）。

コミットが多い場合は**コミット単位で並列に**抽出してよい（1 コミット 1 エージェント）。

### 2a. 章立ての提示（本文を書く前に）

対象コミットと、章ごとの「問題／設計の要点」を箇条書きでユーザーに示し、合意を得てから本文を
書く。5 章 20 問を書き切ってからの手戻りは大きい。

### 3. クイズの作成

`reference/quiz-rules.md` に従い、**1 章あたり 4 問**。機構・境界条件・「なぜ別案では壊れるか」を
問う。`correct_index` は素材の並びに対する 0 始まりでよい（並べ替えは生成器が行う）。

### 4. 素材の検証（必須・別パス、生成の前）

**書いたエージェントとは別のパス**に、原稿（content.json）とコミットだけを渡して検証させる。
`reference/style-guide.md` の「正確性の担保」の 8 項目のうち、素材だけで判定できるもの
（コード片の逐語一致、キャプション、数値、端末出力、主張とコミットの対応、見送り案の壊れ方、
クイズの正解、Mermaid 構文）を通す。指摘を反映したら**もう一度検証を回す**。

Mermaid は `reference/style-guide.md` の構文チェック表の全項目を、図ごとに確認する。

### 5. 生成

```sh
SKILL=~/git/pgsql-toolbox/.claude/skills/db-patch-docs
OUT=~/git/pgsql-toolbox/internals/patch_docs/<slug>
mkdir -p "$OUT"
python3 "$SKILL/assets/build.py" work/tmp/content.json --out "$OUT"
# build.py が content.json を $OUT にも残すので、次からは
# python3 "$SKILL/assets/build.py" "$OUT/content.json" --out "$OUT"
```

build.py は生成前に自己検査を行い、**問題があれば何も書き出さずに終了する**（終了コード 1。
素材の形が壊れている場合は 2）。報告された点を素材側で直して再実行する。

### 5a. 生成物の検証（生成の後）

`--quiet` を付けずに実行し、**選択肢参照の解決ログを目で見る**。「参照 → 記号」の対応が
解説の文意と合っているか確認する（番号で書かれた参照は生成器が推測で解決している）。

```sh
grep -nE '選択肢\s*[0-9]' "$OUT/index.html"   # 0 件であること
grep -c 'data-answer' "$OUT/index.html"        # 設問数
```

### 6. 確認

```sh
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:30002/patch/<slug>/
curl -s http://127.0.0.1:30002/ | grep -o 'kind-patch" href="[^"]*"'  # カードが出ているか
grep -c 'class="q"' internals/patch_docs/<slug>/index.html       # 問題数
```

- 一覧（`http://127.0.0.1:30002/`）の「Patch」タブにカードが出るか。
- サイドバーのリンクが全部飛ぶか、クイズが採点され、間違えた章へのリンクが出るか。
- ドキュメントサーバーは毎リクエストで再スキャンするので、**再起動は不要**。

### 7. コミット

`internals/` 配下のドキュメントは git 管理下にある（一覧の「更新」ボタンが origin と同期する
対象でもある）。生成物と `content.json` を **pgsql-toolbox リポジトリで**コミットする
（解説対象のリポジトリではない）。

## 重要な原則

- **レビューできる状態にすることが最優先**。書くか迷ったら「読者のレビュー能力が上がるか」で決める。
- **捨てた案を必ず書く**。採用案だけの解説は、なぜそれ以外では壊れるのかを読者に渡せない。
- **差分をナレーションしない**。読者が追うのは論理であって、ハンクの並びではない。
- **確認していないことを書かない**。端末出力は実測、コード片は逐語、数値は再計算。
- **検証は別パスで**。書いた本人の検算では思い込みが通る。
- **HTML を手書きしない**。素材を直して build.py を回す。スタイルは編集しない。
