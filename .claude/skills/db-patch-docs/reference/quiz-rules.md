# 理解度クイズの作成規則

「パッチ解説ドキュメント」の末尾に置く自己採点クイズの作り方。出題・シャッフル・解説・検証・実装をこの順に規定する。参照実装は `assets/build.py` の `shuffle_options()` / `_rewrite_refs()` / `answer_distribution_ok()`、出力例は `internals/patch_docs/pgbench-tpcc-patches/index.html` の `.quiz` 節。

## 1. 出題方針

パッチ 1 本につき 4 問。全体では「パッチ本数 × 4」問になる (5 本なら 20 問)。

4 問の型を分けて、同じ論点を 2 度問わない。

| 型 | 問うこと | 例 |
| --- | --- | --- |
| 機構 | そのコードが何をどの順で行うか | 「なぜジャンプ先の代入を `CSTATE_END_COMMAND` まで遅延させているのか」 |
| 境界条件 | 極値・空・オーバーフロー・0 の扱い | 「`\sleep 9223372036854775807 us` を実行するとどうなるか」 |
| 別案の破綻 | 捨てた設計を採るとどこが壊れるか | 「ヒストグラムをポインタで持たせる設計が退けられた理由は何か」 |
| 失敗モード | 実装の一部を抜いたときに何が観測されるか | 「`detailed` 述語に条件を足し忘れた場合どうなるか」 |

出してはいけない問題。

- 用語の暗記 (「この構造体の名前はどれか」「このオプションの正式名称は」)
- 些末な数値当て (「バケット数はいくつか」「diff の行数は」)
- 本文の一文をそのまま抜いた穴埋め
- 「正しいものをすべて選べ」形式 (採点 UI が単一選択のため)

問題文は本文を読み返さずに答えられる程度に自己完結させる。関数名・オプション名は問題文に書いてよい。答えの根拠は必ずその節の本文・コード・落とし穴のいずれかに書かれていること。本文に書いていない事実を正解の根拠にしない。

## 2. 選択肢

- 4 つ。正解はちょうど 1 つ。
- 誤答は「流し読みした人には妥当に見える」ものにする。素材は次から採る。
  - 別モードでの正しい挙動 (`-M prepared` の問題に simple モードの答えを混ぜる)
  - 旧実装の挙動 (「読み込み時に syntax error」など、パッチ前なら正しかったもの)
  - 実装しなかった設計案が生む挙動
  - テキスト的な直感 (「`ms` は直前のトークンに掛かる」)
- 明らかに場違いな選択肢を「捨て札」として入れない。4 つとも本文を読んでいなければ選びうる状態にする。
- 長さを揃える。最長の選択肢が最短の 2.5 倍を超えたら書き直す。正解だけが長い・正解だけが条件節を持つ、は最も露骨な手がかりになる。
- 「上記のいずれでもない」「すべて正しい」は使わない。
- 絶対語 (常に・決して・一切) を誤答だけに集めない。

## 3. 正解位置

**出題時の並びのままにしてはいけない。** 実測では執筆した 20 問のうち 18 問が先頭 (A) だった。書き手は正解を先に書いてから誤答を足すので、先頭偏りは必ず起きる。

決定的シャッフルで散らす。問題文をシードにすれば、再生成しても並びが変わらない。

```python
rng = random.Random(zlib.crc32(q['question_ja'].encode('utf-8')))
order = list(range(len(q['options_ja'])))
rng.shuffle(order)
newpos = {old: new for new, old in enumerate(order)}
q['options_ja'] = [opts[old] for old in order]
q['correct_index'] = newpos[q['correct_index']]
```

シャッフル後に分布を検査する。合格条件は次の 2 つ。

- 各記号 (A/B/C/D) の出現が全体の 15% 以上 35% 以下。20 問なら各 3〜7 問。
- 同じ記号が 3 問以上連続しない。

外れたらシードに定数を足して振り直す。ランダムに手で並べ替えない (再生成で崩れる)。参考までに、上の 20 問はシャッフル後 A=8 / B=3 / C=7 / D=2 で、B と D が下限割れなので振り直しが必要な例である。

## 4. 解説

各問に 3 要素を必ず含める。

1. **なぜ正解か。** 根拠となるコード・処理順・仕様を名指しする。「`CSTATE_END_COMMAND` の処理順 (統計の加算 → `st->command++`) が理由のすべて」のように、追跡できる形で書く。
2. **最も紛らわしい誤答がなぜ違うか。** これは省略不可。どの選択肢が一番引っかかるかを書き手が名指しし、それが成り立たない条件を示す。「選択肢 C が最も誘惑的だが、それは simple モードの挙動」の形。
3. **残りの誤答の棄却理由。** 1 行で足りる。「選択肢 D は事実として誤り (`PGresult` は全行を保持する)」。

長さの目安は 3〜6 文。本文の再掲ではなく、本文を読んだ人が「そこは読み飛ばしていた」と気づく情報を入れる。

## 5. 解説中の選択肢参照

**番号ではなく記号 (A〜D) で書く。** 「選択肢 C」「C が誘惑的」であって「選択肢 2」ではない。

理由は実測の破綻である。番号で書くと 0 始まりと 1 始まりが同一ドキュメント内で混ざる。上の 20 問には次の両方が実在した。

- 0 始まり: 「選択肢 0 も一見もっともらしいが」(先頭の選択肢を指している)
- 1 始まり: 「選択肢 2 が最も誘惑的だが」(2 番目の選択肢を指している)

さらに 1 始まり解釈だと**解説が正解の選択肢を誤答として指す**事故が起きていた。`-T` 満了の問題 (正解は先頭) で「選択肢 1 は元の仕様案の候補だが……却下された」と書かれており、そのまま出すと正解を否定する解説が表示される。

記号で書けばシャッフル時の書き換えも 1 対 1 で機械的に行える。執筆時点で記号を使うのが原則。

### 生成器が番号参照を解決する場合

既存原稿の移行など、番号参照が残った素材を機械処理するときの規則。

- 検出は正規表現で行う。「選択肢N」の明示形に加え、読点・句点・開き括弧の直後に現れる裸の数字も参照とみなす。ただし単位や助数詞が続くものは数量なので除外する (`us` `ms` `ビット` `バイト` `倍` `回` `個` `つ` `行` `件` `本` `問` `MB` `KB`)。`assets/build.py` の `REF_RE` がこの形。
- 0 始まり/1 始まりは**解説ごとに**決める。文書全体で統一されている保証はない。
- 判定は、参照の直後の節 (次の句点までを 120 字で切る) と各選択肢テキストのバイグラム類似度で行う。オフセット 0 と 1 のそれぞれで全参照のスコアを合計し、高い方を採る。
- **参照が正解の選択肢に着地したらスコアを減点する** (実装では −1.0)。解説は誤答を論じるものなので、正解を指す解釈は誤りである可能性が高い。
- どちらのオフセットでも範囲外 (`0 <= idx < len(options)`) になる解釈は捨てる。
- 書き換え後の記号はシャッフル後の位置を使う。`選択肢 ' + chr(65 + newpos[idx])` の形。助詞 (はがもをのとでに) が直後に来る場合は記号の後に半角空白を 1 つ入れる。
- **書き換えは全件ログに出す。** どの問題のどの箇所を、どちらのオフセットで、どの記号に、どの選択肢を指すものとして変換したかを標準出力に並べ、人間が目視する。ヒューリスティックである以上、無検査で通してはいけない。

## 6. 検証 (必須)

生成とは**別パス**で検査する。書いた直後の同じ流れで見直すと、書き手の意図が読めてしまって誤りが通る。検査は選択肢と解説と本文だけを見て、問題ごとに独立に行う。

### 内容チェックリスト

- [ ] 正解キーの選択肢が本当に正しい。本文・コードから根拠を 1 箇所引用できる。
- [ ] 検査者が本文だけを見て解いた答えが、キーと一致する。不一致は必ず調査する (キーの誤りか、問題文の曖昧さのどちらか)。
- [ ] 正解は 1 つだけ。残り 3 つそれぞれについて「これが誤りである理由」を 1 行で言える。
- [ ] 部分的に正しい誤答がない。「半分合っている」選択肢は書き直す。
- [ ] 誤答の否定根拠が本文に書かれている。本文にない事実で誤答にしていない。
- [ ] 問題文が単一の解釈しか許さない。条件 (モード・オプション・バージョン) が問題文に明示されている。
- [ ] 同一パッチの 4 問が別々の論点を問うている。
- [ ] 用語暗記・数値当てになっていない。

### 解説チェックリスト

- [ ] **解説が正解の選択肢を誤答として指していない。** 解説中の全記号参照を抜き出し、`correct_index` の記号と突き合わせる。一致したら必ずエラー。
- [ ] 「最も紛らわしい誤答がなぜ違うか」が書かれている。
- [ ] 記号参照が A〜D の範囲に収まり、実在する選択肢を指している。
- [ ] 番号参照が残っていない。`grep -nE '選択肢\s*[0-9]'` が 0 件。
- [ ] 解説がシャッフル後の並びと整合している (シャッフル前の位置を指したままになっていない)。

### 機械検査

生成器の最後に走らせる。1 件でも落ちたらビルドを失敗させる。

```python
assert len(set(map(id, q['options_ja']))) == 4 and len(q['options_ja']) == 4
assert 0 <= q['correct_index'] < 4
assert not re.search(r'選択肢\s*[0-9]', q['explain_ja'])          # 番号参照の残り
letters = set(re.findall(r'選択肢\s*([A-D])', q['explain_ja']))
assert chr(65 + q['correct_index']) not in letters                # 正解を誤答扱い
L = [len(o) for o in q['options_ja']]
assert max(L) <= 2.5 * min(L)                                     # 長さの偏り
assert q['anchor'] in section_ids                                 # リンク切れ
```

分布検査も同じパスで行う。`Counter(data-answer)` を出力し、上限下限と連続回数を確認する。

## 7. 実装要件

### 採点の挙動

- **即時採点。** 選択した瞬間に正誤・正解の位置・解説を表示する。送信ボタンは置かない。
- 回答済みの問題は全選択肢を `disabled` にして再回答を防ぐ。`data-done` フラグで二重加算も防ぐ。
- 選んだ誤答に `wrong`、正解に `correct` のクラスを付け、両方を同時に見せる。
- 判定文には正解の記号を含める。「不正解 — 正解は C」。
- 解説は正解でも不正解でも同じものを表示する。

### スコア表示

- 追従するスコアバー (`position: sticky; top: 0`) に「n / 全問 正解」、進捗バー、未回答数を出す。
- 進捗バーの幅は正解数 / 全問。
- 全問回答時に結果パネルを表示し、間違えた問題が属する節へのリンクを問題数付きで並べる。パッチ単位で集約する (「パーセンタイル (2 問)」)。
- 全問正解の場合は節リンクを出さず、その旨だけを書く。

```javascript
if (!wrongPatches[name]) wrongPatches[name] = { anchor: q.dataset.anchor, count: 0 };
wrongPatches[name].count++;
```

- やり直しボタンを常時表示する。押すと `data-done` を消し、`disabled` と `correct`/`wrong` を外し、解説を隠し、カウンタを 0 に戻し、クイズ節の先頭へスクロールする。設問の並びと正解位置は変えない (決定的シャッフルなので同じ)。

### アクセシビリティ

- 選択肢は `<button type="button">` にする。ネイティブに Tab で辿れて Enter / Space で発火するので、キーボード操作の追加実装は不要。`<div onclick>` は使わない。
- `:focus-visible` に見えるアウトラインを付ける。`outline: 2px solid var(--accent); outline-offset: 2px`。
- 解説ブロックに `aria-live="polite"` を置き、`hidden` の解除で読み上げさせる。判定文を最初の子要素にして、正誤が先に読まれるようにする。
- 正誤を色だけで示さない。判定文のテキスト、記号ラベル (A〜D) を併用する。
- `prefers-reduced-motion: reduce` で進捗バーのトランジションとスムーススクロールを止める。
- 各問に `Q01` のような連番と、出典パッチへのアンカーリンクを付ける。

### マークアップの骨格

```html
<article class="q" id="q0" data-answer="2" data-anchor="p-while" data-patch="\while ループ">
  <p class="q-meta"><span class="q-no">Q01</span><a href="#p-while">0003 \while ループ</a></p>
  <h4>…設問…</h3>
  <div class="opts">
    <button type="button" class="opt" data-q="0" data-o="0">
      <span class="opt-key">A</span><span class="opt-text">…</span>
    </button>
    …
  </div>
  <div class="q-feedback" hidden aria-live="polite">
    <p class="verdict"></p>
    <p class="why">…解説…</p>
  </div>
</article>
```

`data-answer` はシャッフル後の添字。`data-anchor` と `data-patch` は結果パネルの節リンク生成に使う。

## 8. 執筆データの形式

問題は本文と同じ JSON に節ごとに持つ。生成器がシャッフルと記号解決を担当するので、原稿は素直な形でよい。

```json
{
  "question_ja": "…",
  "options_ja": ["…", "…", "…", "…"],
  "correct_index": 0,
  "explain_ja": "…選択肢 C が最も誘惑的だが…"
}
```

- `correct_index` は原稿では 0 始まりで統一する。表示上の記号はシャッフル後に生成器が決めるので、原稿の並び順に意味はない。
- `explain_ja` の参照は記号で書く。原稿の並びを指すのではなく、**生成器が新しい位置へ書き換える前提**なので、書き換え規則 (5 節) を通す文字列であること。
- 未確定の判断を残す場合は `correct_index_note` に理由を書く。検証パスで必ず解消し、空のまま出力しない。


## 9. 規約と生成器の対応

`assets/build.py` が自動で満たすもの、機械検査するもの、書き手が守るものは次のとおり。

| 規約 | 誰が担保するか |
|---|---|
| 正解位置の分散 (各記号 15〜35%、同一記号の 3 連続なし) | build.py が文書全体でシードを振り直して満たす。満たせなければ生成を止める |
| 解説中の選択肢参照 | 記号 (A〜D) は build.py が並べ替えに追随させる。番号は参照先との類似度が足りるときだけ書き換え、足りなければ生成を止めて記号で書き直させる |
| 選択肢は 4 つ、correct_index は 0〜3 | build.py が素材読み込み時に検査し、外れていれば終了コード 2 |
| 解説が正解の選択肢を誤答として指していないか | build.py が機械検査し、生成を止める |
| クイズのリンク先が本文に存在するか | build.py が機械検査し、生成を止める |
| 選択肢の長さが揃っているか (最長 ≦ 最短 × 2.5) | build.py は**警告**を出すだけ。技術的な正確さのために長くなることがあるので、書き手が読んで判断する |
| 設問の質 (機構・境界・なぜ別案では壊れるか) | 書き手と、別パスの検証が担保する |
