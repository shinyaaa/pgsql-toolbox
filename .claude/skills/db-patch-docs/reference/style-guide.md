# 執筆スタイルガイド（パッチ解説ドキュメント）

対象は「そのパッチシリーズをこれからレビューする、あるいは引き継ぐエンジニア」。一連の git コミットを 1 本のドキュメントで解き明かし、最後に理解度チェックで確認させる。db-internals-docs が「ソースコードで裏づける内部構造の解説」、db-user-docs が「実際に動かして裏づける使い方の解説」であるのに対し、こちらは **「なぜこの実装でないと壊れるのかを、コミットで裏づけて説明する」** ドキュメントである。

参考実装: `internals/patch_docs/pgbench-tpcc-patches/`（素材 `content.json`、生成物 `index.html`、公開先 `/patch/pgbench-tpcc-patches/`）。構成・粒度・語り口はこれを基準にする。生成器は `assets/build.py`。

## 最上位の狙い：読んだ人がそのパッチをレビューできる状態になる

すべての判断はこの一点で決める。書くかどうか迷ったら「この段落は読者のレビュー能力を上げるか」を問い、上がらないなら削る。

読み終えた読者は次を自力で言えるはずである。この 5 つが章ごとに埋まっているかが完成の判定基準になる。

1. パッチ前に何が起きていたか。再現手順とエラーメッセージを含めて言える。
2. 採った設計と、捨てた設計。**捨てた案がなぜ壊れるか**を言える。
3. 変更の中心となるコードがどこで、なぜその順序・その位置なのかを言える。
4. この変更が壊しうる箇所（他モード、他オプション、境界値）を挙げられる。
5. テストが何を固定していて、実装を変えたときにどのテストが落ちるかを言える。

書かないもの。差分の逐語ナレーション（「次に foo.c を編集し、bar() を追加した」）、コミットメッセージの言い換え、機能の宣伝、一般論としての設計論。パッチのファイル一覧やハンクの並びを追いかけてはいけない。読者が追うのは論理であって差分の順序ではない。

## 全体構成

1 ドキュメント = 1 パッチシリーズ。**1 コミット 1 章**、章の順序はシリーズの適用順（0001, 0002, …）にそろえる。コミットを分割・合体して章を作らない。パッチシリーズを読む側はコミット単位で読むので、章とコミットが 1 対 1 でないと照合できなくなる。

- **冒頭（masthead）**: シリーズ名、ベースコミット、パッチ本数、総差分（挿入・削除・ファイル数）、テスト結果、検証方法を等幅の「レポート」ブロックで出す。数字はすべて実測値にする。
- **目次**: 各章へのリンクと、理解度チェックへのリンク。
- **このノートの読み方**: 2 段落。シリーズ内での各パッチの位置づけ（どれが本命でどれが下地か）と、**全章に共通する土台**を関数名で 2〜3 個名指しする。参考実装では `advanceConnectionState()` の状態遷移と `processXactStats()` への統計集約を挙げている。読者はこの 2 つを頭に置いたまま全章を読める。
- **各章**: 章ヘッダ（連番、短い呼び名、タイトル、3〜4 文の要約、事実表）＋ 5 節。
- **末尾**: 理解度チェック。

章ヘッダの事実表には **コミット SHA・コミット件名（英語のまま）・差分（files / +ins / −del）** を置く。読者が `git show` で現物に飛べることが目的なので、SHA は略さずベース側の短縮形をそのまま書く。要約は「何が壊れていて、どう直したか」を機構の名前入りで 3〜4 文。タイトルは日本語、末尾に SHA を重ねて書かない。

## 1 章の骨格：問題 → 設計 → 仕組み → 落とし穴 → テスト

この 5 節は必ずこの順で、この見出しで置く。章によって省いたり増やしたりしない。

| 節 | 答える問い | 書く | 書かない |
| --- | --- | --- | --- |
| 問題 | パッチ前に何が起きていたか | 壊れる仕組みの説明と、実際の端末出力 | 機能が「無かった」という不在の記述だけ |
| 設計 | なぜこの形か | 採用と見送りの対、見送りが壊れる理由 | 一般論としての設計の良し悪し |
| 仕組み | コードは何をしているか | 図 1 枚とコード片 3〜5 個 | 差分の順番どおりの巡回 |
| 落とし穴 | どこで踏み抜くか | 読者が踏む罠と、レビューで実際に出た欠陥 | 「注意して使うこと」という一般的注意 |
| テスト | 何が固定されているか | ケース名と、そのケースが落とす実装ミス | テストファイルの行数や実行方法 |

## 問題 — 何が足りなかったか

**地の文（1 段落）→ 端末出力 → 補足 1 文**、の順に置く。この 3 つを混ぜない。

地の文では、機能の不在ではなく **壊れ方の機序** を書く。「NULL を扱えなかった」ではなく、「`PQgetvalue()` が SQL NULL に空文字列を返す → `makeVariableValue()` が `slen == 0` で false を返す → `ESTATUS_META_COMMAND_ERROR` は `canRetryError()` が偽なのでクライアントが恒久停止する」と、関数名でつながる連鎖にする。最後に、その連鎖が現実のワークロードでどう見えるか（「負荷試験の途中でクライアントが 1 本ずつ静かに死ぬ」）を 1 文添える。

端末出力は **パッチ前のバイナリで実際に採取する**。書き起こしや再構成をしてはいけない。採取手順は次のとおり。

1. パッチ前のコミットをチェックアウトしてビルドする。
2. 最小の再現スクリプトを作る（`cat` で内容を見せられる長さ、5 行以内）。
3. 実行し、標準出力・標準エラーをそのまま貼る。長い集計出力は `... (集計出力) ...` の 1 行に畳んでよい。

貼り方の規則。

- `$` プロンプトから始める。コマンドと出力を 1 つのブロックに入れる。
- ブロックの中に日本語の解説を混ぜない。生成器はプロンプト行と日本語行で地の文と端末出力を切り分けるので、混ぜると分割が壊れる。
- ブロックの後に補足を 1〜2 文だけ置く。ここに書くのは「メッセージだけからは原因が分からない」といった**出力の読み方**と、**パッチ後は同じスクリプトがどうなるか**の 1 行（`processed: 1/1` で正常終了する、など）。

## 設計 — 採った道と捨てた道

判断を **1 判断 1 ブロック** に切る。1 章あたり 3〜5 ブロック。各ブロックは次の 3 つで構成する。

- **採用**: 何をどうしたか。1〜2 文、実装の言葉で書く（「字句解析器が式の先頭に `MODE_SLEEP_EXPR` 疑似トークンを注入し、文法に別 production を持たせる」）。
- **理由**: なぜそれで正しいか。既存コードの性質を根拠にする（「`putVariableValue()` は svalue を free して NULL にし value をそのまま代入するので、`\set var NULL` が作る表現と 1 バイトも違わない」）。
- **見送り**: 捨てた案と、**なぜ壊れるか**。

見送りの書き方がこの節の核である。「別案もあったが採らなかった」で終わらせない。**壊れる機序を、機構の名前と具体的な失敗の形で書く**。参考実装の見本は次のとおり。

> 括弧付きフォールバック。`'(' expr ')'` 自体が expr の production なので、`')'` を読んだ後もパーサは「式が続くのか」を判断するために次のトークンを先読みする（例: `( 1 ) + 1`）。実際 `\set x 1 ms` も `\set x 1 2` も末尾トークンにキャレットが立って syntax error になる。つまり括弧では先読み問題を回避できない。

ここで効いているのは、bison が式の還元に 1 トークン先読みするという**道具の性質**、それが引き起こす**具体的な失敗**（末尾トークンにキャレットが立つ）、そして**実際に試した**という事実の 3 点である。この 3 点がそろわない見送りは書く価値がない。

見送り案が実在しないなら、その項目には見送りを書かない。対を作るために案をでっち上げると、読者は「検討されたが退けられた選択肢」だと信じてしまう。実在した案とは、スペックの初版に書かれていた案、レビューで提案された案、実装中に試して捨てた案のいずれかである。

## 仕組み — コードを読む

機構が言葉だけで追いにくいときは、節の先頭に図を 1 枚、続けてコード片を 3〜5 個置く。

### 図（Mermaid）

- **1 章 1 枚**。分岐と落ち先が見える `flowchart TD` を基本にする。状態遷移が主題なら `stateDiagram-v2`、複数コンポーネントのやり取りなら `sequenceDiagram`。
- **ノードは 12 個まで**。超えるなら図が主題を 2 つ抱えている。片方を落とす。
- **ラベルは日本語**、識別子や関数名はラベルの中に混ぜてよい（`"PQgetisnull(res, ntuples-1, fld)"`）。ラベル内の改行は `<br/>`。
- **ノード ID は英数字**（`A`, `B`, `C1`）。日本語・記号・空白を ID に使わない。
- 図にキャプション番号は付けない。代わりに **図のラベルと、直後のコード片のキャプションで同じ語を使う**。読者は語の一致で図とコードを結ぶ。
- 分岐の枝ラベルは `-- "真" -->` のように引用符で囲む。

構文チェック（貼る前に全項目を確認する）。

| 項目 | 合格条件 | よくある壊れ方 |
| --- | --- | --- |
| ノード ID | 英数字のみ、重複なし | 日本語 ID、同じ ID に別ラベルを 2 回付ける |
| ラベルの引用 | `[" … "]` `{" … "}` で囲む | `(` `)` `:` `,` を裸で入れて解釈が壊れる |
| 改行 | `<br/>` のみ | `\n` や実改行を入れる |
| 括弧の対応 | `[ ]` `{ }` `( )` が閉じている | 判定ノードを `{"…"]` と閉じ違える |
| 枝ラベル | `-- "文字列" -->` | 引用符なしで日本語ラベルを書く |
| 終端 | すべてのノードが到達可能 | 定義しただけで結線し忘れたノード |
| ノード数 | 12 個以下 | 全ケースを 1 枚に詰め込む |

### コード片

- **コミット後の実ファイルからの逐語引用**にする。整形・省略記号の挿入・変数名の短縮をしない。インデントはタブを含めて原文のまま。
- **1 片 20 行程度まで**。関数全体が 20 行を超えるなら、意味の切れる範囲で切る。切ったことを示すために先頭を関数シグネチャから始めるか、キャプションで範囲を書く。
- **キャプションは `パス / 関数名 — 何の断片か`**。例: `src/bin/pgbench/pgbench.c / readCommandResponse() — 格納ループの本体 (パッチの唯一の機能変更点)`。パスと関数名は必須で、括弧内にその片の役割を書く。
- 引用する片は、**変更点そのもの 1 個**、**変更点が依存する既存関数 1〜2 個**、**変更が意図的に触っていない関数 1 個**で構成すると、読者は「何を変えて何を変えなかったか」を同時に受け取れる。

解説（コード片の直後、3〜5 文）は要約ではなく **「なぜこの順序か」「なぜこの位置か」** を語る。

- なぜ判定がこのセルなのか（`PQgetisnull()` と `PQgetvalue()` が同じ `(ntuples - 1, fld)` を指す必要がある理由）。
- なぜこの分岐が先なのか（`v < 64` の線形枝は最初の群を線形にするためだけでなく、`pg_leftmost_one_pos64()` の `Assert(word != 0)` に対するガードでもある。順序を入れ替えると assert 版ビルドで落ちる）。
- なぜこの早期 return が効くのか（`value.type != PGBT_NO_VALUE` の早期 return により、新しく入れた `PGBT_NULL` はここを素通りする）。
- 呼び出し元との関係（どの状態から入り、どこへ戻るか）。

行の逐語説明はしない。読めば分かることは書かず、読んでも分からないことだけを書く。

## 落とし穴

2 種類を混ぜて並べる。1 章あたり 4〜8 項目、各項目は見出し 1 行と本文 2〜5 文。

**(a) 読者が踏む罠。** モード差（simple と prepared で結果が違う）、境界（0 行の結果では変数がそもそも作られない）、既存の非対称（未定義変数だけが本物の SQL NULL をバインドする）、他機能との相互作用（`--max-tries` も `--continue-on-error` も効かない理由）、互換性の変化。実機で確認したものには「実機確認:」を付けて、確認したコマンドと結果を書く。確認していない推測は書かない。

**(b) レビューで実際に見つかった欠陥と、その修正。** これが読者にとって最も価値のある部分で、レビュー時に何を疑うべきかを直接教える。書き方は「症状 → 原因 → なぜ気づきにくいか → どう直したか（テストを含む）」。

> レビューで最初に見つかった重大欠陥。`processXactStats` は `latency = 0.0` で始まり、detailed が偽でも `accumStats` を呼ぶ。したがって `accumStats` にヒストグラム更新を置いただけでは、成功トランザクション全部がバケット 0 に積まれる。失敗モードが「行が出ない」ではなく「もっともらしい 0.001 ms が出る」ことが厄介で、TAP で latency stddev 行を同時に検査することでこれを固定した。

「もっともらしい嘘の値が出る」型の欠陥は必ず書く。読者がレビューで探すべきものはまさにこれである。

## テスト

**何が固定されているか**を、ケース名つきで書く。1 章あたり 3〜5 項目。

各項目は「固定している性質（見出し）」と「どのファイルのどのケース名で、何を実行し、何を要求しているか（本文）」で構成する。

- ファイルパスと **テストケース名を逐語で** 書く（`src/bin/pgbench/t/001_pgbench_with_server.pl` の `"pgbench gset command with NULL ($mode)"`）。読者が `grep` で飛べることが条件。
- 何を要求しているかを具体的に書く。終了コード、stdout に要求する行、stderr に要求する行、`safe_psql` で検証する値。
- **そのテストが落とす実装ミスを 1 文添える**。「`PQgetisnull` の行指定を 0 に変えると、この 2 ケースが同時には通らない」「将来 `getQueryParams()` を変える場合は、意図的な変更としてこのテストを直すことになる」。これがないとテストの一覧はただの目録になる。

実行方法（`make check` の打ち方）や、テストが何件通ったかは書かない。件数は冒頭の masthead に 1 度だけ出す。

## 理解度チェック

ドキュメントの最後に置く。**1 章あたり 4 問**、4 択、即時採点。

- 問うのは **設計判断と落とし穴**。用語の暗記や API の綴りを問わない。良い問いは「この判定に `ntuples - 1` を使う理由として正しいものはどれか」「この案を採っていたら何が起きるか」の形をとる。
- **誤答は実在の誤解から作る**。コードを素直に読むと抱く誤解、他モードでは正しい挙動、レビューで実際に出た誤り。明らかに的外れな選択肢を埋め草に入れない。
- **解説では、最も誘惑的な選択肢を名指しして潰す**。「選択肢 B が最も誘惑的だが、それは simple モードの挙動である」。正解の理由だけを書いた解説は半分しか仕事をしていない。
- 解説の中で選択肢を指すときは **文字（A/B/C/D）** で書く。生成器が選択肢の並びをシャッフルして参照を書き換えるので、素材側で番号を使う場合は 0 始まりと 1 始まりを 1 つのドキュメント内で混ぜない。
- 正解が特定の位置に偏らないようにする（生成器がシャッフルするなら素材側は気にしなくてよい）。
- 各問には出典の章へのリンクを付け、採点後に「取りこぼした章」を一覧できるようにする。

## 正確性の担保

このドキュメントの主張はすべて、コミットの現物と突き合わせて確認できる。確認していない主張を書いてはいけない。

**執筆パスと検証パスを分ける。** 書いた本人（同一エージェント・同一パス）が自分の原稿を検算しても、思い込みはそのまま通る。原稿ができたら、**別のエージェント（あるいは少なくとも別パス）に、原稿とコミットだけを渡して検証させる**。検証側には原稿を書いた経緯を渡さない。参考実装ではこの分離により、実装スペックに「実行時ジャンプが `st->command++` に食われて条件が二度と評価されない」という致命的欠陥が見つかっている。

検証パスの必須項目。

1. **コード片の逐語一致**: 各コード片を、コミット後のファイルから該当箇所を取り出して 1 文字単位で比較する。タブ・空白・コメントを含めて一致すること。一致しないものは原稿側を直す（コードを原稿に合わせない）。
2. **キャプションのパスと関数名**: そのパスが存在し、その関数にその断片が含まれること。
3. **数値**: バケット数（`(29-6+1)*64 + 1 = 1537`）、誤差率（`2^-6 = 1.6%`）、範囲（`2^29 us = 536.871 s`）、差分行数、テスト件数、行番号。**式で書ける数値は式ごと再計算する**。行番号を書いた場合は現在のコミットで実際にその行かを確認する。行番号は陳腐化しやすいので、関数名で位置を示せるなら行番号は書かない。
4. **端末出力**: パッチ前の出力が、パッチ前のバイナリで実際に得られること。エラーメッセージの文言が現物と一致すること。
5. **主張とコミットの対応**: 「パッチは X に触れていない」「テストが Y を固定している」といった主張を、`git show` と実ファイルで裏づける。
6. **見送り案の壊れ方**: 「こう書くと syntax error になる」の類は、実際に試した記録があること。試していないなら、道具の性質から演繹できる範囲に主張を弱める。
7. **クイズの正解**: 各問の正解が本文の記述と矛盾しないこと。誤答が「実は正しい」ものになっていないこと。
8. **Mermaid**: 全図を構文チェック表の全項目に通す。

検証で指摘が出たら、原稿を直したうえで**もう一度検証を回す**。直しが新しい誤りを生むことがある。

## 文体

- **日本語常体**（である調）。一文を短く、主語と述語を明確に。
- **セミコロンを地の文で使わない**。ダッシュもできるだけ避ける。読点と句点で切る。
- **飾らない**。「画期的な」「エレガントな」「うまく」といった評価語を落とす。何が起きるかだけを書く。
- **断定は検証済みのものだけ**。確認していないことは書かない。どうしても触れる必要があるなら「未確認」と明示するか、「別パッチ案件」として範囲外に出す。「たぶん」「はず」で書かない。
- 用語は初出で一言定義する。関数名・マクロ名・状態名は原文どおりの綴りで書き、和訳しない。
- 差分のナレーションをしない。「まず〜し、次に〜する」という書き方が出てきたら、それは論理ではなく手順を書いている。
- 同じことを 2 か所に書かない。落とし穴に書いたことを設計の理由に再掲しない。参照でつなぐ。

## 品質チェック

- 章の数がコミットの数と一致し、順序が適用順になっているか。
- 全章が 5 節（問題・設計・仕組み・落とし穴・テスト）をそろえているか。
