pgbench \sleep の整数溢れ 精読ノート

postgres / src/bin/pgbench — patch 0001

pgbench の \sleep は、約 2148 秒以上を指定すると一切待たずに次のコマンドへ進む。このノートは、その 1 コミットのパッチを、壊れ方の連鎖と設計の選択肢までさかのぼって読み解く。読み終えたら、なぜ換算はエラーで絶対時刻は飽和なのか、なぜ parse 側の 1 行が必要なのかを自分で説明できるはずである。

このドキュメントの読み方

1 コミットのパッチだが、触る場所は 3 つに分かれる。引数を解釈する evaluateSleep()、待ち時間を絶対時刻に変える executeMetaCommand() の META_SLEEP 分岐、そしてスクリプトを読む側の process_backslash_command() である。3 つ目は機能の変更ではなく、1 つ目の実装を成立させるための下地で、これが無いと \sleep 2ms が壊れる。 全体を通して頭に置いておく土台は 2 つある。1 つは advanceConnectionState() の CSTATE_SLEEP で、ここは st->sleep_until と現在時刻を比べるだけの状態であり、待ち時間の妥当性を検査しない。もう 1 つは pgbench が -fwrapv でビルドされることで、int の溢れはクラッシュも警告も起こさず、静かに負の値になる。この 2 つが重なると、壊れた待ち時間は「成功した測定」の形で出力される。

0001/\sleep の整数溢れ

\sleep の待ち時間を int64 で扱い、換算と絶対時刻の溢れを塞ぐ

\sleep の待ち時間は int で保持され、単位からマイクロ秒への換算は検査のない掛け算だった。単位を省略すると秒として 1000000 倍されるので、2148 秒以上の指定は int を溢れて負になり、sleep_until が過去の時刻になって一切待たずに次のコマンドへ進んでいた。待ち時間を int64 に替え、取り込みを strtoint64() に、換算を pg_mul_s64_overflow() に、絶対時刻の加算を pg_add_s64_overflow() による飽和に置き換える。

問題何が足りなかったか

evaluateSleep() は待ち時間を int の局所変数 usec に取り、単位に応じて usec *= 1000000 を行う。単位を省略したときの既定は秒なので、この掛け算は必ず走る。INT_MAX / 1000000 は 2147 なので、2148 秒以上の指定は int を溢れる。pgbench は -fwrapv でビルドされるため値は未定義にはならず負に回り込み、executeMetaCommand() の st->sleep_until = (*now) + usec が過去の時刻になる。CSTATE_SLEEP は now < st->sleep_until の間だけ待つ状態なので、この条件は最初から偽になり、クライアントは待たずに CSTATE_END_COMMAND へ進む。エラーも警告も出ず、トランザクションは成功として計上される。1 時間おきに 1 トランザクションのような低頻度ワークロードを組むと、待ちが全部消えたまま「成功した測定」の見た目で結果が出る。ms 指定でも 2148000 ms 以上で同じことが起きる。

50 分待つはずのスクリプトが 5 ミリ秒で終わり、しかも失敗として数えられていない。出力のどこにも異常は現れないので、測定結果だけを見て気づくことはできない。パッチ後は同じスクリプトが指定どおり 3000 秒待つ。

設計採った道と捨てた道

採用待ち時間を int64 で持ち、単位の掛け算を pg_mul_s64_overflow() で検査して、溢れたら実行時エラーにする。

溢れるのはユーザが指定した値がマイクロ秒として表現できないときだけで、これは入力の誤りである。同じ pgbench の式評価も、掛け算の溢れを pg_mul_s64_overflow() で検出して bigint mul out of range を出す。エラーにすれば語調も既存の \set 系とそろう。

見送り溢れた換算結果を PG_INT64_MAX に飽和させる案。桁を打ち間違えた \sleep 99999999999 s が約 29 万年の待ちに化けるが、エラーが出ないので気づけない。しかも CSTATE_SLEEP は timer_exceeded を見ないので -T を付けていても打ち切られない。直そうとしていた「静かに壊れる」形がそのまま残る。

採用絶対時刻の側、つまり st->sleep_until = (*now) + usec は pg_add_s64_overflow() で検査し、溢れたら PG_INT64_MAX に飽和させる。

ここに来た時点で usec はマイクロ秒として表現できることが確定している。溢れるのは now を足したときだけで、それは要求された待ち時間が長すぎるという意味ではない。CSTATE_SLEEP はこの絶対時刻としか比較しないので、飽和させれば「待ち続ける」に落ちる。

見送り換算側と同じくエラーで統一する案。表現できる待ち時間を要求したクライアントを、pgbench 内部の時刻表現の都合で中断することになる。now は pg_time_now() が返す単調時計の値をマイクロ秒にしたものなので、この加算が溢れるのは指定が int64 の上限そのものに迫るときに限られる。

採用値の取り込みを atoi() から strtoint64(str, errorOK, &result) に替える。

atoi() は範囲外の入力に対して未定義動作で、\sleep 99999999999999999999 のような定数を検出できない。strtoint64() は pgbench 内で \set の整数リテラルにも使われている関数で、範囲外と構文誤りの両方を返す。errorOK を真にして呼べば、関数自身の bigint 向けメッセージは出ず、既存の invalid sleep time "%s" for variable "%s" をそのまま使える。

見送りatoi() の寛容さに合わせて、先頭の数字だけを読む独自の取り込みを書く案。文字列の途中で打ち切る以上、桁数が多すぎる定数は「読めた」ことになり、検出したかった範囲外がそのまま通る。

採用範囲検査は evaluateSleep() の実行時 1 か所に置き、parse 時の process_backslash_command() には足さない。

\sleep :var は変数の値が実行時にしか決まらないので、換算の溢れ検査はどのみち実行時に要る。定数だけを parse 時にも検査すると、同じ換算を 2 か所に書くことになる。

見送り定数の範囲を parse 時に syntax_error で弾く案。スクリプトは起動時に全部読まれるので測定開始前に落とせる利点はあるが、変数経路の検査を消せるわけではないため、重複した換算のコピーが残る。

採用parse 時に数値部を null 終端し、単位の argv[2] は pg_strdup() した複製にする。

\sleep 1ms のように単位を空白なしで書くと、parse 側は argv[1] を "1ms" のまま残し、argv[2] に 'm' の位置を指させていた。これは atoi() が末尾の非数字を読み飛ばす性質に依存した実装で、文字列全体を解釈する strtoint64() では成り立たない。終端しておけば取り込みは定数も変数も同じ 1 行で済む。

見送りevaluateSleep() 側で数字の続く範囲を測り、一時バッファへ複製してから strtoint64() に渡す案。parse 時に一度確定している数字と単位の境界を、\sleep を実行するたびに数え直すことになる。argv[2] が argv[1] の内部を指したままになる点も直らない。

仕組みコードを読む

getVariable() の戻り値をそのまま number で受けているので、エラーメッセージが引用する文字列は変数の値そのものになる。strtoint64() の errorOK を真にしているのは、範囲外のときに関数自身の value "..." is out of range for type bigint を出させず、\sleep が従来から出している文言を保つためである。パッチ前の判定は usec == 0 && !isdigit(*var) で先頭 1 文字しか見ておらず、"0abc" は 0 として通り、範囲外の値は atoi() の未定義動作のまま素通りしていた。

定数側の strtoint64() が失敗しうるのは範囲外のときだけである。先頭が数字であることと単位の綴りは parse 時に検査済みで、そこは変わっていない。単位の分岐は multiplier を決めるだけにしてあるので、掛け算と検査は 1 か所に集まり、us の枝 (multiplier = 1) を通っても pg_mul_s64_overflow() は必ず呼ばれる。unit を argc > 2 ? argv[2] : "s" として先に確定させているのは、エラーメッセージにどの単位で溢れたかを載せるためである。

evaluateSleep() が真を返した時点で usec はマイクロ秒として表現できることが保証されるので、ここで残る溢れは now を足す側だけになる。加算を pg_time_now_lazy() の後に置く必要があるのは、now が確定していないと足せないからである。飽和させた sleep_until は次に示す CSTATE_SLEEP との比較にしか使われないので、PG_INT64_MAX を入れることは「待ち続ける」と同義になる。

壊れていたのはこの比較ではなく sleep_until の作り方だった。負の usec を足した時点で now < st->sleep_until が偽になり、この case は「寝終わった」と判断して CSTATE_END_COMMAND へ進む。だから待ちが消えても失敗にはならない。この節に timer_exceeded の検査がないことも読み取れる。-T の満了は sleep 中のクライアントには届かない。

offsets[2] を先に計算しているのは、c がまだ argv[1] の内部を指しているうちにsyntax_error 用の位置を確定させるためである。pg_strdup(c) を *c = '\0' より前に置く順序も同じ理由で、逆にすると単位が空文字列になる。argv[2] を複製にしたことで、argv を順に pg_free() する free_command() に内部ポインタを渡す形もなくなる。

注意落とし穴

  • 実装中に見つかった欠陥: 空白なしの単位記法が壊れる

    atoi() を strtoint64() に替えただけだと、\sleep 2ms が実行時に invalid sleep time "2ms" で中断する。parse 側が argv[1] を "1ms" のまま残し、単位の argv[2] にその内部を指させていて、数値部が終端されていなかったためである。atoi() が末尾の非数字を読み飛ばすので今まで表面化していなかった。実機確認: *c = '\0' の 1 行だけを外してビルドすると \sleep 2ms が invalid sleep time "2ms" で落ちる。既存の TAP ケース pgbench late throttling がこの記法を使っているので、入れ忘れればテストが落ちる。

  • -T も -t も sleep 中のクライアントを止めない

    CSTATE_SLEEP は sleep_until としか比較せず、timer_exceeded を見ない。threadRun() の待ちは SIGALRM で EINTR になるが、ループの先頭に戻って同じ残り時間を待ち直すだけである。実機確認: \sleep 30 のスクリプトを -T 1 で走らせても 8 秒後に終わっておらず、timeout に kill された。換算の溢れをエラーにした理由でもある。飽和させると、打ち間違えた 1 行が測定を無期限に止める。

  • 変数の値の解釈が厳しくなる

    \sleep :x の x が "1.5" や "0.0" のとき、パッチ前は atoi() が 1 と 0 に切り捨てて通していたが、パッチ後は invalid sleep time で中断する。ドキュメントは以前から integer value を要求しているので文面との差はないが、既存スクリプトの挙動は変わる。バックパッチを master のみにした理由の 1 つである。既存テストの \set one 1.0 が通り続けるのは、getVariable() が double を "%.*g" で文字列化して "1" になるからで、値が "1.5" なら落ちる。

  • 単位ごとに通る上限が違う

    s なら 9223372036854 秒までが通り、9223372036855 秒からは out of range になる。us は int64 の最大値まで換算を通り抜けるので、\sleep 9223372036854775807 us は加算側の飽和で「待ち続ける」に落ちる。実機確認: 前者 2 つは 1 秒の timeout で kill / 即エラー、後者は kill されるまで待つ。

  • 負の待ち時間はそのまま

    \sleep -1 は parse 時に符号が許され、パッチ後も sleep_until が過去になるので即座に次へ進む。溢れの修正であって値域の妥当性検査ではないので、ここは意図的に変えていない。実機確認: 終了コード 0、実行時間 13 ミリ秒。

  • argv[2] の内部ポインタは顕在化していなかった

    パッチ前は argv[2] が argv[1] の途中を指すので、argv を順に pg_free() する free_command() に内部ポインタが渡る形になっていた。free_command() が呼ばれるのは \gset と \aset を直前の SQL コマンドへ畳み込む経路だけで、\sleep のコマンドは解放されないため、実際に踏むことはなかった。この変更で形としても解消する。

検証テストが固定していること

  • 範囲外の定数が未定義動作ではなくエラーになる

    src/bin/pgbench/t/001_pgbench_with_server.pl の @errors に 'sleep constant out of range' を追加した。\sleep 99999999999999999999 を実行し、終了コード 2、stdout に processed: 0/1、stderr に invalid sleep time "99999999999999999999" を要求する。取り込みを atoi() に戻すと、範囲外が何も報告されずに通るのでこのケースが落ちる。

  • 単位換算の溢れがエラーになる

    同ファイルの 'sleep out of range for unit' が \sleep :maxint s を実行する。maxint はテスト共通の -Dmaxint=9223372036854775807 で、秒への換算が必ず溢れる。stderr に sleep time "9223372036854775807" is out of range for unit "s" を要求するので、pg_mul_s64_overflow() の検査を外すと落ちる。

  • 変数の値が整数でなければ受け付けない

    'sleep variable not an integer' が -Dzero=0.0 の変数を使って \sleep :zero を実行し、invalid sleep time "0.0" for variable "zero" を要求する。取り込みを先頭の数字だけ読む実装に緩めると、0 として受理されてエラーが出ず落ちる。

  • 空白なしの単位記法が壊れていない

    既存の 'pgbench late throttling' が \sleep 2ms だけのスクリプト 001_pgbench_sleep を走らせ、processed: [01]/10 と above the 1.0 ms latency limit の行を要求する。parse 時の *c = '\0' を落とすと、このケースが invalid sleep time "2ms" で落ちる。

  • 変数経由の \sleep が従来どおり動く

    既存の 'pgbench backslash commands' が \sleep :one ms、\sleep 100 us、\sleep 0 s、\sleep :zero を続けて実行する。\set one 1.0 が作る double の変数がここを通るので、getVariable() の文字列化と strtoint64() の厳しさが食い違えばこのケースが落ちる。

Q010001 \sleep の整数溢れ

パッチ前の pgbench で \sleep 3000 がエラーも警告も出さずに次のコマンドへ進んだのはなぜか。

CSTATE_SLEEP は sleep_until と now を比べるだけで、待ち時間の符号も妥当性も見ない。3000 * 1000000 が int を溢れて負になり、sleep_until が過去になった時点でこの比較は偽になる。選択肢 A が最も誘惑的だが、evaluateSleep() は溢れを検出できず真を返しているので commandFailed() は呼ばれない。呼ばれていればクライアントは中断し、processed は 1/1 ではなく 0/1 になっていた。選択肢 D は待ちに入った後の話で、そもそもクライアントが CSTATE_SLEEP に留まらないので到達しない。選択肢 B は事実として誤りで、-fwrapv は回り込みを定義するだけで値を 0 にはしない。

Q020001 \sleep の整数溢れ

パッチ後の pgbench で \sleep 9223372036854775807 us を実行すると何が起きるか。

us の枝は multiplier が 1 なので pg_mul_s64_overflow() は溢れない。溢れるのは now を足す側で、そこは pg_add_s64_overflow() が真を返して sleep_until が PG_INT64_MAX になる。選択肢 C が最も誘惑的だが、out of range になるのは s や ms のように掛け算がある単位のときである。選択肢 A は 9223372036854775807 がちょうど int64 に収まるので誤り。選択肢 D はパッチ前の挙動で、飽和処理がその経路を塞いでいる。

Q030001 \sleep の整数溢れ

単位換算が溢れたときにエラーではなく PG_INT64_MAX へ飽和させる案が退けられた理由はどれか。

換算の溢れは、ユーザの指定がマイクロ秒として表現できないという入力の誤りである。黙って別の値に読み替えると、直そうとしていた「静かに壊れる」形がそのまま残る。同じ飽和でも絶対時刻の側で採っているのは、そちらの溢れが入力の誤りではなく時刻表現の限界だからである。選択肢 A が最も誘惑的だが、比較は now < sleep_until なので飽和させると偽ではなく真になり、待ち続ける方に倒れる。選択肢 B は誤りで、飽和も検査も実行時に行えば足りる。選択肢 C は根拠がなく、飽和させた場合は正常終了する。

Q040001 \sleep の整数溢れ

atoi() を strtoint64() に替える一方で、parse 側の *c = '\0' を入れ忘れると何が観測されるか。

終端しないと argv[1] は "2ms" のままで、文字列全体を解釈する strtoint64() が失敗する。実機でも *c = '\0' の 1 行を外すと invalid sleep time "2ms" が出る。選択肢 B が最も誘惑的だが、それは末尾の非数字を読み飛ばす atoi() の性質であって、strtoint64() は途中で打ち切らない。選択肢 D は誤りで、数値と単位の分割そのものは parse 時に成功しており、単位の綴りも既知のものである。選択肢 C は free_command() が \gset と \aset の畳み込み経路でしか呼ばれないので起きない。
