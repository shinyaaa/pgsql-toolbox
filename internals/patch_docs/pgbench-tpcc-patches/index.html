0001/\gset の NULL

pgbench の \gset / \aset が SQL NULL を null 値として保存する

readCommandResponse() が結果列を常に PQgetvalue() で取得していたため、SQL NULL は空文字列として変数に入り、その変数を式で使った瞬間にクライアントが abort していた。PQgetisnull() で分岐し、NULL の列だけ setNullValue()+putVariableValue() で格納することで、`\set varname NULL` と完全に同じ null 値になる。

問題何が足りなかったか

readCommandResponse() の \gset / \aset 格納ループは、全列を PQgetvalue() で取り出して putVariable() に渡していた。PQgetvalue() は SQL NULL に対して空文字列を返すが、pgbench の式言語では空文字列は値として不正である (makeVariableValue() は slen==0 で無条件に false を返す)。そのため NULL を捕まえた変数を最初に式で使った時点で「evaluation of meta-command failed」となり、これは ESTATUS_META_COMMAND_ERROR、つまり canRetryError() が偽を返す非リトライ系エラーなのでクライアントがそこで恒久的に停止する。TPC-C の Delivery のように空の district から min(no_o_id) を取るスクリプトでは、負荷試験の途中でクライアントが1本ずつ静かに死んでいく。式言語自体は PGBT_NULL・IS NULL・三値論理を最初から持ち `\set var NULL` も書けるのに、\gset だけが null 値を生成できない producer だった。

makeVariableValue() は空文字列について何もログを出さないので、メッセージだけからは「NULL が原因」と分からない。パッチ後は同じスクリプトが debug(script=0,command=2): null を出して正常終了する (processed: 1/1)。

設計採った道と捨てた道

採用NULL の列は setNullValue() で PgBenchValue を作り putVariableValue() で格納する。非 NULL の列は従来どおり putVariable(PQgetvalue(...))。

putVariableValue() は svalue を free して NULL にし value をそのまま代入するので、結果の内部表現は `\set var NULL` が作るもの (svalue=NULL, value.type=PGBT_NULL) と1バイトも違わない。遅延パース (makeVariableValue) を一切経由せず、格納時点で null 値が確定する。

見送りputVariable(&st->variables, ..., "NULL") と文字列 "NULL" を格納する案。makeVariableValue() が pg_strcasecmp(svalue, "null") で null 値に変換するので式の上では動いてしまうが、svalue には4文字の "NULL" が残り value.type は PGBT_NO_VALUE のままで、`\set var NULL` の表現と一致しない。目標が「\set var NULL と等価にする」ことなので、たまたま動く表現を選ぶ理由がない。

採用拡張/prepared モードのパラメータバインドには一切手を入れず、ドキュメントに制限として明記するだけにする。

getQueryParams() は getVariable() の戻り値をそのまま libpq に渡すだけで、getVariable() は PGBT_NULL を "NULL" という文字列にレンダリングして svalue にキャッシュする。したがって -M prepared では :nv は4文字の文字列 "NULL" としてバインドされる (実機確認: INSERT INTO t VALUES (:nv) の結果は t = 'NULL')。これは \gset 起因ではなく `\set v NULL` の既存挙動そのもので、\gset 経由の PGBT_NULL は表現が同一なので新たな乖離は生じない。

見送りgetQueryParams() で PGBT_NULL のとき libpq に NULL ポインタを渡し、本物の SQL null をバインドする案。これは既存の `\set v NULL` の挙動 (現在は invalid input syntax for type integer: "NULL" で失敗する) を変えてしまい、互換性議論を伴うので独立したパッチ・スレッドに属する。なお未定義変数は既に NULL ポインタ経由で本物の SQL NULL がバインドされるという非対称が存在しており、それも含めて別途整理すべき話題。

採用NULL 判定は PQgetisnull(res, ntuples - 1, fld)。既存の PQgetvalue(res, ntuples - 1, fld) と同じセルを見る。

この格納ループは \gset と \aset で共有されている。\aset は行数を制限せず「最後の行を残す」仕様なので、判定セルと格納セルがずれると変数の値と NULL 判定が食い違う。\gset は ntuples==1 が保証されているので結果的に同じセルになる。

見送り0 行目を見る案、あるいは「結果セット内に1つでも NULL があれば null」とする案。前者は \aset で最終行以外を見てしまい、ORDER BY ... NULLS LAST/FIRST を切り替えるだけで値と NULL フラグが矛盾する。後者は \aset の「最後の行を残す」仕様そのものと矛盾する。

採用サーバが返した空文字列は空文字列のまま格納する。SQL NULL だけを null 値に写す。

'' と NULL は別の値であり、両者を区別できるようにすること自体がこのパッチの目的の一つ。TAP テストでも :es を引用符の中に埋めて '[]' が入ることを確認している。

見送りmakeVariableValue() の slen==0 のケースも null 値にマップして「式で使えない値」を一掃する案。空文字列を捕まえたスクリプトが黙って NULL 扱いになるうえ、\gset が復元したばかりの区別を再び潰す。空文字列を式で使うと今も abort するが、それは makeVariableValue() 側の別問題として残す。

仕組みコードを読む

PQgetisnull() と PQgetvalue() が同じ (ntuples - 1, fld) を指しているのが要点。\aset は各結果セットの最終行を残すので、この一致が崩れると値と NULL 判定がずれる。パッチは戻り値を bool ok にまとめ、既存の「error storing into variable」エラー分岐 (ESTATUS_META_COMMAND_ERROR → goto error) を両パスで共有している。ループの外側は PGRES_TUPLES_OK かつ (is_last && META_GSET) または META_ASET のときだけ入る点、\aset で 0 行の結果は手前で break される点は変わっていない。

putVariable() が svalue に文字列を入れて value.type = PGBT_NO_VALUE にする (= 遅延パース待ち) のに対し、putVariableValue() は svalue を捨てて NULL にし、値を直接確定させる。だから \gset 由来の null 変数は svalue=NULL / value.type=PGBT_NULL となり、`\set v NULL` (executeMetaCommand の META_SET も evaluateExpr の結果を putVariableValue で入れる) と同一表現になる。context 引数は "gset" / "aset" で、不正な変数名のときのエラーメッセージにだけ使われる。

evaluateExpr() の ENODE_VARIABLE はここを通る。旧コードでは NULL が "" で入っていたので slen==0 の枝でメッセージも出さずに false を返し、呼び出し元の executeMetaCommand() が commandFailed("evaluation of meta-command failed") → CSTATE_ABORTED → ESTATUS_META_COMMAND_ERROR に落ちていた。冒頭の value.type != PGBT_NO_VALUE の早期 return により、putVariableValue() で入れた PGBT_NULL はここを素通りする。なお pg_strcasecmp(svalue, "null") の枝があるため、サーバが返した文字列 'null' も式の上では null になる (この副作用は本パッチでは変わらない)。

simple モードの変数展開 (assignVariables) も、拡張/prepared モードの getQueryParams() も、どちらもこの関数を通る。PGBT_NULL は引用符なしの NULL という4文字にレンダリングされ、svalue にキャッシュされる。simple モードでは INSERT INTO t VALUES (:nv) がそのまま SQL の NULL リテラルになるので本物の SQL NULL が入るが、getQueryParams() は params[i] にこの4文字文字列を渡すだけなので、prepared モードでは text 列に 'NULL' という文字列が入る。パッチが getQueryParams() に触れていないのはこの差を意図的に据え置いたため。

注意落とし穴

  • -M extended / prepared では本物の SQL NULL にならない

    getQueryParams() は getVariable() の戻り値をそのまま渡すので、PGBT_NULL 変数は4文字の文字列 "NULL" としてバインドされる。実機確認: SELECT NULL AS nv \gset の後に -M prepared で INSERT INTO t VALUES (:nv) すると t = 'NULL' (IS NULL は偽)。int 列なら invalid input syntax for type integer: "NULL" になる。これは `\set v NULL` の既存挙動と同じで本パッチが悪化させたわけではないが、simple モード (引用符なし NULL リテラル → 本物の SQL NULL) とモードで結果が変わる点は罠。ドキュメントに明記されている。

  • 未定義変数だけが本物の SQL NULL をバインドするという非対称

    getQueryParams() は getVariable() が NULL ポインタを返したとき (= 変数が存在しない) それをそのまま PQsendQueryParams に渡すため、-M prepared で :undefvar を使うと libpq が SQL NULL としてバインドする (実機確認: 行の x IS NULL が真)。つまり「定義された NULL 値」は文字列 "NULL"、「未定義」は本物の NULL、という逆転が既存で存在する。この整理は別パッチ案件。

  • simple モードの補間は引用符なしなので、引用符の中に置くと4文字の文字列になる

    NULL 変数は SQL テキストに NULL という裸の語として埋め込まれる。VALUES (:nv) なら SQL NULL だが、VALUES ('[:nv]') と書くと '[NULL]' という文字列になる。TAP テストは空文字列側を '[:es]' で確認していて、引用符文脈では NULL / '' の扱いが根本的に違うことを示している。

  • \aset で結果が 0 行のときは変数が NULL にならず、そもそも設定されない

    格納ループの手前に `else if (meta == META_ASET && ntuples <= 0) break;` (coldly skip empty result) があるため、0 行の結果では変数が作られない。実機確認: SELECT 1 AS z WHERE false \aset の後に debug(:z) すると undefined variable "z" で abort する。「行が無い」と「行はあるが NULL」は別物であり、このパッチは後者しか救わない。

  • サーバが返した文字列 'null' は式の上で null と区別できない

    makeVariableValue() が pg_strcasecmp(svalue, "null") で null 値へ変換するため、SELECT 'null'::text AS v, 'NuLl'::text AS w \gset の後 debug(:v) も debug(:w) も null を出す (実機確認)。区別が完全に戻ったのは NULL と '' の間だけで、NULL と文字列 'null' の間ではない。ただし SQL テキストへ補間する経路は svalue をそのまま使うので、そちらでは 'null' のまま残る。

  • 旧挙動は --max-tries でも --continue-on-error でも救えなかった

    空文字列変数の式評価失敗は ESTATUS_META_COMMAND_ERROR になる。canRetryError() が真を返すのは ESTATUS_SERIALIZATION_ERROR と ESTATUS_DEADLOCK_ERROR だけ、canContinueOnError() が扱うのは ESTATUS_OTHER_SQL_ERROR だけなので、どちらのオプションも効かずクライアントが落ちて「Run was aborted」になる。だからこれは単なる不便ではなく、長時間ベンチを静かに壊す罠だった。

  • 互換性: 以前 NULL を補間していたスクリプトの結果が変わる

    旧挙動では NULL 列は "" になり、SQL テキストに補間すると VALUES () のような構文エラーを起こすのが普通だった。パッチ後は NULL が埋まるので構文エラーが消え、SQL としては通る。式で使わず補間だけしていた稀なスクリプトは挙動が変わりうるので、コミットメッセージにも behavior change として明記されている。

  • パイプラインモードとの相互作用は無い

    \gset / \aset はパイプラインモードで禁止されている (実行時にエラー) ため、この変更がパイプライン中の結果処理に絡むことはない。readCommandResponse() の PGRES_PIPELINE_SYNC 分岐は varprefix == NULL の経路であり、格納ループには到達しない。

検証テストが固定していること

  • NULL を捕まえた変数が式で使えること、および IS NULL が真になること (simple と prepared の両モード)

    src/bin/pgbench/t/001_pgbench_with_server.pl の "pgbench gset command with NULL ($mode)" ケース。スクリプト 001_pgbench_gset_null_$mode で SELECT NULL AS nv \gset → \set i debug(:nv) → \if :nv IS NULL → \set i debug(:nv IS NULL) → \endif を実行し、終了コード 0、stdout に processed: 1/1、stderr に command=2.: null と command=4.: boolean true を要求する。command=4 の debug が出ること自体が \if の枝が取られた証拠になっている (旧コードならそもそも command=2 で abort する)。

  • NULL と空文字列が補間先で別物のまま残ること

    同ファイルの "pgbench gset NULL interpolation" ケース。UNLOGGED TABLE gset_null_tab を作り、SELECT NULL AS nv, ''::text AS es \gset の後 INSERT ... VALUES (1, :nv) と VALUES (2, '[:es]') を実行。その後 safe_psql で t IS NULL (id=1) が 't'、t = '[]' (id=2) が 't' であることを検証する。引用符の外の NULL は SQL NULL に、引用符の中の空文字列は空文字列になる。

  • 拡張/prepared モードでは NULL 変数が文字列 "NULL" としてバインドされるという文書化済みの制限

    同ファイルの "pgbench gset NULL as query parameter" ケース。-M prepared で SELECT NULL AS nv \gset → INSERT INTO gset_null_tab VALUES (3, :nv) を実行し、safe_psql で t = 'NULL' が 't' であることを確認する。制限を明示的に固定しているので、将来 getQueryParams() を変える場合は意図的な変更としてこのテストを直すことになる。

  • \aset が判定するのは各結果セットの最終行であること

    同ファイルの "pgbench aset command with NULL" ケース。SELECT * FROM (VALUES (1), (NULL)) AS v(n) ORDER BY 1 NULLS LAST \aset の後は debug が null、NULLS FIRST に変えた後は int 1 になることを stderr の command=2.: null / command=4.: int 1 で確認する。PQgetisnull の行指定を 0 などに変えると、この2ケースが同時には通らない。

0002/\sleep の式

pgbench: \sleep の引数に式を書けるようにする

\sleep が受け付けるのを整数定数か :変数 だけから \set と同じ式全体に広げ、末尾の us/ms/s も従来どおり書けるようにした。字句解析器が式の先頭に MODE_SLEEP_EXPR 疑似トークンを注入し、文法側の別 production が単位を読んで倍率を式に畳み込むので、実行時は cmd->expr を評価して整数化するだけになる。

問題何が足りなかったか

TPC-C の think time は指数分布 (仕様 5.2.5.4) なので、待ち時間は実行のたびに計算する必要がある。ところが \sleep の引数は整数定数か単一の :変数 参照しか許されず、パーサが自前で argv を切って atoi する専用コードになっていた。そのため計算した待ち時間を使うには一度 \set でスクラッチ変数に入れる二行のイディオムが必須で、スクリプトごとに変数名前空間を汚す。式を評価するほかのメタコマンド (\set/\if/\elif) との一貫性もなかった。

単語で argv に分割していたため。1 単語に詰めた \sleep (1+1) でも "invalid sleep time, must be an integer" で読み込み時に落ちる。したがって従来は \set think_ms least(int(-12000.0 * ln(double(random(1,1000000)) / 1000000.0)), 120000) \sleep :think_ms ms と二行書くしかなかった。

設計採った道と捨てた道

採用単位は「式の後から読む」のではなく、字句解析器が式の先頭に MODE_SLEEP_EXPR 疑似トークンを注入し、文法に result: MODE_SLEEP_EXPR expr opt_unit という別 production を持たせて解決する。expr_scanner_init() に sleep_expr フラグを追加し、process_backslash_command() は META_SLEEP を \set/\if/\elif と同じ式パースの枝で処理する。

bison の LALR パーサは式を還元し終えるために必ず 1 トークン先読みする。したがって expr_yyparse() を呼んだ時点で末尾の単位トークンはパーサに食われており、「パースが終わってから残りの単語を単位として見る」ことは原理的にできない。先頭にモード選択トークンを入れれば、パーサはどの production にいるかを最初から知っているので、単位を文法の一部として自然に扱える。

見送り元スペックの本命案「行の最後の単語が us/ms/s かを先に単語走査で調べ、その手前までの範囲を式スキャナで再パースする」。exprscan.l は部分バッファのスキャンをサポートしないと明記しており (expr_scanner_get_substring 付近のコメント)、expr_scanner_init は進行中のスキャン状態を差し替えるだけである。仮に別の PsqlScanState を作ると、syntax_error のオフセットはスクリプト全体のバッファ基準なので行番号とキャレット表示が壊れる。

採用単位を曖昧さなく区切るための「\sleep ( expression ) [unit]」という括弧付き構文も採らない。単位サポートは文法側に置く以外に道はない、と結論した。

opt_unit を FUNCTION トークンで受ける形にすれば、既存文法では完全な expr の直後に裸の FUNCTION が来ることはあり得ない (FUNCTION は必ず '(' を伴うプライマリの先頭にしか現れない) ため衝突が生じない。exprparse.y には %expect 0 があるので、もし競合を作ってしまえばビルドが失敗して即座に気づける。

見送り括弧付きフォールバック。'(' expr ')' 自体が expr の production なので、')' を読んだ後もパーサは「式が続くのか」を判断するために次のトークンを先読みする (例: ( 1 ) + 1)。実際 \set x 1 ms も \set x 1 2 も末尾トークンにキャレットが立って syntax error になる。つまり括弧では先読み問題を回避できない。

採用単位の倍率は Command に保持せず、パース時に make_op(yyscanner, "*", $2, make_integer_constant($3)) で式木に畳み込む。実行時の evaluateSleep() は evaluateExpr() + coerceToInt() だけになり、usec の型は int から int64 に広げる。

既存の "*" 関数がオーバーフロー検査 (bigint mul out of range) と int/double の型昇格を持っているので、掛け算のためのコードを新しく書かずに済む。畳み込みは式木の根に対して行われるため、単位は式全体に掛かる: \sleep 1 + 1 ms は 2 ミリ秒であり、テキスト的に最後の項だけに掛かることはない。Command 構造体に新フィールドも要らない。

見送りベーススペックの「cmd->expr を再利用しつつ単位は argv に残し、実行時に evaluateSleep で掛ける」案。Command に単位を保持する必要が生じるうえ、int64 のオーバーフロー検査を手書きすることになり、既存の演算子実装と重複する。

採用負の値はエラーにせず 0 にクランプし、その旨をドキュメントに書く。エラーメッセージの完全互換は諦め、「失敗する段階 (読み込み時か実行時か)」の互換だけを保証する。ただし "unrecognized time unit, must be us, ms or s" は一字一句維持する。

\sleep -1 s は現状も受理され (旧コードは符号をスキップしていた)、sleep_until が過去になるだけの no-op だった。エラー化は受理されていた書式の非互換になる。一方メッセージ本文は bison が出す診断に変わるため維持不可能で、missing argument / too many arguments / sleep: undefined variable の 3 つは文言が変わる。これらは t/001 の正規表現でしか固定されておらず API ではない。

見送りスペック原文の「ゴミ入力に対する現在のエラー挙動を含めた完全な後方互換は必須」。パース診断が bison 由来になった時点で文言一致は達成不能なので、段階パリティ (壊れた引数・引数なし・余分なトークン・不正な単位は読み込み時、未定義変数や型不正は実行時) に要件を弱めた。

仕組みコードを読む

flex 規則にマッチする前に走る yylex() の先頭コード。expr_scanner_init(..., sleep_expr) が立てたファイルスコープの sleep_expr_pending が真なら、入力を一切消費せずに MODE_SLEEP_EXPR を 1 回だけ返し、フラグを下ろす。expr_source / expr_command といった既存の静的変数と同じ流儀で、スキャナの状態機械には手を入れていない。フラグは expr_scanner_init が毎回 true/false どちらかを代入するので、次のコマンドに持ち越されることはない。\sleep は \set と違って引数語を先に単語レキシングしないので、この注入が引数の最初のトークンより前に来ることが保証される。

開始記号が 2 本立てになった。先頭に MODE_SLEEP_EXPR が来た場合だけ、式のあとに opt_unit を許す。アクションでは式木の根に "*" 演算子ノードを被せ、右辺に単位倍率 (マイクロ秒) の整数定数を置く。以後 \sleep の引数は「マイクロ秒を返す普通の式」でしかなく、Command 側に単位を覚える場所は要らない。畳み込みは構文木レベルなので演算子優先順位の影響を受けず、\sleep 1 + 1 ms は (1 + 1) * 1000 = 2 ミリ秒になる。

単位は識別子なので字句解析器からは FUNCTION トークンとして届く。ここでは find_func() を通さず、pg_strcasecmp で us/ms/s を判定して倍率に変換する (旧実装と同じく大文字小文字は区別しない: \sleep 1 US も通る)。未知の単位は expr_yyerror_more で読み込み時に落ち、メッセージは旧実装から一字一句そのまま。expr_yyerror_more は行末までレキシングして行全体とキャレットを表示してから exit(1) する。FUNCTION を単位として shift するのは「完全な expr の直後」という状態だけで、そこで FUNCTION を function に還元する経路は存在しないため競合は生じない (%expect 0 が番人になる)。

旧版は Variables* と argc/argv を受け取り、getVariable + atoi + 単位の掛け算を自前でやる 40 行弱だった。新版は式を評価して整数に落とすだけ。coerceToInt は double を rint() で丸め、NULL と boolean は "cannot coerce %s to int" で失敗させる (これが \sleep null / \sleep true の実行時エラーの正体)。倍率は式に畳み込み済みなので、丸めが起きるのはマイクロ秒に換算した後である点に注意 (\sleep 0.4 s は 400000us であって 0 ではない)。負値は歴史的挙動に合わせて 0 にクランプする。出力は int64 で、旧版の int は 2148 秒付近で溢れていた。

式の評価は実行のたびに行われるので、ランダムな think time が毎トランザクション変わる。評価に失敗すれば commandFailed して CSTATE_ABORTED (クライアント異常終了、終了コード 2)。成功すれば絶対時刻 sleep_until を置いて CSTATE_SLEEP を返し、advanceConnectionState() は now < sleep_until の間 return するだけでスレッドループに制御を戻す (スレッドは threadRun() 側で sleep_until - now を select のタイムアウトに使う)。usec が int64 になったため now + usec が int64 を超え得るようになり、pg_add_s64_overflow で INT64_MAX に飽和させている。飽和させないと sleep_until が過去に回り込み、巨大な待ち時間が「即座に起床」に化ける。

注意落とし穴

  • 単位を後から読むことは原理的にできない

    bison のパーサは expr を還元するのに常に 1 トークン先読みするため、expr_yyparse() から戻った時点で単位トークンは既に消費 (あるいはエラー扱い) されている。\set x 1 ms が "syntax error in command \"set\"" になりキャレットが ms に立つのがその証拠。括弧で囲む案も '(' expr ')' 自体が expr なので同じ先読みが起き、回避にならない。

  • 単位は FUNCTION トークンなので、識別子でない単位は別のエラーになる

    \sleep 1 week と \sleep 1 abs はどちらも "unrecognized time unit, must be us, ms or s (week|abs)" になる (opt_unit の中では find_func を呼ばないので、既存関数名でも単位として扱われて弾かれる)。一方 \sleep 1 END や \sleep 1 5 は END_KW / INTEGER_CONST であって FUNCTION ではないため、単位エラーではなく素の "syntax error in command \"sleep\"" になる。\sleep 1 s s も 2 個目の s は文法上どこにも置けず syntax error。

  • 丸めは単位換算の後に起きる

    倍率が式木に畳み込まれているので、実行時の計算順序は「式の値 × 倍率 → coerceToInt」である。\sleep 0.4 s は 0.4*1000000 = 400000us となり、0.4 を先に丸めて 0 にはならない。旧実装は atoi なので小数を扱えず、\sleep :v で v=1.7 は 1 に切り捨てられていたが、今は rint されて 1.7ms 相当になる。文字列変数の扱いも変わり、v="150abc" は atoi による黙った切り捨てではなく "malformed variable \"v\" value: \"150abc\"" という実行時エラーになる。

  • sleep_until のオーバーフロー

    usec が int から int64 になったことで、now + usec が int64 の範囲を超え得る。\sleep 9223372036854775807 us が典型で、無防備だと sleep_until が負に回り込み「一瞬で起床」になる (これは旧実装が int の桁あふれで 2148 秒以上のスリープを事実上無効化していたのと同じ壊れ方)。pg_add_s64_overflow で検出して PG_INT64_MAX に飽和させ、threadRun() が計算する sleep_until - now が正のままになるようにしている。なお \sleep 9223372036854775807 s は掛け算の段階で "bigint mul out of range" になり、飽和ではなくコマンド失敗になる。

  • エラーが起きる「段階」が一部変わる

    文法的に正しいが数値でない引数 (\sleep true, \sleep null) は、旧実装では読み込み時に落ちたが、今はパーサを通ってしまい coerceToInt で実行時に落ちる (終了コード 1 ではなく 2)。逆に 64 ビットに収まらない整数定数 (\sleep 99999999999999999999) は旧実装では atoi 任せで受理されていたが、今は字句解析器が "bigint constant overflow" で読み込み時に落とす。なお 1e20 は DOUBLE_CONST なので読み込みは通り、実行時に "double to int overflow" になる。

  • process_backslash_command() の枝が変わり argv 検査が効かなくなる

    META_SLEEP は \set/\if/\elif と同じ式パースの枝に移り、その枝は expr_scanner_init → expr_yyparse → return で早期に戻る。したがって残りの単語を argv に集めるループも MAX_ARGS チェックも \sleep には走らない (\sleep too many args が "too many arguments" ではなく "unexpected function name (too)" になるのはこのため)。旧 \sleep ブロックだけが使っていたローカル配列 offsets[MAX_ARGS] は未使用になるので同時に削除している。

検証テストが固定していること

  • 従来書式と新しい式書式が同一スクリプトで動くこと (受理側の回帰)

    t/001_pgbench_with_server.pl の 'pgbench backslash commands' ケースのスクリプトに "-- sleep expressions" ブロックを追加。\sleep (:one + 1) us (括弧付きの式)、\sleep 1ms (空白なしの単位)、\sleep least(0, :zero - 1) s (関数呼び出しで負値 → 0 クランプ) を並べ、既存の \sleep :one ms / \sleep 100 us / \sleep 0 s / \sleep :zero と一緒に exit 0 と processed: 1/1 を確認する。:one は \set one 1.0 で double なので、double 引数が通ることも同時に押さえている。

  • 失敗が起きる段階と終了コード

    t/001_pgbench_with_server.pl の @errors 表。読み込み時 (status 1): 'sleep too many args' が /unexpected function name \(too\)/、'sleep missing arg' が /syntax error in command "sleep"/、'sleep unknown unit' が /unrecognized time unit/。実行時 (status 2): 'sleep undefined variable' が /undefined variable "nosuchvariable"/、新規追加の 'sleep null' が /cannot coerce null to int/、'sleep not an int' (\sleep true ms) が /cannot coerce boolean to int/。段階パリティという設計判断をそのままテストに落としたもの。

  • サーバ不要のスクリプト構文チェックと、維持すると決めたメッセージ

    t/002_pgbench_no_server.pl の @script_tests に 3 件追加。'sleep bad expression' (\sleep 1 +) は /syntax error in command "sleep"/ と /\^ error found here/ の両方を要求し、式パーサ由来の診断でもキャレット付きの行表示が壊れていないことを固定する。'sleep missing argument' (\sleep のみ) も同じ構文エラー。'sleep bad unit' (\sleep 1 week) は /unrecognized time unit, must be us, ms or s \(week\)/ で、一字一句維持すると決めたメッセージを固定する。

0003/\while ループ

pgbench に \while / \endwhile ループを追加する

問題何が足りなかったか

pgbench のスクリプト言語には条件分岐 (\if) はあるがループがない。TPC-C 風のワークロードでは New-Order が 5〜15 本のオーダーラインを、Delivery が 10 個の district を処理するといった可変長の反復が本質的で、これを書くには (a) 最大回数までボディを展開して \if で個々の反復を潰す、(b) ループをサーバ側の DO ブロックに移す、のどちらかしかなかった。(a) はスクリプトが巨大になり、同じ SQL が別コマンドとして -r 統計に分散する。(b) はクライアントのラウンドトリップが消えるので、そもそも測っている対象が変わってしまう。

設計採った道と捨てた道

採用実行時のジャンプを executeMetaCommand() で直接行わず、CState に int pending_jump を持たせて CSTATE_END_COMMAND まで遅延させる。

CSTATE_END_COMMAND は -r 統計のために commands[st->command] を読み直して addToSimpleStats() し、そのあとで st->command++ する。ジャンプ先の代入をこの増分の直前に置くことで、統計は「実際に実行したコマンド」に付き、増分をジャンプで置き換える形にできる。pending_jump は設定した直後の CSTATE_END_COMMAND で必ず消費されるので、CSTATE_START_TX での -1 初期化と CSTATE_END_TX の Assert(st->pending_jump == -1) だけで整合が取れる。

見送りexecuteMetaCommand() の中で st->command = command->jump_target と代入する案 (元の仕様案)。壊れる: (a) \endwhile の後方ジャンプ先が直後の st->command++ で while+1 になり、条件が二度と評価されない無条件の無限ループになる。(b) \while の偽ジャンプは目的地を 1 つ行き過ぎ、ループ直後のコマンドを黙って飛ばす。(c) -r ではメタコマンドの latency が「実行されていないジャンプ先コマンド」の統計に加算される。代わりに CSTATE_START_COMMAND を返す案も不可で、executeMetaCommand() の直後の Assert が WAIT_RESULT/END_COMMAND/SLEEP/ABORTED しか許さず、かつコマンド単位統計そのものを飛ばしてしまう。

採用-T 満了時は「\while が条件を評価せずに偽として扱う」という 1 か所のグローバルな規則にする。\endwhile 側は変更せず、常に後方ジャンプする。

timer_exceeded は SIGALRM が立てる sig_atomic_t で、実行中にクリアされない単調なフラグ。したがって一度立てば、どの \while も即座に抜ける。\endwhile の後方ジャンプが着地する先はその \while なので、入れ子がいくつあっても順にほどけ、スクリプト末尾 (通常は COMMIT) が普通に実行され、CSTATE_END_TX が通常どおりトランザクションを計上してから既存のタイマーチェックでクライアントを終了させる。メタコマンドだけのループに -T が効くのもこの経路。

見送り\endwhile で CSTATE_FINISHED にする案。既存のタイマーチェックはすべてトランザクション境界 (CHOOSE_SCRIPT / THROTTLE / END_TX など) にあり、スクリプト途中で切る挙動は今日どこにも存在しない。導入するとトランザクションを開いたまま接続を閉じ、-r のコマンド単位データ点は記録済みなのに processXactStats() を通らず、END_TX の整合チェックも迂回する。もう一つの「そのループだけ break する」案も入れ子に対して不十分で、内側を抜けた先の外側 \endwhile が後方ジャンプして内側ループに再突入しうる。フラグを見る場所を \while 1 か所に固定するとこの穴が消える。

採用\if 系と \while 系を 1 本のスタック (ScriptBlock { is_while, saw_else, command }) で検査する pgbench ローカルの静的パスにし、CheckConditional() を CheckScriptStructure() に置き換える。

閉じ側・分岐側のトークン (\elif/\else/\endif/\endwhile) が必ず「一番内側の開いたブロックの種別」を見るので、交差した入れ子は最初の交差トークンかスクリプト末尾で必ず捕まる。結果としてループは条件分岐の 1 つの枝に完全に含まれ、条件ブロックは 1 つのループボディに完全に含まれることが保証される。同じパスで \while と \endwhile を相互リンクし、jump_target を静的に埋める。

見送りfe_utils の ConditionalStack / ifState を拡張する案。この enum は psql と共有されており、pgbench 専用の WHILE フレームを表現するために共有の型を太らせることになる。\if 用と \while 用に別々のスタックを持つ案も不可で、\if 1 \while 1 \endif \endwhile のような交差はどちらのスタックも単体では balanced に見えるため検出できない。

採用ループとパイプラインの組み合わせにパース時の制限を新設せず、既存の実行時ガードに任せる。リトライ時のクライアント変数の復元も行わない。

ボディ内に \startpipeline と \endpipeline が揃っている正しい形は、PGRES_PIPELINE_SYNC の処理でパイプラインモードを抜けるため反復をまたいで動く。誤った形 (開いたまま後方ジャンプ) は 2 回目の \startpipeline が既存の "already in pipeline mode" でクライアントを abort させる。リトライについては CSTATE_RETRY が復元するのは乱数状態 (st->cs_func_rs = st->random_state) と st->command = 0 だけで、変数のスナップショットは CState に存在しない。

見送りループを意識したパイプラインの対応チェックを parse 時に追加する案。そもそも \startpipeline/\endpipeline の対応は今日まったく静的検査されていないので、ループ絡みだけ検査するのはスコープの不整合。CState に変数スナップショットを持たせてリトライで復元する案も却下で、既存の全スクリプトのリトライ意味論を変えてしまう。代わりに「条件が読む変数をすべてスクリプト内でループ前に代入していれば反復数は再現する」ことをドキュメント化した。

仕組みコードを読む

-T が満了していたら式を評価すらせずに脱出ジャンプを予約する。式を評価しないのは意図的で、条件が \gset の結果や関数呼び出しに依存していても、満了後は必ず抜けるという単調性を保証したいから。Assert(command->jump_target >= 0) は、Command が pg_malloc0 されるためリンク漏れが「0 番コマンドへのジャンプ」という有効な値に化けるのを防ぐ守り。

条件の評価と真偽判定は \if とまったく同じ evaluateExpr() + valueTruth() で、0 と SQL NULL が偽。評価エラー時は \if と同じく commandFailed() + CSTATE_ABORTED (呼び出し側が ESTATUS_META_COMMAND_ERROR を立てる)。\endwhile 側にはタイマーチェックがないことに注意。無条件に \while へ戻し、判断はその \while に一元化している。

このブロックは、直前にある -r 用の addToSimpleStats() の後、既存の st->command++ の手前に置かれている。順序が肝で、統計は必ず「今実行し終えたコマンド」に付いてからジャンプが起きる。backward の判定は pending_jump <= st->command という位置比較だけで、\endwhile かどうかは見ない (\while の偽ジャンプは必ず前方なので同じ式で足りる)。後方ジャンプで return するのがスレッド飢餓対策。

スタック最上位が \if フレームだった場合、下に \while フレームが開いているか (openBlockOfKind) でメッセージを出し分ける。開いていれば「その \if の枝をまたいでいる」という具体的な指摘、なければ従来どおりの素の "without matching"。相互リンクは \while → \endwhile の次 (i + 1)、\endwhile → \while の位置。i + 1 がスクリプト末尾の NULL スロットになるケース (ループがスクリプトの最後) も、CSTATE_START_COMMAND が commands[st->command] == NULL を見て CSTATE_END_TX に移るので正しく動く。

注意落とし穴

  • 後方ジャンプで return しないとスレッドが飢える (このパッチのレビューで見つかった欠陥)

    advanceConnectionState() の for(;;) から抜ける (return する) のは、結果待ちの CSTATE_WAIT_RESULT / CSTATE_WAIT_ROLLBACK_RESULT、待機中の CSTATE_SLEEP / CSTATE_THROTTLE、次のトランザクションへ移る CSTATE_END_TX、終端の CSTATE_ABORTED / CSTATE_FINISHED だけ。メタコマンドだけのループはそのどれにも到達しないので、return を入れないと 1 クライアントがスレッドを占有し、同じスレッドに割り当てられた他のクライアントが一度も進まない。pgbench -T 1 -c 2 -j 1 で processed が 2 でなく 1 になる。修正が backward 判定つきの return。なお終了はする (\while が timer_exceeded を見るので) ため、症状は「ハング」ではなく「他のクライアントが動かない」という見えにくい形になる。この return にコストはなく、threadRun() は CSTATE_START_COMMAND のクライアントを見つけると min_usec = 0 にして待たずに次のラウンドに入る。

  • jump_target は明示的に -1 で初期化する必要がある

    Command は create_sql_command() でも process_backslash_command() でも pg_malloc0 されるので、初期化を忘れると jump_target は 0、つまり「スクリプトの先頭コマンド」という完全に有効なインデックスになる。リンク漏れがクラッシュではなく静かな暴走 (毎回スクリプト先頭に戻る) になってしまうため、両方の生成箇所で -1 を代入し、実行時の 2 か所で Assert(command->jump_target >= 0) している。

  • -T で打ち切られた最後のトランザクションは「不完全なのに成功として計上される」

    タイマー満了後もスクリプト末尾は普通に走るので、ループが本来の回数を回りきっていないのに COMMIT され、成功トランザクションとして数えられる。クライアントごとに最大 1 回起きる境界アーティファクト。データ不変条件がループの完走に依存するワークロード (TPC-C の o_ol_cnt と実際の order_line 行数など) はこの 1 トランザクションで壊れる。ドキュメントの caution は「ループ由来の値はループの後で書く」(例では UPDATE orders SET o_ol_cnt = :i - 1 をループの後に置く) か、-T ではなく -t を使うことを求めている。逆に -t にはタイマーがないので、終わらないループは単なるスクリプトのバグでクライアントは永久に回り続ける。

  • リトライでクライアント変数は復元されない

    CSTATE_RETRY が戻すのは乱数状態 (st->cs_func_rs = st->random_state) と st->command = 0 だけで、CState に変数のスナップショットは存在しない。したがってリトライ後のループ回数が一致するのは決定的リプレイが成り立つとき、つまり条件が読む変数をすべてスクリプト内でループより前に \set しているときだけ。\if の分岐ズレは「一度違う枝を通る」で有界だが、ループでは書き換わったカウンタが等値の終了条件をまたいで、以前は終了していたループが終了しなくなりうるという点で症状の質が異なる。pgbench.sgml の既存の「変数もトランザクション前の状態に戻る」という記述はここでは繰り返さず、\while の項と failures-and-retries の項の両方に注意書きを足している。

  • CSTATE_SKIP_COMMAND は \while / \endwhile を素通りする

    スキップループが特別扱いするのは META_IF/ELIF/ELSE/ENDIF だけで、\while と \endwhile は else 側の st->command++ に落ちてジャンプしない。これが安全なのはパース時の包含規則のおかげ。危険な逆ケース、つまり「実行中の反復の \endwhile がスキップ領域に入っていて黙って反復が殺される」は、\if/\endif の対がループボディに完全に含まれるかループを完全に含むかのどちらかでしかありえないので起こらない。単一スタックによる静的検査は、ジャンプ機構だけでなくこのスキップ経路の正しさも支えている。

  • エラーメッセージの出し分けと prepareCommandsInPipeline の過剰準備

    \while 1 \endif \endwhile は「\while ボディの中の \if にマッチしない」ではなく素の "\endif without matching \if" になる (下に \if フレームが開いていないため)。002 のテストが $ アンカーでこれを固定している。もう 1 点、prepareCommandsInPipeline() は \startpipeline の次から最初の \endpipeline まで前方走査するので、パイプラインがループ境界をまたぐと \endwhile を越えて、その反復では到達しないコマンドまで prepare する。準備は st->prepared[use_file][command_num] で冪等なので無害であり、修正ではなくコメントを足すだけにしてある。

問題何が足りなかったか

pgbench が出すレイテンシ指標は平均と標準偏差だけで、テール (裾) の挙動をほとんど表さない。一方 TPC-C の応答時間基準はトランザクション種別ごとの 90 パーセンタイルで定義されており、平均が基準を満たしていても p90 が超過している状況を pgbench 単体では検出できない。従来の唯一の手段は -l のトランザクションログを外部ツールでソートして手計算することだった。latency stddev を入れたのは commit 2d6c0f10ef4 "pgbench: Elaborate latency reporting." (Author: Fabien COELHO、コミッタが Noah Misch) で、そこでも平均と標準偏差だけではテールを表せないという限界は残ったままだった。

パッチ前はオプションそのものが存在しない。

最終レポートに出るのは実行時間から割り算した latency average = 1.234 ms の 1 行だけで (latency stddev は --progress / --rate / --latency-limit のいずれかでレイテンシを実測したときにしか出ない)、p90 を知るには -l でログを出して sort に流す自前の後処理が要る。

設計採った道と捨てた道

採用オプション指定時は processXactStats() の detailed 述語に num_latency_percentiles > 0 を足し、レイテンシを実測させる。同時に printResults() の平均表示の分岐にも同じ条件を足す。

detailed が偽のとき processXactStats は latency = 0.0 のまま accumStats を呼ぶ。ヒストグラム更新を accumStats に置くだけでは、成功トランザクションすべてがバケット 0 に入り、その中点 0.5 us が p90 = 0.001 ms として平然と出力される。表示側も同様で、条件を足さないと実測ヒストグラムから求めた p50 の隣に、実行時間から割り算しただけの latency average (total_duration * nclients / total_cnt、接続オーバーヘッドや idle を含む) が並び、同じレポート内で系統的に食い違う数値になる。両方を直した結果、このオプションだけを付けた実行でも latency stddev 行が新たに出るようになる (出力仕様の変更であり、TAP で固定した)。

見送り「ヒストグラムは常に累積する」案。将来 -P でパーセンタイルを出すのに便利という利点はあるが、測定純度の問題 (計測用の追加処理そのものが計測を歪める) への最も強い回答は「オプション未指定ならトランザクションあたりの追加命令はゼロ」であり、常時累積は既定の実行でも detailed 経路を強制して pg_time_now の呼び出し回数まで変えてしまう。

採用ヒストグラムは固定長の int64[1537] を StatsData に直接埋め込む。

StatsData のインスタンスは TState.stats、静的配列 sql_script[128].stats、threadRun のローカル aggs/last、printProgressReport のローカル cur、main のローカル stats と各所にあり、埋め込みなら確保もライフサイクル管理も不要で、構造体コピーが自動的にディープコピーになる。コストは initStats の 12,296 バイト memset (最悪でも集約インターバルごと、進捗レポートごと) と、sql_script[128] 分の約 1.57 MB (12,296 x 128 = 1,573,888 バイト) の BSS (未使用エントリのページはフォルトしない) だけで、トランザクション単位の経路には何も足さない。

見送りポインタ + 遅延 alloc 案。StatsData は last = aggs (threadRun) と *last = cur (printProgressReport) で丸ごとコピーされるため、ポインタメンバだと 2 つの StatsData が同じヒストグラムを指すエイリアスになる。その状態で doLog の initStats(agg, next) が走ると、他方がまだ保持しているヒストグラムをゼロクリアしてしまう。

採用スクリプト別ヒストグラムは既存の per-script 統計と同じく無同期のまま更新し、パーセンタイルの順位はヒストグラム自身のバケット合計 (latencyHistTotal) から計算する。

per-script 統計には既に「XXX could use a mutex here, but we choose not to」というコメント付きの競合がある。64 ビット環境ではアラインされた int64 のインクリメントが破れることはなく、競合の影響は 1 衝突あたり 1 サンプルの更新喪失に限られる。ただし喪失があると バケット合計 < sstats->cnt になるので、cnt から順位を出すと累積が rank に届かないままループが終わり、idx はあふれバケット 1536 ではなく配列の外側 1537 になる。この idx はあふれ判定 (idx == LATENCY_HIST_NBUCKETS - 1) に一致しないため、範囲外の中点計算がそのまま走り「549453.824 ms」という存在しない値を出しかねない。読み出しは全スレッド join 後の printResults だけなので、読み取り時に値が破れることはない。

見送りスレッド × スクリプトごとに正しくヒストグラムを持つ案。nthreads * num_scripts * 12.3 KB (最悪 128x128 で約 200 MB) に加え、TState の配列と join 後のマージループ、accumStats の契約変更が必要になる。コミュニティが明示的に受け入れている既存の競合を、診断用の集計値のためだけに直すことになり、それは別パッチの仕事。

採用SUBBITS=6, MAXBITS=29。累乗レンジごとに 64 個の線形サブバケット、レンジは [0, 2^29) us = 536.871 s、末尾 1 個をあふれ用にして計 1537 バケット。

64 分割なら 64 us 超での相対誤差は最悪 2^-6 = 1.6% で、p90/p95/p99 を 3 桁で報告するには十分。64 us 未満は幅 1 us の線形群になり、そこでは誤差が絶対値で 1 us 未満に収まる。レンジが 300 s を超えている必要があるのは、latency = now - txn_scheduled がスケジュール遅延を含むためで、--rate が詰まった実行では「レイテンシ」が実行時間そのものに近づいて分単位になるのが普通だから。

見送りMAXBITS=28 案 (元スペックの記述)。2^28 us = 268.435 s は 300 s に届かず、上のスケジュール遅延で日常的にあふれる。元スペックのバケット数 (28-6+1)*64 + 64 も、線形群が最初の群そのものであることを見落として二重計上していた。

仕組みコードを読む

このパッチで足したのは detailed 述語の末尾 num_latency_percentiles > 0 だけだが、ここが機能全体の土台になっている。detailed が偽だと latency は 0.0 のまま、しかも accumStats は無条件に呼ばれる (最後の行)。つまり述語に足さなければ、ヒストグラムには毎回 0.0 が入り、パーセンタイル行はエラーも警告もなく p50 = 0.000 ms を出す。逆に足したことで、--progress も --rate も付けない実行でも pg_time_now_lazy が呼ばれ、latency = now - txn_scheduled が計測される。この latency はスケジュール遅延 (txn_scheduled から実際に始まるまでの待ち) を含む値であり、ヒストグラムのレンジ設計に直結する。

累積点は既存の latency SimpleStats の真横 1 か所だけ。ゲート条件が既存の latency 計上と完全に同じ (成功かつ非スキップ) になるので、パーセンタイルの母集団と latency average の母集団が必ず一致する。オプション未指定時は num_latency_percentiles == 0 なので、トランザクションあたりの追加コストはグローバル変数の比較 1 回だけ。指定時でもロック・アロケーション・システムコールはなく、pg_leftmost_one_pos64 とシフト・マスク、そして配列インクリメント 1 回で済む (thread->stats はスレッド専有だが、sql_script[].stats は他の per-script 統計と同じく共有かつ無同期)。accumStats は渡された StatsData 全部 (thread->stats、per-script、doLog の agg) に対して同じことをするので、-l --aggregate-interval のときは報告されない agg のヒストグラムも更新される (統一性のために許容した無駄)。

us 単位の値を 1537 個のバケットに写す。v < 64 の枝は幅 1 us の線形群 (群 g=0) を返すと同時に、pg_leftmost_one_pos64 が Assert(word != 0) を持つことへのガードでもある。サブミリ秒どころかサブマイクロ秒のトランザクション (メタコマンドだけのスクリプトなど) は (int64) キャストで 0 に落ちるので、この枝がなければ assert 失敗する。64 以上では k = 最上位ビット位置から群番号 g = k-5 を作り、最上位ビットのすぐ下の 6 ビット ((v >> (k-6)) & 63) を副番号にする。境界の連続性: v=63 -> 63、v=64 (k=6) -> (1<<6)|0 = 64、v=127 -> 127、v=128 (k=7) -> (2<<6)|0 = 128、v=2^29-1 (k=28) -> (23<<6)|63 = 1535 が最後の通常バケット、v=2^29 で k=29 となりインデックス 1536 のあふれバケットに落ちる。

nearest-rank 定義: 順位 rank = ceil(p * total / 100) を求め、先頭から累積して cum >= rank になった最初のバケットを答えにする。total は関数冒頭の latencyHistTotal(histogram)、つまりバケットの実合計であって SimpleStats の cnt ではない (per-script の無同期更新で cnt のほうが大きくなりうる)。1e-9 * exact を引くのは、10 進で表現できないパーセンタイルへの保険。例えば p=99.9 で total=41000 のとき 99.9 * 41000.0 / 100.0 は 40959.00000000001 になり、素直に ceil すると 40960 と 1 サンプル分ずれる。値の表示はバケット中点 (latencyHistBucketMidpoint) で、あふれバケットに当たったときだけ "> 536870.912 ms" と出す。

上の分岐が「実測レイテンシを出すか、実行時間から割り算した平均を出すか」の選択。ここに num_latency_percentiles > 0 を足さないと、実測ヒストグラムから出した p50 の隣に、接続オーバーヘッドや idle を含む導出値の平均が並ぶ。足した結果、printSimpleStats が latency average と latency stddev の 2 行を出すようになり、--latency-percentiles だけを付けた実行でも stddev 行が現れる。下のブロックは総数 0 の扱いで、printLatencyPercentiles 自体は空ヒストグラムなら何も出さない (per-script 行が黙って消えるのはこの仕様) ため、グローバル側だけ明示的に "(no successful transactions)" を出して行の消失を防いでいる。

注意落とし穴

  • detailed 述語に足し忘れると、無言で p50 = 0.001 ms を出す

    レビューで最初に見つかった重大欠陥。processXactStats は latency = 0.0 で始まり、detailed が偽でも accumStats を呼ぶ。したがって accumStats にヒストグラム更新を置いただけでは、成功トランザクション全部がバケット 0 に積まれる。失敗モードが「行が出ない」ではなく「もっともらしい 0.001 ms (バケット 0 の中点 0.5 us) が出る」ことが厄介で、TAP で latency stddev 行 (実測しないと出ない行) を同時に検査することでこの結合を固定している。

  • pg_leftmost_one_pos64 はゼロに対して未定義

    pg_bitutils.h の pg_leftmost_one_pos64 は Assert(word != 0) を持つ。latencyHistBucket の v < 64 の線形枝は「最初の群を線形にする」ためだけでなく、この assert のガードでもある。サブマイクロ秒のトランザクション (メタコマンドだけのスクリプトなど) は (int64) キャストで 0 になるので現実に起こる。最適化のつもりで枝の順序を入れ替えると assert 版ビルドで落ちる。

  • 順位は必ずヒストグラムのバケット合計から求める

    cnt から rank を出すと累積が rank に届かないままループが終わり、抜けたときの idx は 1536 (あふれ) ではなく 1537 (配列の外) になる。あふれ判定 idx == LATENCY_HIST_NBUCKETS - 1 に一致しないので "> 536870.912 ms" ですらなく、範囲外バケットの中点から計算した "549453.824 ms" という嘘の値が出る。

  • レンジは 300 s ではなく 536.871 s まで必要

    latency = now - txn_scheduled にはスケジュール遅延が含まれる。--rate が詰まった実行では予定時刻からの遅れが実行時間全体に向かって伸びるため、分単位の「レイテンシ」が日常的に出る。2^28 us = 268.435 s ではこれを取りこぼす。MAXBITS=29 で [0, 536.871 s) をカバーし、バケット数は (29-6+1)*64 + 1 = 1537 (線形群は最初の群そのものなので別枠で足さない)。

  • 進捗レポートのマージにはヒストグラムを混ぜてはいけない

    mergeSimpleStats の呼び出し箇所は 2 つある。main() の join 後のループ (ここに mergeLatencyHistogram を足した。スレッド 0 は threadRun を同期的に実行して戻っているので全スレッドをカバーする) と、printProgressReport 内のループ。後者はスレッド 0 が他スレッドの走行中に呼ぶもので、コード中に競合が明記されている。v1 ではここでヒストグラムを読まないと決めた結果、-P の出力は一切変わらない。

  • 浮動小数の丸めで 1 サンプルずれる

    rank = ceil(p * total / 100.0) を素直に計算すると、10 進で表現できない p で 1 つ上のサンプルに着地することがある。実例: p=99.9, total=41000 で式の値は 40959.00000000001。相対許容 1e-9 * exact を引いてから ceil する。バケット幅が最悪 1.6% なので、この程度の許容がパーセンタイル値そのものを歪めることはない。

  • p は 0 < p < 100 の開区間、順序は保持、重複も可

    p=100 を弾くのは、最大値がせいぜい最上位の通常バケット (幅 2^22 us = 4.19 s) か、上限のないあふれバケット (表示は "> 536870.912 ms") に落ちる粗い近似にしかならないため (printSimpleStats も max を出さない)。出力はユーザーが書いた順のままなので、p50 <= p95 を検査したければ引数もソートして渡す必要がある。pgbench は setlocale を呼ばないので strtod は常に C ロケールで走り、小数点は必ず '.'、',' は曖昧さなくリスト区切りになる。したがって "99,5" はエラーではなく {99, 5} という妥当な 2 要素リスト。

  • 空ヒストグラムのときの出力は 2 種類ある

問題何が足りなかったか

TPC-C をはじめとする定常状態ベンチマークの方法論では、計測区間の前の立ち上がり(バッファプールの充填、プラン・接続の暖機、autovacuum の落ち着き)を捨てることが前提になっている。しかし pgbench は常に時刻ゼロから数えるため、ユーザーは -l のトランザクションログを後段で切り出すか、-P の出力を目視して「このあたりから定常」と判断するしかなかった。sysbench の --warmup-time や BenchmarkSQL の rampupMins に相当する機能が pgbench には無く、-hackers にも提案履歴がない。結果として、同じサーバー・同じスクリプトでも実行時間の長短だけで tps が変わり、比較可能な数字にならない。

`pgbench -c 32 -j 8 -T 300 bench` の "tps = ..." には、shared_buffers が冷えている最初の数十秒が丸ごと入る。除外したければ -l を付けて後で awk で切るか、-P 10 の行を目視するしかない。パッチ前に `pgbench --warmup=60 -T 300 bench` と打つと、getopt_long が argv 要素をそのまま出すため `pgbench: unrecognized option '--warmup=60'` と `pgbench: hint: Try "pgbench --help" for more information.` を出して終了ステータス 1 で終わる。

設計採った道と捨てた道

採用-T に対して加算方式 (総実行時間 = warmup + T) とし、-t との併用は起動時に fatal エラーにする。setalarm(duration + warmup)、end_time += warmup*1e6、printResults に渡す時間から warmup*1e6 を引く、という三点で実装する。

-T が「計測区間」を意味するままになり、sysbench の --warmup-time と同じ挙動になる。--warmup を -T なしで指定した場合は DEFAULT_NXACTS により暗黙の -t 10 になってしまうので、duration <= 0 を fatal ("--warmup requires -T/--time") にして -t 併用と -T 忘れをまとめて弾く。

見送り減算方式 (-T にウォームアップを含め、計測は T - warmup) は、-T が実行時間と計測時間の二重の意味を持ち、warmup >= T のときの挙動も定義が要るので却下。-t との併用も却下: 終了判定は st->cnt (CSTATE_END_TX の `st->cnt >= nxacts`) が駆動し、この st->cnt はウォームアップ中のトランザクションも数える。計測分だけ数えるよう st->cnt をゲートすると終了ロジックそのものが壊れるため、-t 併用は定義不能。

採用破棄バケットは単なるカウンタではなく完全な StatsData (thread->warmup_stats) にし、統計のマージ処理を mergeStats() として切り出して printProgressReport と最終集約の両方で使う。

printProgressReport() は threads[i].stats の latency/lag の和と cnt から区間 tps と平均レイテンシを出す。ウォームアップ中の統計を迂回させると、そのままでは -P の行が 0 tps / 0 ms になる。バケットを StatsData にしておけば進捗表示側で measured + warmup の両方を mergeStats() で足すだけで済み、-P は時刻ゼロから正しいライブ表示のままになる。accumStats() もそのまま再利用でき、--latency-percentiles 用の latency_histogram も StatsData の中にあるので自動的に除外対象になる。

見送り「破棄件数を数える int64 カウンタだけ持つ」案は却下。カウンタでは -P が必要とする latency.sum / sum2 / lag.sum を復元できず、ウォームアップ中の進捗行が 0 tps・0 ms になる (「-P は影響を受けない」という当初のスペック記述はこの方式では成立しない)。

採用境界時刻 warmup_until はスレッドごとに持ち、threadRun() の GO バリア直後に thread->bench_start + warmup*1e6 として設定する。共有変数も追加バリアも導入しない。

bench_start はバリア解放直後に各スレッドが自分で取る値で、!is_connect なら初期接続完了後、-C なら各トランザクションの接続の前という、ウォームアップの起点として意味のある時点になる。スレッド間のズレはバリア解放のジッタ (サブミリ秒) にすぎず、既存の -T が全スレッド共通の setalarm を(それよりさらに前の時点で)使っているのと同程度の許容誤差。

見送り「共有の bench start から導いた一つの絶対時刻 warmup_end を全スレッドで使う」案は実装不能なので却下。実行中に共有の bench start は存在せず、main のローカル bench_start は全スレッドを join した後に各 thread->bench_start の最小値として計算されるものだから、走行中に参照できる値ではない。

採用ゲートは processXactStats の一点ではなく、統計が積まれる全サイトに個別に入れる: thread->stats の accumStats、latency_late++、スクリプト別 accumStats、そして CSTATE_END_COMMAND の command->stats、CSTATE_RETRY の command->retries++、CSTATE_FAILURE の command->failures++。

統計の書き込み口を grep で列挙した結果、-r の per-command 統計だけは processXactStats の外、advanceConnectionState() の状態機械アームの中にあった。advanceConnectionState は thread ポインタを持っているので、同じ warmupActive(thread, &now) をそこでも呼べる。

見送り「processXactStats を一箇所ゲートすれば -r の統計まで含めて全部覆える」という当初の設計は誤りなので却下。CSTATE_END_COMMAND の addToSimpleStats は完全に別サイトで、そこを漏らすと -r のレイテンシ列だけが計測区間、失敗数とリトライ数は全期間、という内部不整合なレポートになる。

仕組みコードを読む

ゲートの本体。第一行の `warmup == 0` で、オプション未指定時は完全にゼロコスト(時計も読まない)。warmup_done が立った後も即 false を返すので、ウォームアップ終了後に毎トランザクション余分な時計読みをすることはない。逆に言うと、ウォームアップ中は pg_time_now_lazy() を自分で呼んで *now を必ず埋める。これは processXactStats の既存の時刻取得が `detailed` 条件の下にしかなく、素の `-T N --warmup=M` では now が 0 のままになってしまうため。ラッチが外れる瞬間 (最初に false を返す呼び出し) に thread->conn_duration をスナップショットして warmup_conn_duration に取り、-C の平均接続時間からウォームアップ分を引けるようにしている。

in_warmup は関数冒頭で `bool in_warmup = warmupActive(thread, now);` として一度だけ評価され、以降の判定はすべてこの値を使う(同一トランザクションの中でゲートが揺れないため)。accumStats の宛先を差し替えるだけなので、成功件数・skipped・retries/retried・失敗種別・latency/lag の SimpleStats・レイテンシヒストグラムがまとめて破棄バケットへ行く。--latency-limit の latency_late も同じ else 側に入っている。このブロックの直後にある `st->cnt++;` と `doLog(...)` は意図的にゲートしていない: 前者はクライアントの終了判定を駆動し、後者はログの完全性 (--aggregate-interval の集計は doLog の内部で行われる) のため。関数末尾のスクリプト別統計は `if (per_script_stats && !in_warmup)` という形でゲートされている。

-r (--report-per-command) の文別レイテンシは processXactStats ではなくこの状態機械アームで積まれる。ここを見落とすと、-r の出力だけがウォームアップを含んだままになる。判定は文の記録時刻で行われるので、境界をまたぐトランザクションでは、境界より前に終わった文は破棄側、後に終わった文は計測側に分かれる(トランザクション全体のレイテンシは計測側に丸ごと入る)。同じ理由で CSTATE_RETRY の `command->retries++` と CSTATE_FAILURE の `command->failures++` にも同じ `if (!warmupActive(thread, &now))` が入っている。

-P の進捗行は「今どれくらい出ているか」のライブ表示なので、ウォームアップ中もゼロにしてはいけない。ここで両バケットを足すことで、進捗行は時刻ゼロから連続した正しい値になる。マーカー行は出さない方針なので、-P だけを見ているとウォームアップが終わった瞬間は分からない(区別が必要なら最終レポートの warmup 行を見る)。元のコードは threads[i].stats のフィールドを一つずつ足していたが、同じ足し算が二箇所と最終集約で必要になったので mergeStats() に括り出されている。

tps の分母。printResults は `tps = total->cnt / PG_TIME_GET_DOUBLE(total_duration)` を計算するので、分子 (計測区間の件数) と辻褄を合わせるには経過時間から warmup 秒を引く必要がある。クランプは中断時の保険: Ctrl-C や接続失敗でウォームアップが終わる前に走行が終わると引き算が負になり、tps が負値やレイテンシ平均が異常値になる。1 マイクロ秒に丸めれば「異常に大きい tps」として見えるだけで済む。conn_total_duration の方も、各スレッドで `thread->conn_duration - thread->warmup_conn_duration` として集約されている。

注意落とし穴

  • -r の統計は processXactStats の外にあり、失敗数とリトライ数はさらに別サイト

    レビューで見つかった実際の欠陥。当初は「processXactStats をゲートすれば -r も覆える」と考えていたが、per-command のレイテンシは CSTATE_END_COMMAND、リトライ数は CSTATE_RETRY の command->retries++、失敗数は CSTATE_FAILURE の command->failures++ と、三つの独立した書き込み口がある。レイテンシだけゲートすると、-r の出力で「レイテンシ列は計測区間だけ、failures/retries 列は全期間」という内部不整合なレポートが出る。修正は三箇所すべてに同じ warmupActive() ガードを入れること。

  • -C の平均接続時間は分子と分母を揃える必要がある

    printResults は `average connection time = 0.001 * conn_total_duration / (total->cnt + failures)` (usec を ms に直した値) を出す。分母は計測区間の件数だけになったので、分子もウォームアップ中に費やした接続時間を引かないと平均が水増しされる (ウォームアップが長いほど大きく外れる)。そのため warmupActive() がラッチを外す瞬間に thread->conn_duration をスナップショットして warmup_conn_duration に保存し、main の集約で差し引いている。逆に、あるスレッドが走行中に一度も統計記録点に到達しなかった場合はラッチが外れず warmup_conn_duration が 0 のまま残る (極端に長いトランザクション一本だけ、といったケース)。

  • ゲート用の時計読みは自前で行う必要がある

    processXactStats の既存の `pg_time_now_lazy(now)` は `detailed = progress || throttle_delay || latency_limit || use_log || per_script_stats || num_latency_percentiles > 0` の下にしかない。素の `pgbench -T 10 --warmup=5 -n` ではこれが全部 false なので *now は 0 のまま、`0 < warmup_until` が常に真になって全トランザクションが破棄され、レポートが空になる。だから warmupActive() が自分で pg_time_now_lazy() を呼ぶ。そのままだと恒久的に余分な時計読みが増えるので、warmup_done フラグでラッチして終了後は最初の条件式だけで返る。

  • 中断走行での負の duration

    `total_duration = pg_time_now() - bench_start - warmup*1e6` は、ウォームアップ完了前に走行が中断されると負になる。そのまま printResults に渡すと tps が負値、`latency average = 0.001 * total_duration * nclients / total_cnt` も負になる。`if (total_duration < 1) total_duration = 1;` のクランプが必要。関連して、setalarm(duration + warmup) と end_time の計算で int が溢れないよう、起動時に `warmup > INT_MAX - duration` を fatal にしている。

  • -P / -l と最終レポートの数字は意図的に食い違う

    -P は両バケットをマージするので時刻ゼロからの値、-l と --aggregate-interval の行はタイムスタンプ付きで後から切れるためゲートせず全期間を覆う。一方で最終レポートは計測区間のみ。したがって「-P の行を平均した値」と「最終行の tps」は --warmup ありでは一致しない。これは仕様であり、破棄した件数は `warmup: 60 s (12345 transactions discarded)` の行で確認できる (失敗があれば `, including N failed` が付く)。

  • 境界判定は記録時刻ベース (record-time gating)

    「開始時刻がウォームアップ中かどうか」ではなく「統計を記録しようとした時刻がウォームアップ中かどうか」で判定する。したがって境界をまたぐトランザクションは丸ごと計測区間に算入される。トランザクション開始時刻でのゲートはトランザクションごとの追加簿記が必要で、しかも -T による打ち切りが既に記録時刻ベース (最後のトランザクションは -T を超えてもコミットまで走る) なのと不整合になる。なお -r の文別統計には同じ規則が文単位で適用されるため、またぐトランザクションの前半の文は破棄側に落ちる。

  • warmup_until はスレッドごと、GO バリアの直後

    走行中に共有の bench start は存在しない (main のローカル bench_start は join 後に各 thread->bench_start の最小値として計算される後付けの値)。よって warmup_until は threadRun() で `start + warmup*1e6` として各スレッドが自分で計算する。スレッド間のズレはバリア解放のジッタ分だけで、setalarm がさらに前の時点で仕掛けられている既存の -T と同程度の許容誤差。TState の初期化側 (main) では warmup_until = 0 を置くだけで、実値はバリア後に埋まる。

検証テストが固定していること

  • 走行が warmup + duration 続き、レポートに warmup 行が出て、実際に非ゼロ件数が破棄されていること (001_pgbench_with_server.pl の 'pgbench warmup')

    `-T 1 --warmup=1 -n -r` を `\sleep 200 ms` だけのスクリプトで走らせ、出力に `duration: 1 s`、`warmup: 1 s \([1-9]\d* transactions discarded\)`、`processed: \d+\b`、`statement latencies in milliseconds` を要求する。スクリプトを sleep にしているのは、マシン速度によらずウォームアップ区間と計測区間の双方にトランザクションが入るようにするため。破棄件数を [1-9]\d* (非ゼロ) にしてあるので、統計の迂回をやめる退行はここで落ちる。stderr は空 (qr{^$}) を要求。

  • --latency-percentiles との組み合わせで、パーセンタイルが計測区間のデータから計算されていること (001_pgbench_with_server.pl の 'pgbench warmup with latency percentiles')

    `-T 2 --warmup=1 -n --latency-percentiles=50` を `\sleep 200 ms` スクリプトで走らせ、warmup 行に加えて `latency percentiles: p50 = \d+\.\d+ ms` を要求する。ヒストグラムは StatsData の一部なので破棄バケット側へ一緒に迂回する。もし計測区間のトランザクションまで破棄していれば、printResults はここで `latency percentiles: (no successful transactions)` を出すためテストが落ちる。

  • オプション引数の検証 (002_pgbench_no_server.pl の 'zero warmup' / 'negative warmup' / 'not a warmup')

    `--warmup=0 -T 10` と `--warmup=-1 -T 10` に対して `--warmup must be in range 1\.\.` を、`--warmup=fast -T 10` に対して `invalid value "fast" for option --warmup` を要求する。これは option_parse_int(optarg, "--warmup", 1, INT_MAX, &warmup) の下限が 1 であることを固定している。

  • -T との依存関係 (002_pgbench_no_server.pl の 'warmup with -t' / 'warmup without -T')

    `--warmup=5 -t 100` と `--warmup=5` (単独) の双方が `--warmup requires -T/--time` で落ちることを確認する。後者が重要で、-T も -t も無い場合は DEFAULT_NXACTS により暗黙の -t 10 になるため、duration <= 0 のチェックがこのケースも捕まえていることを固定している。

getQueryParams() は getVariable() の戻り値をそのまま libpq に渡すだけで、getVariable() は PGBT_NULL を "NULL" という文字列にレンダリングして svalue にキャッシュする。よってパラメータは4文字の文字列になる (TAP テストが t = 'NULL' で固定している)。選択肢 D が最も誘惑的だが、それは simple モードの挙動 — simple では変数が引用符なしの NULL として SQL テキストに埋め込まれるので、パーサが NULL リテラルとして解釈して本物の SQL NULL になる。パッチはこのモード差を意図的に据え置き、ドキュメントに書くだけにしている。

Q030001 \gset の NULL

このパッチ以前、SELECT NULL AS v \gset の直後に \set i debug(:v) を実行すると何が起きたか。

PQgetvalue が "" を返し、makeVariableValue() が slen==0 で false を返すため、executeMetaCommand() が commandFailed("evaluation of meta-command failed") → CSTATE_ABORTED → ESTATUS_META_COMMAND_ERROR に落ちる。canRetryError() が真になるのは serialization / deadlock だけ、canContinueOnError() が扱うのは ESTATUS_OTHER_SQL_ERROR だけなので、どちらのオプションでも救えない。選択肢 A が誘惑的だが、空文字列は式言語の値として不正なので debug に到達すらしない (makeVariableValue はメッセージすら出さないため、原因が NULL だと分かりにくいのが実害の大きさでもある)。

Q040001 \gset の NULL

setNullValue()+putVariableValue() の代わりに putVariable(&st->variables, ..., "NULL") と文字列を格納した場合、何が起きるか。

makeVariableValue() には pg_strcasecmp(svalue, "null") で null 値に変換する枝があるので、文字列 "NULL" を入れても式では null として動いてしまう。だから選択肢 B も選択肢 D も誤り。しかし putVariable() は svalue に文字列を入れ value.type を PGBT_NO_VALUE のままにするので、`\set v NULL` が作る svalue=NULL / PGBT_NULL とは別表現であり、遅延パースを1回挟む点も違う。選択肢 A が最も誘惑的だが、「観測される挙動がほぼ同じ」ことと「内部表現が同一」であることは別物で、パッチの目標は後者 (\set var NULL と等価) の達成にある。

Q050002 \sleep の式

なぜ「式をパースし終えてから残りの単語を単位として読む」実装にできなかったのか。

LALR パーサは式が続くのかを判断するために必ず 1 トークン先読みする。\set x 1 ms がキャレットを ms に立てて syntax error になるのがその実証で、\sleep でも同じことが起きるため「後から読む」余地がない。だから先頭にモード選択トークンを注入し、単位を文法の一部にした。選択肢 C (括弧案) が最も紛らわしいが、'(' expr ')' 自体が expr の production なので ')' の後もパーサは次のトークンを先読みする (( 1 ) + 1 が書ける以上そうなる)。選択肢 A は誤りで、flex の最長一致により "1ms" は INTEGER_CONST(1) と FUNCTION(ms) に分かれる。選択肢 B も誤りで、単位判定は pg_strcasecmp なので US も通る。

Q060002 \sleep の式

\sleep 1 + 1 ms は実際にどれだけ待つか。

文法アクションは make_op("*", <式全体>, <倍率>) で式木の根に掛け算ノードを被せる。テキスト上の位置ではなく構文木の根に対する操作なので、単位は常に式全体に掛かり (1 + 1) * 1000 = 2000us = 2 ミリ秒になる。選択肢 A は「ms が直前のトークンに付く」というテキスト的な直感からの誤りで、opt_unit は expr を還元し終えた後にしか現れないため、そのような結合は起こらない。

Q070002 \sleep の式

\sleep 0.4 s の挙動として正しいものはどれか。

倍率は式木に畳み込まれているので、実行時はまず 0.4 * 1000000 が評価され (片方が double なので結果も double の 400000.0)、その後に coerceToInt が rint する。つまり丸めはマイクロ秒換算の後に起きる。選択肢 B は「先に整数化してから単位を掛ける」という旧実装のイメージからの誤りで、この順序なら 0 になるが実装はそうなっていない。選択肢 C は誤りで、coerceToInt が拒否するのは NULL と boolean だけ。選択肢 D は旧実装の読み込み時エラーで、現在は式として正当に受理される。

Q080002 \sleep の式

\sleep 9223372036854775807 us を実行するとどうなるか。

us の倍率は 1 なので掛け算は溢れず、値はそのまま INT64_MAX として evaluateSleep から返る。危ないのは executeMetaCommand の now + usec で、ここは pg_add_s64_overflow で検出して PG_INT64_MAX に飽和させている。選択肢 D が最も紛らわしいが、それが起きるのは倍率が 1000000 になる \sleep 9223372036854775807 s の場合。選択肢 A は飽和させなかった場合の壊れ方 (旧実装が int の桁あふれで 2148 秒以上を無効化していたのと同種) で、このパッチが明示的に潰したもの。選択肢 B は 9223372036854775807 が int64 に収まるので誤り (収まらない 20 桁の定数なら読み込み時に落ちる)。

Q090003 \while ループ

なぜジャンプ先の代入を executeMetaCommand() の中で行わず、pending_jump を経由して CSTATE_END_COMMAND まで遅延させているのか。

CSTATE_END_COMMAND の処理順 (統計の加算 → st->command++) が理由のすべて。特に \endwhile の後方ジャンプは while の位置に置いてもその直後の ++ で while+1 になり、条件が一度も再評価されない無条件無限ループになる。紛らわしいのは選択肢 B で、executeMetaCommand() の直後の Assert は WAIT_RESULT / END_COMMAND / SLEEP / ABORTED しか許さず、仮に通してもコマンド単位統計を丸ごと飛ばすので採れない。jump_target はパース時に CheckScriptStructure() が静的に埋めるので選択肢 A も誤り。

Q100003 \while ループ

入れ子のループを実行中に -T の時間が満了した。何が起きるか。

timer_exceeded は実行中クリアされない単調な sig_atomic_t で、これを見るのは \while 1 か所。\endwhile は常に後方ジャンプするが、着地する \while が即座に抜けるので新しい反復は始まらない。選択肢 A が一番もっともらしいが、これは「そのループを 1 回だけ break する」という言い方に対応する反論であって、フラグを見る場所を \while に固定した実装には当てはまらない。選択肢 D は元の仕様案の候補だが、トランザクション途中で終了させる挙動は既存のどのタイマーチェックにもなく、processXactStats() を飛ばしつつ -r のデータ点だけが残るため却下された。

Q110003 \while ループ

CSTATE_END_COMMAND の後方ジャンプで return せずに break していたら、\while 1 / \set x 1 / \endwhile を pgbench -T 1 -c 2 -j 1 で実行するとどうなるか。

advanceConnectionState() の状態機械ループから return するのは WAIT_RESULT / WAIT_ROLLBACK_RESULT / SLEEP / THROTTLE / END_TX と終端の ABORTED / FINISHED だけで、メタコマンドだけのループはそのどれにも到達しない。だから 1 クライアントがスレッドを占有する。選択肢 A (無限ループになる) が引っかけで、\while 自身が timer_exceeded を見るのでプロセスはちゃんと終わる。症状はハングではなく「他のクライアントの結果が出ない」という見つけにくい形で、001 の processed: 2 を要求するテストがこれを固定している。なお return してもコストはなく、threadRun() は CSTATE_START_COMMAND のクライアントを見つけると min_usec = 0 にして待機せず次のラウンドに入る。

Q120003 \while ループ

\if false / \while 1 / SELECT 1/0; / \endwhile / \endif というスクリプトを実行すると何が起きるか。

CSTATE_SKIP_COMMAND のループが特別扱いするのは META_IF / ELIF / ELSE / ENDIF だけで、それ以外は else 側の st->command++ に落ちる。\while と \endwhile はここに含まれるので executeMetaCommand() 自体が呼ばれず、条件も評価されない。選択肢 D が引っかけで、スキップ中はメタコマンドが実行されないという原則を見落とすと引っかかる。逆に危険なのは「実行中の反復の \endwhile がスキップ領域に入ってしまう」ケースだが、\if/\endif の対がループボディに完全に含まれるかループを完全に含むかのどちらかであることを CheckScriptStructure() が保証しているので起こらない。

Q130004 パーセンタイル

accumStats() にヒストグラム更新を足しただけで、processXactStats() の detailed 述語に num_latency_percentiles > 0 を足し忘れた場合、--latency-percentiles=90 だけを付けた実行はどうなるか。

detailed が偽でも processXactStats は accumStats を無条件に呼ぶ。latency は 0.0 で初期化されているので、成功トランザクションは全部 latencyHistBucket(0.0) = 0 に積まれ、合計は 0 にならない。バケット 0 の中点は 0.5 us なので、printf("%.3f ms", 0.001 * 0.5) がもっともらしい p90 = 0.001 ms を警告なしに出す。選択肢 D が紛らわしいのは、その分岐が総数 0 のときにしか走らないから。ヒストグラムには 0.0 が「入っている」ので総数は正の値になり、この分岐には落ちない。この失敗モードが「行が出ない」ではなく「誤った数値が出る」ことが、レビューでこれを重大と判定した理由。

Q140004 パーセンタイル

ヒストグラムを StatsData にポインタで持たせ、必要になったときだけ確保する設計が退けられた理由は何か。

StatsData には丸ごとコピーする箇所が 2 つあり、ポインタメンバはそこでエイリアスになる。その後 doLog の initStats(agg, next) が走ると、もう一方がまだ参照しているヒストグラムをゼロクリアする。埋め込みならコピーが自動的にディープコピーになり、このバグの種類が消える。選択肢 D も一見もっともらしいが、間接参照 1 回は測定純度の議論の争点ではない (その議論の答えは「オプション未指定なら追加命令ゼロ」というゲート設計のほう) し、ポインタ案でもコストはほぼ同じ。

Q150004 パーセンタイル

スクリプト別のパーセンタイルで、順位を sstats->cnt から計算すると何が起きるか。

per-script 統計は無同期に更新され、同時インクリメントは更新を失う。失われるとバケット合計 < cnt になり、cnt から出した rank に累積が届かないままループが終わる。ループを抜けたときの idx は NBUCKETS (1537) であって NBUCKETS-1 ではないので、あふれ判定にも当たらず、範囲外バケットの中点 549453.824 ms がそのまま印字される (実際のコードは rank = Min(rank, latencyHistTotal(...)) で頭打ちにしているのでこの経路には入らない)。選択肢 B が紛らわしいのは、64 ビット環境ではアラインされた int64 の更新が破れないうえ、読み出しは全スレッドの join 後 (printResults) にしか起きないから。破れではなく更新喪失が本質。

Q160004 パーセンタイル

latencyHistBucket() で v < 64 の判定を pg_leftmost_one_pos64 の呼び出しより前に置くことが必須なのはなぜか。

この枝は幅 1 us の線形群を返すという役割と、pg_leftmost_one_pos64 のゼロ引数ガードという役割を兼ねている。メタコマンドだけのスクリプトなど、1 us 未満で終わるトランザクションは実在するので assert 版ビルドで確実に踏む。選択肢 D は誤りで、pg_leftmost_one_pos64 は最上位ビット位置 (v=1..63 なら k=0..5) を返し、常に 0 を返すわけではない。なお枝を外すと v=1..31 では群番号 k-5 が負になって配列外書き込みにもなるが、v=0 の assert 失敗のほうが先に問題になる。選択肢 B の速度は動機ではない (この枝がなくても正しく動くなら話は別だが、動かない)。

Q170005 ウォームアップ

--warmup の実装で、ウォームアップ中でもゲートしてはならない (常に実行しなければならない) のはどれか。

st->cnt はクライアントの終了判定 (CSTATE_END_TX の `st->cnt >= nxacts`) を駆動するので、ゲートすると -t 系の終了ロジックが壊れる。doLog は「ログはタイムスタンプ付きで完全に残し、後段で切ってもらう」という方針で非ゲートであり、--aggregate-interval の集計は doLog の内部で行われるので、これによって集計行も自動的に全期間を覆う。誘惑されやすい 選択肢 B は逆で、-r の per-command 統計は processXactStats の外の別の状態機械アームにあるため見落としやすいが、ここもゲート対象 (加えて CSTATE_RETRY の retries++ と CSTATE_FAILURE の failures++ も)。

Q180005 ウォームアップ

破棄バケットを単なる int64 カウンタではなく完全な StatsData にした理由として正しいものはどれか。

-P の行は独立した計測ではなく threads[i].stats の生の集計値から計算するので、統計を迂回させただけではウォームアップ中の進捗行が 0 になってしまう。バケットを StatsData にしておけば printProgressReport で measured + warmup を mergeStats() で足すだけで元の表示に戻せる。選択肢 A が誘惑的だが、warmup 行に出るのは件数 (と失敗があればその数) だけで、レイテンシ統計は表示しない。選択肢 C は無関係 (pgbench は単一バイナリで ABI の話は出てこない)、選択肢 D は doLog をゲートしていないので破棄トランザクションも通常フォーマットでログに残る。

Q190005 ウォームアップ

warmupActive() が自分で pg_time_now_lazy() を呼ばず、processXactStats の既存の `detailed` 条件下の時計読みに頼っていたとすると、`pgbench -T 10 --warmup=5 -n` (-P も -l も -R も -L も --latency-percentiles も無し) で何が起きるか。

detailed = progress || throttle_delay || latency_limit || use_log || per_script_stats || num_latency_percentiles > 0 であり、この起動オプションではすべて false になるので pg_time_now_lazy が一度も呼ばれず *now は 0 のまま。ゲートが常に真になり、thread->stats には何も入らないので「number of transactions actually processed: 0」になる。選択肢 C が誘惑的だが、レイテンシが 0 になるだけでなく件数そのものが破棄バケットへ行ってしまう点が本質。なお warmup_done ラッチにより、ウォームアップ終了後は追加の時計読みは発生しない。

Q200005 ウォームアップ

warmup_until の 50 ミリ秒前に開始し、20 ミリ秒後にコミットしたトランザクション (-r 指定あり) はどう扱われるか。

判定は記録時刻ベースで、processXactStats が呼ばれた時点では now >= warmup_until なので計測側に丸ごと入る。同じ規則が CSTATE_END_COMMAND では文単位に適用されるため、-r の統計だけは境界前後で分かれる。選択肢 C が誘惑的だが、開始時刻ゲートはトランザクションごとの追加簿記を要求する上、-T の打ち切り (最後のトランザクションは -T を超えてもコミットまで走る) が既に記録時刻ベースなのと不整合になるため採用していない。選択肢 B のような按分は行わない。選択肢 A は誤りで、doLog は非ゲートなのでログには必ず残る。

    ブランチ poc-pgbench-tpc-c、ベース e395fbd32a0。各パッチは SGML ドキュメントと TAP テストを含む。
