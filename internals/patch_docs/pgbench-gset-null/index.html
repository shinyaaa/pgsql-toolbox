pgbench \gset の SQL NULL 修正 精読ノート

postgres / src/bin/pgbench — patch 0001 (single commit)

pgbench の \gset と \aset が SQL NULL を空文字列として格納していたため、その変数を式で使った瞬間にクライアントが恒久停止していた。1 コミットの修正だが、直せる範囲と直さない範囲の線引きに判断が集中している。このノートはその線引きを、コミットと実機の挙動で裏づけて解き明かす。

このドキュメントの読み方

パッチは 1 本で、機能変更は readCommandResponse() の格納ループ 1 か所だけである。したがって読みどころは差分の量ではなく、なぜ null 値を入れるのが正しく、なぜ文字列 "NULL" を入れるのでは足りないのか、そしてなぜ空文字列と拡張プロトコルのバインドには手を出さないのかという 3 つの判断にある。 全編を通じて頭に置いておく土台が 2 つある。1 つは変数の二重表現で、Variable は文字列側の svalue と値側の value を持ち、value.type == PGBT_NO_VALUE のあいだは未変換を意味する。式で初めて使われたときに makeVariableValue() が svalue から value を作り、この変換が失敗するとメタコマンドが失敗する。もう 1 つはクライアント状態機械で、メタコマンドの失敗は advanceConnectionState() の中で executeMetaCommand() が CSTATE_ABORTED を返すことで決まり、SQL 側のエラーとは通る経路が違う。

0001/\gset の SQL NULL

\gset と \aset が SQL NULL を null 値として格納する

readCommandResponse() の格納ループは全列を無条件に PQgetvalue() で取り出していた。PQgetvalue() は SQL NULL に空文字列を返し、空文字列は pgbench の式言語では値として不正なので、その変数を初めて式で使ったところでクライアントが恒久停止していた。PQgetisnull() で判定し、NULL 列だけ setNullValue() と putVariableValue() で入れることで、\set varname NULL が作る表現と一致させる。空文字列と拡張プロトコルのパラメータバインドは意図的に触っていない。

問題何が足りなかったか

壊れ方は関数名でつながる一本の連鎖である。PQgetvalue() は SQL NULL に対して空文字列を返すので、格納ループは svalue = "" と value.type = PGBT_NO_VALUE の変数を作る。その変数を初めて式で使うと makeVariableValue() が呼ばれ、slen == 0 の枝でメッセージを何も出さずに false を返す。false は evaluateExpr() を経て executeMetaCommand() の META_SET 分岐に届き、commandFailed() でログを出したうえで CSTATE_ABORTED をそのまま返す。呼び出し元は st->estatus に ESTATUS_META_COMMAND_ERROR を記録するだけなので、救済の述語は一度も評価されない。長時間の負荷試験では、NULL を踏んだクライアントが 1 本ずつ静かに消えていき、残ったクライアントで測り続けた tps だけが報告される。

メッセージは command 1 の \set を指しており、NULL にも \gset にも触れていない。原因が前の行の格納にあることは出力からは読み取れない。2 つ目の実行は救済オプションを両方付けたもので、結果が 1 つ目と 1 行も違わない。パッチ後は同じスクリプトが debug(script=0,command=2): null を出して processed: 1/1 で終わる。

設計採った道と捨てた道

採用PQgetisnull() が真の列だけ setNullValue() で null 値を作り、putVariableValue() で格納する。非 NULL 列は従来どおり putVariable() に PQgetvalue() の結果を渡す。

putVariableValue() は svalue を free して NULL にし、value に渡された値をそのまま代入する。\set varname NULL も同じ putVariableValue() を通って PGBT_NULL の値を入れるので、\gset で作られる変数の内部表現が \set varname NULL の作るものと一致する。式言語側には PGBT_NULL、IS NULL、三値論理がすでに実装済みなので、表現をそろえるだけで追加の対応は要らない。

見送り文字列 "NULL" を putVariable() で入れる案。式の上は動いてしまう。makeVariableValue() には pg_strcasecmp(var->svalue, "null") == 0 の枝があり、そこで setNullValue() が呼ばれるからである。しかしこの案は SQL NULL とサーバが返した 4 文字のテキスト 'NULL' を区別できなくする。実機確認: SELECT 'NULL'::text AS s \gset に続けて \set i debug(:s) を実行すると debug(script=0,command=2): null が出る。つまり空文字列と NULL の混同を解消する代わりに、'NULL' と NULL の混同を持ち込むだけになる。

採用判定するセルを PQgetisnull(res, ntuples - 1, fld) にして、値を取り出す PQgetvalue(res, ntuples - 1, fld) と同じセルを指させる。

この格納ループは \gset と \aset で共有されている。\gset は ntuples != 1 を手前でエラーにするので ntuples - 1 は常に 0 だが、\aset は行数を制限せず最終行を採る仕様なので ntuples - 1 が 0 でない。判定と格納が同じセルを指していないと、変数に入った値と NULL 判定が別の行のものになる。

見送り行 0 を見る案。\gset では ntuples が 1 なので 0 と ntuples - 1 が一致し、\gset のテストは全部通ってしまう。壊れるのは \aset で複数行が返るときだけである。実機確認: PQgetisnull の行指定を 0 に変えてビルドすると、001_pgbench_with_server.pl のうち "pgbench aset command with NULL" の 4 アサーションだけが落ち、\gset 側は 1 件も落ちない。

採用空文字列の扱いは変えない。PQgetisnull() が偽なら従来どおり putVariable() を通るので、makeVariableValue() の slen == 0 で false を返す枝はそのまま残る。

サーバが返した空文字列を null 値にしてしまうと、このパッチが復元したばかりの「NULL と空文字列の区別」を再び潰すことになる。空文字列を式で使えるようにするかどうかは makeVariableValue() 側の設計問題で、\gset の格納とは独立している。

見送りslen == 0 も null 値として扱う案。1 行で書けるうえに再現手順のもう半分も直るので誘惑があるが、区別の復元という目的そのものを打ち消す。加えて \gset を経由しない \set v '' のような経路にも影響が及び、バグ修正のスコープを超える。

採用拡張および prepared モードのパラメータバインドは変えず、ドキュメントに制限として書くだけにする。

getQueryParams() は getVariable() の戻り値をそのまま libpq に渡し、getVariable() は value.type == PGBT_NULL を 4 文字の文字列 "NULL" にレンダリングする。したがって NULL 値の変数は文字列 'NULL' としてバインドされる。これは \set varname NULL の既存挙動そのもので、本修正が持ち込む退行ではない。実機確認: \set nv NULL と \gset 経由の NULL のどちらでも、-M prepared で TEXT 列に入れた結果は 4 文字の 'NULL' になる。

見送り同じパッチで本物の SQL null をバインドする案。getVariable() か getQueryParams() を変えることになるので \set varname NULL の既存挙動も同時に変わり、互換性の議論を呼ぶ。さらに未定義変数だけは getVariable() が NULL ポインタを返すため、すでに本物の SQL NULL がバインドされるという非対称がある。実機確認: 未定義変数を -M prepared で TEXT 列に INSERT すると、その行は v IS NULL が真になる。この非対称も一緒に整理しないと中途半端になるので、独立したパッチに分ける。

仕組みコードを読む

判定と格納が同じ (ntuples - 1, fld) を指していることがこの片の要点である。ループの手前で context を 1 つの const char * に束ねているので、NULL 側と非 NULL 側で同じ文字列が渡り、両方の結果を bool ok に集めて既存の「error storing into variable」分岐を共有できる。NULL 側で PgBenchValue をローカルに置いているのは、putVariableValue() が受け取った値を var->value に構造体コピーするからで、呼び出しが返った後にこのローカルが消えても問題ない。varname の psprintf と pfree はループ内に閉じているので、どちらの経路を通っても解放は 1 回である。

パッチ前に停止していたのは slen == 0 の枝である。コメントが「what should it do on ""?」で止まっているとおり、空文字列に何を割り当てるべきかが決まっていないまま false になる。ここで重要なのは冒頭の早期 return で、value.type != PGBT_NO_VALUE なら何もせず true を返す。putVariableValue() で入れた PGBT_NULL の変数はこの早期 return を素通りするので、パッチは slen == 0 の枝に一切近づかない。pg_strcasecmp(var->svalue, "null") の枝が存在することが、文字列 "NULL" を入れる案が「動いてしまう」理由でもある。

svalue を free して NULL にしたうえで value を代入する 3 行が、内部表現の一致を保証している。svalue が NULL になるので getVariable() は「文字列形式を持っていない」経路に入り、そこで PGBT_NULL を 4 文字の "NULL" にレンダリングする。この関数は \set varname NULL の実行時にも同じ形で呼ばれるため、\gset 由来の NULL 変数と \set 由来の NULL 変数は以降の全経路で区別が付かない。表現をそろえることが目的だったので、putVariable() で文字列を入れる案では svalue が残ってしまい目標を外す。

救済オプションが効かない理由がここにある。executeMetaCommand() は式評価の失敗時に CSTATE_ABORTED を返し、呼び出し元はそれを見てから st->estatus に理由を記録する。つまり状態はすでに確定しており、canRetryError() も canContinueOnError() もこの経路では一度も呼ばれない。estatus は報告と集計のために設定されるだけである。\gset 自体の行数エラーは readCommandResponse() が estatus を立てて CSTATE_WAIT_RESULT 側へ戻るので、そちらでは救済の述語が評価される。同じ ESTATUS_META_COMMAND_ERROR でも通る経路が違う。

述語が列挙している状態に ESTATUS_META_COMMAND_ERROR は含まれていない。したがって仮に前の片の dispatch が救済の述語を通る形だったとしても、結論は CSTATE_ABORTED のままである。この 2 つの述語を広げて救済する案を採らなかったのは、NULL の格納は誤りであって再試行や継続の対象ではないからである。同じ NULL を引き直しても結果は同じで、リトライは無限に失敗する。この 2 関数を引用したのは、パッチが「回復手段を足す」方向を選ばなかったことを読者が確認できるようにするためである。

注意落とし穴

  • 救済オプションが存在しない停止だった

    --max-tries も --continue-on-error も効かない。canRetryError() が真を返すのは ESTATUS_SERIALIZATION_ERROR と ESTATUS_DEADLOCK_ERROR だけ、canContinueOnError() が扱うのは ESTATUS_OTHER_SQL_ERROR だけである。さらに \set の式評価失敗の経路では、そもそもこの 2 つの述語が評価されない。実機確認: --max-tries=10 --continue-on-error を両方付けても出力は素の実行と 1 行も違わない。

  • 空文字列は直っていない

    サーバが返した空文字列を式で使うと、パッチ後も同じ理由で停止する。実機確認: SELECT ''::text AS es \gset に続けて \set i debug(:es) を実行すると、パッチ後のバイナリでも client 0 aborted in command 1 (set) と processed: 0/1 になる。これは makeVariableValue() の slen == 0 の枝が残っているためで、意図的にスコープ外にしてある。

  • 拡張と prepared モードでは 4 文字の文字列 'NULL' がバインドされる

    NULL 値の変数を SQL に埋めると、simple モードでは無引用の NULL がテキストとして展開されて SQL NULL になるが、拡張と prepared モードでは getVariable() がレンダリングした 4 文字の文字列がパラメータとして渡る。実機確認: -M prepared で TEXT 列に INSERT すると v = 'NULL' かつ length(v) = 4 になる。\set nv NULL でも同じ結果なので、これは本修正の退行ではない。

  • 未定義変数だけは本物の SQL NULL がバインドされる

    getVariable() は変数が見つからないと NULL ポインタを返し、それがそのまま libpq のパラメータになるので SQL NULL としてバインドされる。実機確認: 未定義変数を -M prepared で TEXT 列に INSERT すると、その行は v IS NULL が真になる。つまり「NULL 値の変数」と「存在しない変数」で結果が逆になるという非対称が残っている。別パッチの案件である。

  • テキスト補間の結果が黙って変わる互換性の穴

    パッチ前に NULL を捕まえてテキスト補間していたスクリプトは、空文字列ではなく NULL が埋まるようになる。無引用の位置なら以前は SQL 構文エラーになっていたので気づけるが、引用符の中に埋めていた場合はエラーにならない。実機確認: パッチ前のバイナリで INSERT INTO t VALUES (':nv'); を実行すると length 0 の空文字列が入り、processed: 1/1 で正常終了する。パッチ後は同じスクリプトが 4 文字の 'NULL' を入れる。この黙った値の変化が、バックパッチを master のみと判断した理由である。

  • 行が無いことと、行はあるが NULL であることは別物

    \aset で結果が 0 行のときは格納ループの手前で break するので、変数はそもそも作られない。その変数を式で使うと undefined variable のエラーになり、これも CSTATE_ABORTED である。パッチはこの経路を変えていない。\gset の場合は 0 行が expected one row, got 0 のエラーになる。どちらも「NULL が格納される」ケースとは別の失敗であり、本パッチでは直らない。

  • もっともらしく動いてしまう実装ミスが 2 種類ある

    レビューで疑うべき点はこの 2 つである。1 つは判定セルを行 0 にすること。\gset のテストは全部通るので、\aset の複数行ケースを試すまで気づけない。もう 1 つは文字列 "NULL" を putVariable() で入れること。makeVariableValue() の pg_strcasecmp の枝があるので式は正しく動き、IS NULL も通る。どちらも「エラーが出ない」形で間違うので、出力を見ただけでは判別できない。

検証テストが固定していること

  • NULL を捕まえた変数が式で使えて、IS NULL が真になる

    src/bin/pgbench/t/001_pgbench_with_server.pl の "pgbench gset command with NULL"。SELECT NULL AS nv \gset に \set i debug(:nv) と \set i debug(:nv IS NULL) を続け、終了コード 0、stdout に processed: 1/1、stderr に command=2.: null と command=3.: boolean true を要求する。PQgetisnull() を見ない実装に戻すと command=2 に到達する前に abort するので、stderr の 2 本と終了コードが同時に落ちる。

  • NULL と空文字列が補間で区別される

    同ファイルの "pgbench gset NULL interpolation" と、続く 2 つの is()。UNLOGGED テーブル gset_null_tab に SELECT NULL AS nv, ''::text AS es \gset の結果を 2 行 INSERT し、safe_psql で id = 1 の t IS NULL が t、id = 2 の t = '[]' が t であることを検証する。空文字列も null 値として扱う実装にすると 2 つ目の is() が落ちる。

  • prepared モードでは文字列 'NULL' がバインドされる

    同ファイルの "pgbench gset NULL as query parameter" と、続く is()。-M prepared で NULL 値の変数を TEXT 列に INSERT し、safe_psql で t = 'NULL' が t であることを検証する。将来 getQueryParams() を変えて本物の SQL null をバインドするなら、意図的な変更としてこのテストを直すことになる。逆に言えば、この非互換を無自覚に持ち込むことはできない。

  • \aset で判定セルと格納セルが一致している

    同ファイルの "pgbench aset command with NULL"。VALUES (1), (NULL) を ORDER BY 1 NULLS LAST と NULLS FIRST の 2 通りで \aset し、stderr に command=2.: null と command=4.: int 1 を要求する。実測: PQgetisnull の行指定を ntuples - 1 から 0 に変えると、このケースの 4 アサーションだけが落ち、\gset 側は 1 件も落ちない。この 2 通りを 1 つのスクリプトに入れてあるので、判定を固定側の行に寄せる実装ミスはどちらかで必ず露見する。

  • 0 行では変数が作られないという既存の境界が保たれている

    同ファイルの既存ケース "pgbench aset command with empty result"。0 行を返す \aset のあとに \set i debug(:i8) を置き、終了コード 2、stderr に undefined variable "i8" と evaluation of meta-command failed を要求する。パッチはこのケースに手を入れていないので、0 行を NULL として扱う方向に踏み込んだ実装はここで落ちる。

Q010001 \gset の SQL NULL

格納ループの NULL 判定に PQgetisnull(res, ntuples - 1, fld) を使い、行番号を 0 にしない理由として正しいものはどれか。

\gset だけを見ると ntuples は必ず 1 なので 0 と ntuples - 1 は同じ値になり、行 0 でも通ってしまう。差が出るのは行数を制限しない \aset のときだけである。実測でも、行指定を 0 に変えると落ちるのは "pgbench aset command with NULL" の 4 アサーションだけで、\gset のケースは 1 件も落ちない。選択肢 D が最も誘惑的で、\gset が行数を検査するという前提は正しいが、そこから導かれるのは「\gset では 0 と ntuples - 1 が一致する」であって範囲外アクセスではない。B は PQgetisnull が PGresult 上のローカル操作である事実に反する。D は行と列を取り違えている。

Q020001 \gset の SQL NULL

NULL 列に対して setNullValue() + putVariableValue() ではなく、文字列 "NULL" を putVariable() で格納する案を採ったとすると、何が起きるか。

makeVariableValue() には pg_strcasecmp(var->svalue, "null") == 0 の枝があり、そこで setNullValue() が呼ばれるので式の上は動く。この「動いてしまう」ことが厄介で、代わりに SQL NULL とテキストの 'NULL' が同じ表現になる。実機でも SELECT 'NULL'::text AS s \gset のあと debug(:s) は null を出す。選択肢 B が最も誘惑的だが、いま述べた pg_strcasecmp の枝があるので IS NULL は真になる。B は同じ枝が整数解釈より先に来るので成り立たない。D は putVariable() が svalue を必ず設定するので逆で、svalue が NULL になるのは putVariableValue() を使う採用案の側である。

Q030001 \gset の SQL NULL

パッチ適用後のバイナリで、SELECT ''::text AS es \gset に続けて \set i debug(:es) を実行すると何が起きるか。

PQgetisnull() は空文字列に対して偽を返すので、この列は従来どおり putVariable() の経路を通る。makeVariableValue() の slen == 0 の枝は意図的に残してあるため、停止の仕組みはパッチ前と変わらない。実機確認でもパッチ後のバイナリで processed: 0/1 になる。選択肢 C が最も誘惑的だが、PQgetvalue() が NULL と空文字列の両方に "" を返すことと、PQgetisnull() が両者を区別することは別の話である。C は pgbench の式言語に文字列型が無いので成り立たない。D は結果が 1 行返っているので break の条件を満たさない。

Q040001 \gset の SQL NULL

\gset で NULL を捕まえた変数を -M prepared で SQL に埋めた場合、サーバに渡るものはどれか。

getQueryParams() は getVariable() の戻り値をそのまま libpq に渡し、getVariable() は svalue が NULL のとき value.type == PGBT_NULL を "NULL" という文字列にレンダリングする。実機でも TEXT 列に length 4 の 'NULL' が入る。これは \set varname NULL の既存挙動と同じで、本修正の退行ではない。選択肢 C が最も誘惑的で、putVariableValue() が svalue を NULL にするのは事実だが、getVariable() はその場合に文字列形式を作って返すので NULL ポインタは外に出ない。NULL ポインタが渡るのは変数そのものが未定義のときだけである。C は simple モードの挙動で、モードを取り違えている。D は pgbench が全パラメータをテキスト形式で送るので成り立たない。
