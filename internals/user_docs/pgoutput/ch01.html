第1章　pgoutput でできること

🎯 この章のゴール
  • pgoutput が「何を入力に、何を出力するもの」なのかを説明できる
  • 論理レプリケーションと CDC ツールのどこで pgoutput が使われているかが分かる
  • pgoutput で取り出せるもの・取り出せないものを区別できる
📋 前提
  • この章は読むだけ。手を動かすのは第2章から
  • PostgreSQL の WAL（先行書き込みログ）という言葉を聞いたことがある

1.1　pgoutput とは何か

pgoutput は PostgreSQL 本体に標準で組み込まれている論理デコーディング出力プラグインである。 PostgreSQL は更新のたびに WAL を書くが、WAL はブロック単位の物理的な記録なので、そのままでは 「items テーブルの id=1 の行が入った」といった論理的な変更としては読めない。

論理デコーディングは、この WAL を読み直して行単位の変更に組み立て直す仕組みで、 その結果を「どんな形式で外に出すか」を決めるのが出力プラグインである。pgoutput はそのうちの1つで、 変更を独自のバイナリメッセージ列として出力する。図 1.1 のような位置づけになる。

図 1.1 のとおり、pgoutput の出力先は1つではない。購読側の PostgreSQL がそのまま適用することもあれば、 CDC ツールが読み取って Kafka などに流すこともあるし、pg_recvlogical や SQL 関数で自分の手元に 取り出すこともできる。本ガイドでは主に3つ目の「自分の手元に取り出す」方法で中身を確かめながら進める。

💡 ヒント pgoutput は PostgreSQL 10 以降に標準で同梱されている。CREATE EXTENSION も shared_preload_libraries への追加も不要で、共有ライブラリとして $libdir/pgoutput.so が最初から置かれている。

1.2　どこで使われているか

pgoutput が実際に動いている場面は、大きく3つある。

場面誰が pgoutput を使うか本ガイドで扱う章
論理レプリケーションCREATE SUBSCRIPTION した購読側が、既定の出力プラグインとして指定する第7章
CDC（変更データキャプチャ）Debezium などのツールが、レプリケーションスロット経由で読む第3章・第5章
調査・検証運用者が pg_recvlogical や SQL 関数で直接覗く第3章・第4章

重要なのは、この3つはすべて同じ pgoutput を、同じオプションで呼んでいるという点である。 論理レプリケーションのトラブルを調べるときに pg_recvlogical で生の出力を覗けるのは、この共通性のおかげである。

1.3　test_decoding との違い

PostgreSQL には test_decoding というもう1つの標準プラグインが同梱されている。 名前のとおりテスト用で、人間が読めるテキストを出力する。両者は用途がはっきり分かれている。

pgoutputtest_decoding
出力形式バイナリのメッセージ列人間可読のテキスト
用途本番の論理レプリケーション・CDC動作確認・デバッグ
送るテーブルの選択パブリケーションで指定（必須）全テーブル
行フィルタ・列リスト使える使えない
ストリーミング・2相コミット使える使える（形式は簡易）
読みやすさデコードが必要そのまま読める

「とりあえず変更が拾えているか見たい」だけなら test_decoding のほうが手軽である。 一方、本番で使うのは pgoutput なので、本番と同じ挙動を確認したいなら pgoutput を直接読む必要がある。 本ガイドは後者のための手順書である。

1.4　このガイドの進め方

pgoutput から取り出せるもの・取り出せないものを、先に押さえておく。以下はすべて PostgreSQL 16.13 で実際に確認した結果である。

取り出せる取り出せない
INSERT / UPDATE / DELETE の行データDDL（ALTER TABLE など）
TRUNCATEシーケンスの値の進み
トランザクションの開始・コミット・タイムスタンプ生成列（GENERATED ALWAYS AS ... STORED）
2相コミットの PREPARE / COMMIT PREPAREDラージオブジェクト
pg_logical_emit_message() で埋めた任意のメッセージ更新されなかった TOAST 値の実体（後述）
⚠️ よくある誤解 「論理レプリケーションを張れば購読側も自動で ALTER TABLE される」というのは誤り。 DDL は一切流れないので、テーブル定義の変更は発行側・購読側の両方で自分で行う必要がある。 第8章で、これを忘れたときに何が起きるかを扱う。

本ガイドは第2章から実際に手を動かす。第2章で作った環境を第8章まで引き継ぐので、 章をまたいで作り直す必要はない。各章の冒頭に前提を書いてあるので、途中から読む場合はそこを確認してほしい。

✅ チェックポイント
  • pgoutput の入力（WAL）と出力（バイナリメッセージ列）を自分の言葉で言える
  • 論理レプリケーションと CDC ツールが、同じ pgoutput を使っていると説明できる
  • DDL とシーケンスは pgoutput から取り出せない、と即答できる
