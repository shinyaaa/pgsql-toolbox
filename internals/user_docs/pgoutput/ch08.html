第8章　つまずきポイントと対処・チートシート

🎯 この章のゴール
  • pgoutput 利用時によく出るエラーを、メッセージから原因に結び付けられる
  • スロットが原因のディスク逼迫を検知し、対処できる
  • チートシートを使って、必要な操作をすぐ引ける
📋 前提
  • 第7章までの環境（発行側 :5432、購読側 :5433）
  • この章のエラー例はすべて実際に再現させたもの

8.1　環境まわりのエラー

wal_level が足りない。 論理スロットを作ろうとして次のエラーが出たら、 そのインスタンスの wal_level が logical になっていない。

入力（psql） 
SELECT * FROM pg_create_logical_replication_slot('demo', 'pgoutput');
出力 
ERROR:  logical decoding requires wal_level >= logical

対処は 2.1 と同じ（ALTER SYSTEM SET wal_level = 'logical'; のあと再起動）。 再起動が必要なので、pg_reload_conf() だけでは直らない。

プラグインが見つからない。 pgoutput 以外を指定したときによく出る。

出力 
ERROR:  could not access file "wal2json": No such file or directory

pgoutput は標準同梱なのでこのエラーは出ないはずである。出るなら綴りを疑う。 インストール済みのプラグインは次で確認できる。

入力（シェル） 
ls $(pg_config --pkglibdir) | grep -E 'pgoutput|decoding'
出力 
pgoutput.so
test_decoding.so

オプションの不備。 5.2 で見たとおり、起動時コールバックで落ちる。 CONTEXT 行に output plugin "pgoutput" と出るのが目印である。

出力 
ERROR:  publication_names parameter missing
CONTEXT:  slot "shop_slot", output plugin "pgoutput", in the startup callback

同一インスタンス内でのサブスクリプション。 発行側と購読側が同じインスタンス（データベースは別）だと、 CREATE SUBSCRIPTION が終わらずハングする。スロット作成が 「実行中のトランザクションが終わるのを待つ」状態になり、そのトランザクション自身が CREATE SUBSCRIPTION だからである。発行側のログにはこう出る。

出力（発行側ログ） 
LOG:  logical decoding found initial starting point at 0/1E31378
DETAIL:  Waiting for transactions (approximately 1) older than 774 to end.
STATEMENT:  CREATE_REPLICATION_SLOT "shop_sub" LOGICAL pgoutput (SNAPSHOT 'nothing')

回避策はスロットを先に作っておくことである。実際に次の手順で成功する。

入力（psql、発行側データベース） 
SELECT * FROM pg_create_logical_replication_slot('local_sub_slot', 'pgoutput');
出力 
   slot_name    |    lsn
----------------+-----------
 local_sub_slot | 0/27883D0
(1 row)
入力（psql、購読側データベース） 
CREATE SUBSCRIPTION local_sub
  CONNECTION 'host=127.0.0.1 port=5432 dbname=shop user=repl_user password=repl_pass'
  PUBLICATION shop_pub
  WITH (create_slot = false, slot_name = 'local_sub_slot', copy_data = false);
出力 
CREATE SUBSCRIPTION

8.2　REPLICA IDENTITY まわりのエラー

パブリケーションに含まれるテーブルにレプリカアイデンティティが無いと、 UPDATE と DELETE そのものが失敗するようになる。INSERT は成功するので、 気付くのが遅れやすい。

入力（psql -d shop） 
CREATE TABLE audit_log (a int, b text);
ALTER TABLE audit_log REPLICA IDENTITY NOTHING;
ALTER PUBLICATION shop_pub ADD TABLE audit_log;

INSERT INTO audit_log VALUES (1, 'x');   -- これは通る
UPDATE audit_log SET b = 'y';
DELETE FROM audit_log;
出力 
INSERT 0 1
ERROR:  cannot update table "audit_log" because it does not have a replica identity and publishes updates
HINT:  To enable updating the table, set REPLICA IDENTITY using ALTER TABLE.
ERROR:  cannot delete from table "audit_log" because it does not have a replica identity and publishes deletes
HINT:  To enable deleting from the table, set REPLICA IDENTITY using ALTER TABLE.

対処は3つある。

  1. 主キーか一意索引を付けて ALTER TABLE ... REPLICA IDENTITY USING INDEX ... を設定する（推奨）
  2. ALTER TABLE ... REPLICA IDENTITY FULL; にする（購読側の適用が遅くなる）
  3. そのテーブルをパブリケーションから外すか、publish = 'insert' にする

危ないテーブルは事前に洗い出せる。

入力（psql -d shop） 
SELECT c.relname, c.relreplident
  FROM pg_class c
  JOIN pg_publication_rel pr ON pr.prrelid = c.oid
 WHERE c.relreplident IN ('n', 'd')
   AND NOT EXISTS (SELECT 1 FROM pg_index i
                    WHERE i.indrelid = c.oid AND i.indisprimary);

この結果に出たテーブルは、レプリカアイデンティティが決まっていないので UPDATE / DELETE で失敗する。

6.2 で見た行フィルタ由来のエラーも同じ系統である。

出力 
ERROR:  cannot update table "items"
DETAIL:  Column used in the publication WHERE expression is not part of the replica identity.

8.3　スロットの運用

pgoutput のトラブルで最も深刻なのは、誰も読まないスロットが WAL を溜め続けることである。 スロットは「まだ読まれていない WAL を消すな」と指示するので、放置するとディスクが埋まる。 状態は図 8.1 のように遷移する。

監視は次のクエリで行う。

入力（psql -d shop） 
SELECT slot_name, active,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained_wal,
       wal_status
  FROM pg_replication_slots ORDER BY slot_name;
出力 
  slot_name  | active | retained_wal | wal_status
-------------+--------+--------------+------------
 big_slot    | f      | 494 kB       | reserved
 cdc_slot    | f      | 909 kB       | reserved
 shop_slot   | f      | 19 kB        | reserved
 shop_sub    | t      | 56 bytes     | reserved
 stream_slot | f      | 494 kB       | reserved
 tp_slot     | f      | 58 kB        | reserved
(6 rows)

読み方は次のとおり。

  • active = f かつ retained_wal が増え続けるスロットが危険である
  • wal_status が extended になったら猶予は残り少ない
  • lost になったスロットは復旧できない。作り直しになる

不要なスロットは削除する。ただし使用中は削除できない。

入力（psql -d shop） 
SELECT pg_drop_replication_slot('shop_sub');
出力 
ERROR:  replication slot "shop_sub" is active for PID 8518
⚠️ 破壊的操作の注意 pg_drop_replication_slot() は取り消せない。 稼働中のサブスクリプションのスロットを消すと、購読側は二度と続きを受け取れず、 サブスクリプションの作り直し（＝全データの再コピー）が必要になる。 消す前に必ず pg_replication_slots と pg_stat_replication で そのスロットの持ち主を確認すること。サブスクリプション側から消すなら DROP SUBSCRIPTION を使えば、発行側のスロットも一緒に消える。

スロットを先に消してしまった場合。 購読側より先に発行側のスロットを消すと、サブスクリプションが「消せない」状態になる。 DROP SUBSCRIPTION は発行側のスロットも消そうとするが、それが存在しないためである。

入力（psql :5433 -d shop） 
DROP SUBSCRIPTION shop_sub;
出力 
ERROR:  could not drop replication slot "shop_sub" on publisher: ERROR:  replication slot "shop_sub" does not exist

データベースごと消そうとしても止められる。

出力 
ERROR:  database "shop" is being used by logical replication subscription
DETAIL:  There is 1 subscription.

対処は、スロットとの紐付けを外してから削除することである。

入力（psql :5433 -d shop） 
ALTER SUBSCRIPTION shop_sub DISABLE;
ALTER SUBSCRIPTION shop_sub SET (slot_name = NONE);
DROP SUBSCRIPTION shop_sub;
出力 
ALTER SUBSCRIPTION
ALTER SUBSCRIPTION
DROP SUBSCRIPTION

片付けの正しい順序は購読側の DROP SUBSCRIPTION が先である。 そうすれば発行側のスロットも一緒に消える。

💡 ヒント max_slot_wal_keep_size を設定しておくと、スロットが保持できる WAL に上限を設けられる。 上限を超えたスロットは lost になるが、サーバが停止するよりはましである。 本番では設定しておくことを勧める。

8.4　出力が空になるとき

エラーは出ないのに何も届かない、という状況にはいくつかの原因がある。上から順に確認する。

原因確認方法対処
すでに get で消費済み confirmed_flush_lsn が進んでいる 調査には peek を使う
存在しないパブリケーションを指定した SELECT * FROM pg_publication; 綴りを直す。エラーにならず 0 件になるので気付きにくい
テーブルがパブリケーションに入っていない SELECT * FROM pg_publication_tables; ALTER PUBLICATION ... ADD TABLE
行フィルタに合っていない pg_publication_tables.rowfilter 条件を見直す
publish で操作種別が除外されている SELECT * FROM pg_publication; ALTER PUBLICATION ... SET (publish = ...)
論理メッセージが messages=false で捨てられている オプション指定を確認 messages=true を付ける
別のデータベースの変更を見ようとしている pg_replication_slots.database 対象データベースでスロットを作り直す
DDL・シーケンス・生成列を期待している — pgoutput では取得できない（1.4 参照）

存在しないパブリケーション名を渡した場合の挙動は、実際に確認しておく価値がある。

入力（psql -d shop） 
SELECT data FROM pg_logical_slot_peek_binary_changes(
    'shop_slot', NULL, NULL,
    'proto_version','4','publication_names','nosuch_pub');
出力 
 data
------
(0 rows)

エラーにならない。「0 件だから変更が無い」と判断する前に、パブリケーション名を確認すること。
