第7章　実践: 論理レプリケーションと CDC

🎯 この章のゴール
  • 2つのインスタンス間で論理レプリケーションを構成できる
  • CREATE SUBSCRIPTION が裏で発行している pgoutput のオプションを、自分の目で確認できる
  • サブスクリプションの設定変更が pgoutput のオプションに直結することを説明できる
  • レプリケーションの進み具合を監視ビューで確認できる
📋 前提
  • 第6章までの環境（発行側 = ポート 5432 の shop データベース、shop_pub）
  • 購読側として、別インスタンスをポート 5433 に用意する（作り方は 7.1）
  • 第6章で作った検証用パブリケーションは削除しておく: DROP PUBLICATION ins_only_pub, cheap_pub, names_pub, sales_leaf_pub, sales_root_pub;

7.1　購読側インスタンスを用意する

ここまでは pgoutput の出力を自分で覗いてきた。この章では、 PostgreSQL 自身に受け取らせる構成を作る。図 7.1 の形になる。

⌨️ ハンズオン: 購読側を用意する

  1. ポート 5433 に別インスタンスを作って起動する（Debian/Ubuntu の例）。

    入力（シェル） 
    pg_createcluster 16 replica -p 5433 -- -A trust
pg_ctlcluster 16 replica start
pg_lsclusters
    出力 
    Ver Cluster Port Status Owner    Data directory                 Log file
16  main    5432 online postgres /var/lib/postgresql/16/main    ...
16  replica 5433 online postgres /var/lib/postgresql/16/replica ...

  2. 購読側にデータベースと同じ定義のテーブルを作る。 DDL は複製されないので、これは手で用意する必要がある。

    入力（psql -p 5433） 
    CREATE DATABASE shop;
\c shop
CREATE TABLE items (
    id       integer PRIMARY KEY,
    name     text    NOT NULL,
    price    integer NOT NULL,
    in_stock boolean DEFAULT true
);
    出力 
    CREATE DATABASE
CREATE TABLE

  3. 発行側にレプリケーション用のロールを作り、対象テーブルの読み取り権限を与える。

    入力（psql :5432） 
    CREATE ROLE repl_user WITH LOGIN REPLICATION PASSWORD 'repl_pass';
\c shop
GRANT USAGE ON SCHEMA public TO repl_user;
GRANT SELECT ON items TO repl_user;
    出力 
    CREATE ROLE
GRANT
GRANT

  4. 発行側の pg_hba.conf に、購読側からの接続を許す行を足して再読み込みする。

    入力（シェル） 
    echo 'host    shop    repl_user    127.0.0.1/32    scram-sha-256' \
  >> /etc/postgresql/16/main/pg_hba.conf
psql -c "SELECT pg_reload_conf();"

  5. 発行側にテスト用のデータを入れておく。

    入力（psql :5432 -d shop） 
    TRUNCATE items;
INSERT INTO items VALUES (1, 'apple', 120), (2, 'banana', 80);
⚠️ よくある落とし穴 pg_hba.conf の設定を忘れると、CREATE SUBSCRIPTION がこう失敗する。
出力 
ERROR:  could not connect to the publisher: connection to server at "127.0.0.1",
port 5432 failed: fe_sendauth: no password supplied
論理レプリケーションの接続は replication 用の行ではなく、 対象データベースへの通常の接続行で許可する点に注意する （ロール側に REPLICATION 属性は必要）。

7.2　CREATE SUBSCRIPTION で複製する

⌨️ ハンズオン: サブスクリプションを作る

  1. 購読側でサブスクリプションを作る。出力プラグインは指定していない点に注目する。

    入力（psql :5433 -d shop） 
    CREATE SUBSCRIPTION shop_sub
  CONNECTION 'host=127.0.0.1 port=5432 dbname=shop user=repl_user password=repl_pass'
  PUBLICATION shop_pub;
    出力 
    NOTICE:  created replication slot "shop_sub" on publisher
CREATE SUBSCRIPTION

  2. 数秒待って購読側を見ると、初回コピーが終わっている。

    入力（psql :5433 -d shop） 
    SELECT * FROM items ORDER BY id;
    出力 
     id |  name  | price | in_stock
----+--------+-------+----------
  1 | apple  |   120 | t
  2 | banana |    80 | t
(2 rows)

  3. 発行側で1件足すと、購読側にも現れる。

    入力（psql :5432 -d shop） 
    INSERT INTO items VALUES (3, 'cherry', 300);
    入力（psql :5433 -d shop） 
    SELECT * FROM items ORDER BY id;
    出力 
     id |  name  | price | in_stock
----+--------+-------+----------
  1 | apple  |   120 | t
  2 | banana |    80 | t
  3 | cherry |   300 | t
(3 rows)

  4. 発行側にできたスロットを見ると、プラグインは pgoutput である。

    入力（psql :5432 -d shop） 
    SELECT slot_name, plugin, slot_type, active, two_phase
  FROM pg_replication_slots WHERE slot_name = 'shop_sub';
    出力 
    -[ RECORD 1 ]-------
slot_name | shop_sub
plugin    | pgoutput
slot_type | logical
active    | t
two_phase | f

ここまでで pgoutput を一度も名指ししていないのに、 スロットの plugin は pgoutput になっている。 論理レプリケーションは pgoutput を既定かつ唯一の出力プラグインとして使うためである。

7.3　裏側で流れている pgoutput のオプション

購読側が発行側に何を要求しているかは、発行側のログで直接見られる。 log_replication_commands を有効にすると、レプリケーションコマンドが記録される。

⌨️ ハンズオン: START_REPLICATION を覗く

  1. 発行側でログ設定を有効にする。

    入力（psql :5432） 
    ALTER SYSTEM SET log_replication_commands = on;
SELECT pg_reload_conf();
    出力 
    ALTER SYSTEM
 pg_reload_conf
----------------
 t
(1 row)

  2. 購読側を一度切って繋ぎ直し、接続をやり直させる。

    入力（psql :5433 -d shop） 
    ALTER SUBSCRIPTION shop_sub DISABLE;
ALTER SUBSCRIPTION shop_sub ENABLE;

  3. 発行側のログを見る。

    入力（シェル） 
    grep -a "START_REPLICATION" /var/log/postgresql/postgresql-16-main.log | tail -1
    出力 
    STATEMENT:  START_REPLICATION SLOT "shop_sub" LOGICAL 0/0 (proto_version '4', origin 'any', publication_names '"shop_pub"')

第3章で pg_recvlogical -o proto_version=4 -o publication_names='shop_pub' と 手で打ったのと同じものが、購読側から自動的に送られている。 論理レプリケーションと pg_recvlogical は、まったく同じ入口を使っている。

💡 ヒント 初回のデータコピー中には、テーブルごとの一時スロットが別に作られ、 こちらも pgoutput で START_REPLICATION する。ログには SLOT "pg_24585_sync_24577_7670908608867262836" のような名前で現れる。 同期が終われば自動的に消えるので、この名前のスロットを見かけても慌てなくてよい。

7.4　サブスクリプションの設定は pgoutput の設定

サブスクリプションのオプションを変えると、START_REPLICATION の中身がそのまま変わる。 つまり ALTER SUBSCRIPTION は pgoutput のオプションを変えているのである。

⌨️ ハンズオン: オプションを変えてログを見比べる

  1. binary と streaming を変える。

    入力（psql :5433 -d shop） 
    ALTER SUBSCRIPTION shop_sub SET (binary = true, streaming = 'parallel');
    出力 
    ALTER SUBSCRIPTION

  2. 数秒待ってログを見る。

    出力 
    STATEMENT:  START_REPLICATION SLOT "shop_sub" LOGICAL 0/234F900 (proto_version '4', streaming 'parallel', origin 'any', publication_names '"shop_pub"', binary 'true')

  3. さらに origin を変える。

    入力（psql :5433 -d shop） 
    ALTER SUBSCRIPTION shop_sub SET (origin = none);
    出力（ログ） 
    STATEMENT:  START_REPLICATION SLOT "shop_sub" LOGICAL 0/234F900 (proto_version '4', streaming 'parallel', origin 'none', publication_names '"shop_pub"', binary 'true')

  4. 設定はカタログにも反映されている。

    入力（psql :5433 -d shop） 
    SELECT subname, subbinary, substream, suborigin FROM pg_subscription;
    出力 
     subname  | subbinary | substream | suborigin
----------+-----------+-----------+-----------
 shop_sub | t         | p         | none
(1 row)

対応関係を表にすると次のとおり。第5章で1つずつ試したオプションが、そのまま並んでいる。

サブスクリプションのオプションpgoutput に渡るオプション
binary = truebinary 'true'
streaming = 'on' / 'parallel'streaming 'on' / 'parallel'
two_phase = truetwo_phase 'true'（スロット作成時に決まる）
origin = noneorigin 'none'
PUBLICATION a, bpublication_names '"a","b"'

7.5　監視する

運用で見るべきビューは3つある。

入力（psql :5433 -d shop）— 購読側 
SELECT subid, subname, pid, received_lsn, latest_end_lsn FROM pg_stat_subscription;
出力 
-[ RECORD 1 ]--+----------
subid          | 24585
subname        | shop_sub
pid            | 8479
received_lsn   | 0/234F900
latest_end_lsn | 0/234F900

received_lsn と latest_end_lsn が一致していれば追いついている。

入力（psql :5432 -d shop）— 発行側 
SELECT application_name, state, sent_lsn, flush_lsn, replay_lsn, sync_state
  FROM pg_stat_replication;
出力 
-[ RECORD 1 ]----+----------
application_name | shop_sub
state            | streaming
sent_lsn         | 0/234F900
flush_lsn        | 0/234F900
replay_lsn       | 0/234F900
sync_state       | async

state = streaming が定常状態である。sent_lsn と replay_lsn の差が 遅延にあたる。3つ目の pg_stat_replication_slots（5.5 で使った）で spill / stream の発生状況を見れば、遅延の原因がデコード側にあるかどうかが切り分けられる。

✅ チェックポイント
  • 発行側で INSERT した行が、数秒以内に購読側に現れる
  • 発行側の pg_replication_slots に plugin = pgoutput のスロットがある
  • 発行側のログで START_REPLICATION ... (proto_version '4', ...) を確認した
  • ALTER SUBSCRIPTION ... SET (binary = true) がログの binary 'true' に対応するのを確認した
