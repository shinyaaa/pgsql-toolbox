第6章　送る内容をパブリケーションで絞る

🎯 この章のゴール
  • publish オプションで、送る操作の種類を絞れる
  • 行フィルタと列リストで、送る行・列を絞れる
  • パーティションテーブルを、葉と親のどちらの名前で送るか選べる
📋 前提
  • 第5章までの環境（shop_slot は消費済み、items は REPLICA IDENTITY DEFAULT）
  • この章の冒頭で TRUNCATE items; して、たまったテストデータを空にしてから始める
  • デコード結果は pgoutput_decode.py（4.5）を通したもの

第5章のオプションが「pgoutput 側の設定」だったのに対し、この章で扱うのは パブリケーション側の設定である。図 6.1 のように、同じテーブルに絞り込みの違う パブリケーションを複数定義しておき、pgoutput の publication_names でどれを使うかを選ぶ。 同じスロット・同じオプションでも、指定するパブリケーションが違えば届く内容が変わる。

6.1　publish で操作種別を絞る

publish オプションで、INSERT / UPDATE / DELETE / TRUNCATE のどれを送るかを選べる。

⌨️ ハンズオン: INSERT だけ送る

  1. テストデータを空にし、スロットも空にしてから始める。

    入力（シェル） 
    psql -d shop -c "TRUNCATE items;"
psql -d shop -tAc "SELECT count(*) FROM pg_logical_slot_get_binary_changes(
    'shop_slot', NULL, NULL, 'proto_version','4','publication_names','shop_pub')"

  2. INSERT だけを発行するパブリケーションを作る。

    入力（psql -d shop） 
    CREATE PUBLICATION ins_only_pub FOR TABLE items WITH (publish = 'insert');
    出力 
    CREATE PUBLICATION

  3. 3種類の操作を実行する。

    入力（シェル） 
    psql -d shop -c "INSERT INTO items VALUES (10, 'apple', 120);"
psql -d shop -c "UPDATE items SET price = 130 WHERE id = 10;"
psql -d shop -c "DELETE FROM items WHERE id = 10;"

  4. ins_only_pub を指定してデコードする。

    入力（シェル） 
    psql -d shop -tAc "SELECT data FROM pg_logical_slot_get_binary_changes(
    'shop_slot', NULL, NULL,
    'proto_version','4','publication_names','ins_only_pub')" \
  | python3 pgoutput_decode.py
    出力 
    BEGIN      final_lsn=0/2342AE0 ts=2026-08-06T13:35:41.165872+00:00 xid=820
RELATION   24596 public.items identity=d cols=[*id:23, name:25, price:23, in_stock:16]
INSERT     rel=24596 N['10', 'apple', '120', 't']
COMMIT     commit_lsn=0/2342AE0 end_lsn=0/2342B10 ts=2026-08-06T13:35:41.165872+00:00

UPDATE と DELETE のトランザクションは丸ごと消えている。 送るものが1つも無いトランザクションは、Begin / Commit すら出力されない。 これは pgoutput 全般に共通する挙動で、「空トランザクションは送らない」と覚えておくとよい。

6.2　行フィルタ

FOR TABLE テーブル名 WHERE (条件) で、条件を満たす行だけを送れる。

⌨️ ハンズオン: 500 未満の商品だけ送る

  1. 行フィルタ付きのパブリケーションを作る。

    入力（psql -d shop） 
    CREATE PUBLICATION cheap_pub FOR TABLE items WHERE (price < 500);
    出力 
    CREATE PUBLICATION

  2. 条件に合う行と合わない行を1件ずつ入れる。

    入力（psql -d shop） 
    INSERT INTO items VALUES (11, 'cheap', 100), (12, 'luxury', 9800);
    出力 
    INSERT 0 2

  3. デコードする。

    出力 
    BEGIN      final_lsn=0/23435F8 ts=2026-08-06T13:35:41.430540+00:00 xid=824
RELATION   24596 public.items identity=d cols=[*id:23, name:25, price:23, in_stock:16]
INSERT     rel=24596 N['11', 'cheap', '100', 't']
COMMIT     commit_lsn=0/23435F8 end_lsn=0/2343628 ts=2026-08-06T13:35:41.430540+00:00

  4. 設定はカタログで確認できる。

    入力（psql -d shop） 
    SELECT pubname, tablename, attnames, rowfilter
  FROM pg_publication_tables ORDER BY pubname;
    出力 
       pubname    | tablename |         attnames         |   rowfilter
--------------+-----------+--------------------------+---------------
 cheap_pub    | items     | {id,name,price,in_stock} | (price < 500)
 ins_only_pub | items     | {id,name,price,in_stock} |
 shop_pub     | items     | {id,name,price,in_stock} |
(3 rows)

price = 9800 の luxury は同じトランザクションにあったにもかかわらず送られていない。 フィルタは行単位で効く。

⚠️ よくある落とし穴（重要） 行フィルタに使った列がレプリカアイデンティティに含まれていないと、 そのテーブルへの UPDATE / DELETE が失敗するようになる。 しかもこれは cheap_pub を使っていない操作にも影響する。
入力（psql -d shop） 
UPDATE items SET price = 260 WHERE id = 13;
出力 
ERROR:  cannot update table "items"
DETAIL:  Column used in the publication WHERE expression is not part of the replica identity.
対処は2つ。REPLICA IDENTITY FULL にするか、行フィルタを主キーなど レプリカアイデンティティに含まれる列だけで書き直す。 なお publish から update,delete を外しておけば、この制約はかからない。

6.3　列リスト

テーブル名の後ろに括弧で列を並べると、その列だけが送られる。 個人情報を含む列を購読側に渡したくない、といった場面で使う。

⌨️ ハンズオン: id と name だけ送る

  1. 列リスト付きのパブリケーションを作る。

    入力（psql -d shop） 
    CREATE PUBLICATION names_pub FOR TABLE items (id, name);
    出力 
    CREATE PUBLICATION

  2. 1件入れてデコードする。

    入力（psql -d shop） 
    INSERT INTO items VALUES (13, 'kiwi', 250);
    出力（デコード結果） 
    BEGIN      final_lsn=0/2343F38 ts=2026-08-06T13:35:41.967612+00:00 xid=826
RELATION   24596 public.items identity=d cols=[*id:23, name:25]
INSERT     rel=24596 N['13', 'kiwi']
COMMIT     commit_lsn=0/2343F38 end_lsn=0/2343F68 ts=2026-08-06T13:35:41.967612+00:00

Relation メッセージの列定義そのものが2列になっている点が重要である。 受け取る側から見れば「そういう2列のテーブル」に見えるので、 購読側のテーブルには price と in_stock が無くてもよい。

💡 ヒント 列リストにはレプリカアイデンティティの列を必ず含める必要がある。含めないと CREATE PUBLICATION の時点ではなく、UPDATE / DELETE の実行時にエラーになる。

6.4　パーティションテーブル

パーティションテーブルは、既定では実際に行が入った葉テーブルの名前で送られる。 publish_via_partition_root = true にすると、親テーブルの名前で送られる。 購読側がパーティション化されていない普通のテーブルの場合は後者が必要になる。

⌨️ ハンズオン: 葉と親を比べる

  1. パーティションテーブルと、2種類のパブリケーションを作る。

    入力（psql -d shop） 
    CREATE TABLE sales (id int, region text, amount int) PARTITION BY LIST (region);
CREATE TABLE sales_east PARTITION OF sales FOR VALUES IN ('east');

CREATE PUBLICATION sales_leaf_pub FOR TABLE sales;
CREATE PUBLICATION sales_root_pub FOR TABLE sales
  WITH (publish_via_partition_root = true);
    出力 
    CREATE TABLE
CREATE TABLE
CREATE PUBLICATION
CREATE PUBLICATION

  2. 1件入れて、まず sales_leaf_pub（既定）でデコードする。

    入力（psql -d shop） 
    INSERT INTO sales VALUES (1, 'east', 500);
    出力（デコード結果） 
    BEGIN      final_lsn=0/234AE80 ts=2026-08-06T13:35:42.349796+00:00 xid=832
RELATION   24631 public.sales_east identity=d cols=[id:23, region:25, amount:23]
INSERT     rel=24631 N['1', 'east', '500']
COMMIT     commit_lsn=0/234AE80 end_lsn=0/234AEB0 ts=2026-08-06T13:35:42.349796+00:00

  3. もう1件入れて、sales_root_pub でデコードする。

    入力（psql -d shop） 
    INSERT INTO sales VALUES (2, 'east', 600);
    出力（デコード結果） 
    BEGIN      final_lsn=0/234AEF8 ts=2026-08-06T13:35:42.440576+00:00 xid=833
RELATION   24628 public.sales identity=d cols=[id:23, region:25, amount:23]
RELATION   24631 public.sales_east identity=d cols=[id:23, region:25, amount:23]
INSERT     rel=24628 N['2', 'east', '600']
COMMIT     commit_lsn=0/234AEF8 end_lsn=0/234AF28 ts=2026-08-06T13:35:42.440576+00:00

  4. OID を照合する。

    入力（psql -d shop） 
    SELECT 'sales'::regclass::oid AS sales, 'sales_east'::regclass::oid AS sales_east;
    出力 
     sales | sales_east
-------+------------
 24628 |      24631
(1 row)

既定では Insert の rel が葉テーブル sales_east（24631）だったのに対し、 publish_via_partition_root = true では親テーブル sales（24628）になっている。 受け取る側が見るテーブル名が変わる、というのがこのオプションの効果である。

6.5　テーブル集合の指定方法

パブリケーションに含めるテーブルの指定方法は4通りある。

書き方意味注意
FOR TABLE a, b指定したテーブルだけ後から ALTER PUBLICATION ... ADD/DROP TABLE できる
FOR TABLES IN SCHEMA sスキーマ内の全テーブル後から作られたテーブルも自動的に含まれる
FOR ALL TABLESデータベース内の全テーブルスーパーユーザ権限が必要
組み合わせFOR TABLE a, TABLES IN SCHEMA sPostgreSQL 15 以降

publication_names にはカンマ区切りで複数のパブリケーションを渡せる。 その場合、いずれかに含まれていれば送られる（和集合）。行フィルタも同様に OR で合成されるので、 「片方にフィルタ無しのパブリケーションが混ざっていると、フィルタが実質無効になる」点に注意する。

入力（psql -d shop）— 複数指定の例 
SELECT data FROM pg_logical_slot_peek_binary_changes(
    'shop_slot', NULL, NULL,
    'proto_version','4',
    'publication_names','cheap_pub,names_pub');
✅ チェックポイント
  • publish = 'insert' のパブリケーションで UPDATE / DELETE が丸ごと消えるのを確認した
  • 行フィルタに合わない行が送られないのを確認した
  • 行フィルタ列がレプリカアイデンティティに無いと UPDATE がエラーになる、と説明できる
  • 列リストを付けると Relation メッセージの列定義自体が変わるのを確認した
  • publish_via_partition_root で Insert の rel が親テーブルの OID になるのを確認した
