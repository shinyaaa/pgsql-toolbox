第3章　まず動かす — 3 分で出力を見る

🎯 この章のゴール
  • SQL 関数だけで pgoutput の出力を取り出せる
  • 取り出した4行が何を意味しているか、先頭1バイトから読み取れる
  • peek と get の違いを説明でき、使い分けられる
  • pg_recvlogical で同じ内容をファイルに受け取れる
📋 前提
  • 第2章の環境（shop データベース、items テーブル、shop_pub、shop_slot）
  • psql で shop に接続できること
  • 3.4 では pg_recvlogical コマンドを使う（PostgreSQL のクライアントパッケージに同梱）

pgoutput の出力を手元に取り出す方法は2つある。図 3.1 のとおり、 どちらも同じスロット・同じオプションを使い、返ってくるメッセージ列も同じである。 違うのは取り出し方だけなので、まず手軽な SQL 関数から始める。

3.1　SQL 関数で出力を覗く

pgoutput の出力を見る一番手軽な方法は、pg_logical_slot_peek_binary_changes() である。 レプリケーション接続を張らずに、普通の psql から呼べる。

⌨️ ハンズオン: 最初の1件を取り出す

  1. 1行 INSERT する。

    入力（psql -d shop） 
    INSERT INTO items VALUES (1, 'apple', 120);
    出力 
    INSERT 0 1

  2. スロットに溜まった変更を pgoutput 形式で取り出す。第4引数以降は キーと値を交互に並べた pgoutput のオプションで、 proto_version と publication_names は必須である。

    入力（psql -d shop） 
    SELECT lsn, xid, data
  FROM pg_logical_slot_peek_binary_changes(
         'shop_slot', NULL, NULL,
         'proto_version', '4',
         'publication_names', 'shop_pub');
    出力 
        lsn    | xid |                                                data
-----------+-----+------------------------------------------------------------------------------------
 0/2269E60 | 792 | \x420000000002269f480002fb5fb165a5ce00000318
 0/2269E60 | 792 | \x52000060147075626c6963006974656d73006400040169640000000017ffffffff006e616d650000000019ffffffff0070726963650000000017ffffffff00696e5f73746f636b0000000010ffffffff
 0/2269E60 | 792 | \x49000060144e000474000000013174000000056170706c657400000003313230740000000174
 0/2269F78 | 792 | \x43000000000002269f480000000002269f780002fb5fb165a5ce
(4 rows)

    2行目と3行目は長いので、端末では折り返して表示される。区切り線の幅は端末幅に合わせて縮めてある。

1回の INSERT から4つのメッセージが出た。これが pgoutput の出力そのものである。 lsn は WAL 上の位置、xid はトランザクション ID で、この4つが同じ 792 なので 同一トランザクションのものだと分かる。

⚠️ よくある落とし穴 pg_logical_slot_peek_changes()（binary なし）を使うと ERROR: output plugin "pgoutput" produces binary output, but function ... expects textual data になる。pgoutput はバイナリを出すので、_binary_ が付いた関数を使うこと。

3.2　4 行の出力を読む

pgoutput のメッセージは先頭1バイトが型である。ASCII 1文字なので、16進の最初の2桁を見れば 何のメッセージか分かる。今回の4行は次のとおり。

先頭バイトASCIIメッセージ意味
42BBeginトランザクション開始
52RRelationこれから送るテーブルの定義
49IInsert行が1件入った
43CCommitトランザクション終了

3行目の Insert メッセージを手で分解してみる。16進を意味の単位で区切ると、次のように読める。

Insert メッセージの分解 
49            'I'         メッセージ型 = Insert
00006014      24596       テーブルの OID（relid）
4e            'N'         これから続くのは新しい行（New tuple）
0004          4           列数
74 00000001 31            't' 長さ1 "1"        → id       = 1
74 00000005 6170706c65    't' 長さ5 "apple"    → name     = 'apple'
74 00000003 313230        't' 長さ3 "120"      → price    = 120
74 00000001 74            't' 長さ1 "t"        → in_stock = true

各列は「種別1バイト＋長さ4バイト＋値」の形で並んでいる。種別 t は テキスト表現という意味で、120 という整数も文字列 "120" として送られている。 これを本来のバイナリ表現に変える方法が第5章の binary オプションである。

テーブルの OID がメッセージに載っているので、実際のテーブルと照合できる。

入力（psql -d shop） 
SELECT 'items'::regclass::oid AS relid,
       to_hex('items'::regclass::oid::int) AS hex;
出力 
 relid | hex
-------+------
 24596 | 6014
(1 row)

Insert メッセージにあった 00006014 と一致している。OID は環境ごとに異なるので、 自分の環境ではこのクエリで確認すること。同様に列の型 OID も確認できる。

入力（psql -d shop） 
SELECT oid, typname FROM pg_type WHERE oid IN (16, 23, 25) ORDER BY oid;
出力 
 oid | typname
-----+---------
  16 | bool
  23 | int4
  25 | text
(3 rows)
💡 ヒント Relation メッセージ（2行目）の中に 7075626c6963（public）と 6974656d73（items）が見える。16進を眺めるときは、ASCII が混ざっている部分を 探すとスキーマ名・テーブル名・列名の切れ目が見つけやすい。詳しい分解は第4章で行う。

3.3　peek と get の違い

いま使った peek は覗くだけで、スロットの読み取り位置を進めない。 何度呼んでも同じものが返る。

⌨️ ハンズオン: peek と get を比べる

  1. もう一度 peek する。同じ4件が残っている。

    入力（psql -d shop） 
    SELECT count(*) FROM pg_logical_slot_peek_binary_changes(
    'shop_slot', NULL, NULL,
    'proto_version', '4', 'publication_names', 'shop_pub');
    出力 
     count
-------
     4
(1 row)

  2. get に変えると、返すと同時に消費する。

    入力（psql -d shop） 
    SELECT count(*) FROM pg_logical_slot_get_binary_changes(
    'shop_slot', NULL, NULL,
    'proto_version', '4', 'publication_names', 'shop_pub');
    出力 
     count
-------
     4
(1 row)

  3. もう一度覗くと空になっている。

    入力（psql -d shop） 
    SELECT count(*) FROM pg_logical_slot_peek_binary_changes(
    'shop_slot', NULL, NULL,
    'proto_version', '4', 'publication_names', 'shop_pub');
    出力 
     count
-------
     0
(1 row)

使い分けは単純である。調査中は peek、スロットを進めて WAL を解放したいときは get。 以降の章では、前の章の残骸を片付ける目的で get をよく使う。

⚠️ よくある落とし穴 本番で使われているスロットに対して get を実行してはいけない。 本来の消費者（購読側や CDC ツール）が受け取るはずだった変更を横取りしてしまい、 データの取りこぼしになる。本番調査では必ず peek を使うか、 調査専用のスロットを別に作ること。

3.4　pg_recvlogical で受け取る

本番の CDC ツールは SQL 関数ではなくレプリケーション接続で受け取る。 その最小の実装が、PostgreSQL 同梱の pg_recvlogical コマンドである。

⌨️ ハンズオン: pg_recvlogical で受け取る

  1. 受信用のスロットを作る。-P で出力プラグインを指定する。成功時は何も表示されない。

    入力（シェル） 
    pg_recvlogical -d shop --slot=cdc_slot --create-slot -P pgoutput
    出力 
    (何も出力されない。終了コード 0 なら成功)

  2. 変更を1件作る。

    入力（psql -d shop） 
    INSERT INTO items VALUES (8, 'lemon', 210);
    出力 
    INSERT 0 1

  3. 現在の WAL 位置を控える。これを終了位置に使うと、 pg_recvlogical がそこまで受け取って自動的に終了するので、 対話的に Ctrl-C しなくて済む。

    入力（シェル） 
    LSN=$(psql -d shop -tAc "SELECT pg_current_wal_lsn();")
echo $LSN
    出力 
    0/226C5F8

  4. 受信する。オプションは -o キー=値 の形で pgoutput にそのまま渡る。

    入力（シェル） 
    pg_recvlogical -d shop --slot=cdc_slot --start \
  -o proto_version=4 \
  -o publication_names='shop_pub' \
  --endpos="$LSN" -f /tmp/cdc.bin
    出力 
    (何も出力されず、$LSN まで受け取ると終了する)

  5. 受け取った内容はバイナリなので od で見る。

    入力（シェル） 
    od -A d -t x1z /tmp/cdc.bin
    出力 
    0000000 42 00 00 00 00 02 26 c5 c8 00 02 fb 5f b4 35 73  >B.....&....._.5s<
0000016 c3 00 00 03 27 0a 52 00 00 60 14 70 75 62 6c 69  >....'.R..`.publi<
0000032 63 00 69 74 65 6d 73 00 64 00 04 01 69 64 00 00  >c.items.d...id..<
0000048 00 00 17 ff ff ff ff 00 6e 61 6d 65 00 00 00 00  >........name....<
0000064 19 ff ff ff ff 00 70 72 69 63 65 00 00 00 00 17  >......price.....<
0000080 ff ff ff ff 00 69 6e 5f 73 74 6f 63 6b 00 00 00  >.....in_stock...<
0000096 00 10 ff ff ff ff 0a 49 00 00 60 14 4e 00 04 74  >.......I..`.N..t<
0000112 00 00 00 01 38 74 00 00 00 05 6c 65 6d 6f 6e 74  >....8t....lemont<
0000128 00 00 00 03 32 31 30 74 00 00 00 01 74 0a 43 00  >....210t....t.C.<
0000144 00 00 00 00 02 26 c5 c8 00 00 00 00 02 26 c5 f8  >.....&.......&..<
0000160 00 02 fb 5f b4 35 73 c3 0a                       >..._.5s..<

右側の ASCII 表示に public、items、id、name、 price、in_stock、lemon が読み取れる。 3.1 の SQL 関数で見たのとまったく同じメッセージ列である。取り出し方が違うだけで、 pgoutput が出しているものは変わらない。

💡 ヒント pg_recvlogical は各メッセージの後ろに改行（0a）を1バイト足して書き出す。 上の出力で ...00 00 03 27 0a 52 00 00 60 14... のように、Begin と Relation の 境目に 0a が挟まっているのがそれである。これは pg_recvlogical が付ける区切りであって、 pgoutput のメッセージの一部ではない。
⚠️ よくある落とし穴 -f で指定したファイルは追記される。同じ手順を2回実行すると 前回の内容の後ろに繋がってしまうので、やり直すときは rm -f /tmp/cdc.bin してから実行する。
また、--endpos を付けずに -f - で標準出力に流すと、 端末がバイナリで埋まって表示が壊れる。必ずファイルに落とすか | od -A d -t x1z に繋ぐこと。
✅ チェックポイント
  • pg_logical_slot_peek_binary_changes() で4件のメッセージが取り出せた
  • 先頭バイト 42 / 52 / 49 / 43 がそれぞれ Begin / Relation / Insert / Commit だと言える
  • get を実行すると次の peek が 0 件になることを確認した
  • /tmp/cdc.bin の od 出力に public と items が読める
