第2章　準備

🎯 この章のゴール
  • wal_level = logical を設定し、論理デコーディングを使える状態にできる
  • サンプルテーブルとパブリケーションを作れる
  • pgoutput を指定したレプリケーションスロットを作り、状態を確認できる
📋 前提
  • PostgreSQL 16 が動いていて、スーパーユーザ（例: postgres）で psql に接続できる
  • サーバを1回再起動できる（wal_level の変更に必要）
  • 本ガイドの出力例は Ubuntu 24.04 上の PostgreSQL 16.13、ポート 5432 で採取した

ここで作る環境は第8章まで使い続ける。図 2.1 の4ステップで用意する。

2.1　wal_level を logical にする

論理デコーディングは、WAL に「行の中身」まで書かれていないと成立しない。既定の wal_level = replica では情報が足りないので、logical に上げる。

⌨️ ハンズオン: wal_level を上げる

  1. 現在の設定を確認する。

    入力（psql） 
    SHOW wal_level;
    出力 
     wal_level
-----------
 replica
(1 row)

  2. logical に変更する。スロットとウォールセンダの上限も、後の章で複数スロットを使うので余裕を持たせておく。

    入力（psql） 
    ALTER SYSTEM SET wal_level = 'logical';
ALTER SYSTEM SET max_replication_slots = 10;
ALTER SYSTEM SET max_wal_senders = 10;
    出力 
    ALTER SYSTEM
ALTER SYSTEM
ALTER SYSTEM

  3. サーバを再起動する。wal_level は再起動が必要なパラメータで、pg_reload_conf() では反映されない。

    入力（シェル） 
    pg_ctlcluster 16 main restart      # Debian/Ubuntu の場合
# もしくは: pg_ctl -D $PGDATA restart

  4. 反映を確認する。

    入力（psql） 
    SHOW wal_level;
    出力 
     wal_level
-----------
 logical
(1 row)

logical と表示されれば準備完了である。ここが replica のままだと、この先のスロット作成が すべて失敗する（第8章 8.1 で実際のエラーを示す）。

⚠️ よくある落とし穴 wal_level を上げると WAL の量が増える。ディスクの空きと WAL アーカイブの容量に 余裕があるかを、本番で変更する前に確認すること。また ALTER SYSTEM は postgresql.auto.conf に書き込むので、構成管理ツールで postgresql.conf を管理している環境では設定が二重になる点に注意する。

2.2　サンプルデータベースとテーブルを作る

以降の章で使う shop データベースと items テーブルを作る。 主キーを付けるのが重要で、これが後の章で出てくる「レプリカアイデンティティ」の既定値になる。

⌨️ ハンズオン: shop データベースを作る

  1. データベースを作る。

    入力（psql） 
    CREATE DATABASE shop;
    出力 
    CREATE DATABASE

  2. shop に接続し直してテーブルを作る。

    入力（psql -d shop） 
    CREATE TABLE items (
    id       integer PRIMARY KEY,
    name     text    NOT NULL,
    price    integer NOT NULL,
    in_stock boolean DEFAULT true
);
    出力 
    CREATE TABLE
💡 ヒント 論理デコーディングはデータベース単位で動く。スロットは作成時のデータベースに固定され、 他のデータベースの変更は一切見えない。複数データベースを対象にしたいなら、データベースごとにスロットを作る。

2.3　パブリケーションを作る

pgoutput は「どのテーブルを送るか」を自分では決めない。パブリケーションという カタログオブジェクトで指定する。これは pgoutput の必須の前提で、パブリケーションを渡さないと pgoutput は起動時にエラーになる（第5章 5.2 で確認する）。

⌨️ ハンズオン: パブリケーションを作る

  1. items を含むパブリケーションを作る。

    入力（psql -d shop） 
    CREATE PUBLICATION shop_pub FOR TABLE items;
    出力 
    CREATE PUBLICATION

  2. どの操作が発行対象になっているかを確認する。

    入力（psql -d shop） 
    SELECT pubname, pubinsert, pubupdate, pubdelete, pubtruncate
  FROM pg_publication;
    出力 
     pubname  | pubinsert | pubupdate | pubdelete | pubtruncate
----------+-----------+-----------+-----------+-------------
 shop_pub | t         | t         | t         | t
(1 row)

  3. どの列・どの行が対象かは pg_publication_tables で分かる。

    入力（psql -d shop） 
    SELECT * FROM pg_publication_tables;
    出力 
     pubname  | schemaname | tablename |         attnames         | rowfilter
----------+------------+-----------+--------------------------+-----------
 shop_pub | public     | items     | {id,name,price,in_stock} |
(1 row)

attnames が4列すべて、rowfilter が空なので、いまは items の全行・全列が対象である。 これを絞る方法は第6章で扱う。

2.4　レプリケーションスロットを作る

レプリケーションスロットは「どこまで読んだか」を覚えておく栞であり、 同時に「まだ読まれていない WAL を消すな」とサーバに指示する仕組みでもある。 スロットを作るときに、使う出力プラグインとして pgoutput を指定する。

⌨️ ハンズオン: pgoutput のスロットを作る

  1. スロットを作る。第2引数が出力プラグイン名である。

    入力（psql -d shop） 
    SELECT * FROM pg_create_logical_replication_slot('shop_slot', 'pgoutput');
    出力 
     slot_name |    lsn
-----------+-----------
 shop_slot | 0/2269E60
(1 row)

  2. 状態を確認する。

    入力（psql -d shop） 
    SELECT slot_name, plugin, slot_type, database, active,
       restart_lsn, confirmed_flush_lsn
  FROM pg_replication_slots WHERE slot_name = 'shop_slot';
    出力 
    -[ RECORD 1 ]-------+----------
slot_name           | shop_slot
plugin              | pgoutput
slot_type           | logical
database            | shop
active              | f
restart_lsn         | 0/2269E28
confirmed_flush_lsn | 0/2269E60

読み方は次のとおり。plugin が pgoutput、slot_type が logical なら意図どおり。 database が shop に固定されている点、いま誰も接続していないので active が f である点も確認しておく。confirmed_flush_lsn は「消費者がここまで受け取ったと確認した位置」で、 第3章以降、変更を消費するたびに進んでいく。

⚠️ よくある落とし穴 スロットは誰も読まなくても WAL を保持し続ける。作りっぱなしのスロットを放置すると WAL がディスクを埋め尽くしてサーバが停止する。検証で作ったスロットは SELECT pg_drop_replication_slot('スロット名'); で必ず消すこと。監視方法は第8章 8.3 で扱う。
✅ チェックポイント
  • SHOW wal_level; が logical を返す
  • shop データベースに items テーブルがある
  • pg_publication_tables に shop_pub / items の行が1つある
  • pg_replication_slots に plugin = pgoutput の shop_slot がある
