第4章　出力メッセージを読む

🎯 この章のゴール
  • pgoutput のメッセージ型を一覧で把握し、先頭バイトから見分けられる
  • UPDATE / DELETE の出力が REPLICA IDENTITY でどう変わるかを説明できる
  • 手元のデコーダで、16進を人間が読める形に変換できる
📋 前提
  • 第3章までの環境（shop_slot は 3.3 で消費済み、cdc_slot も作成済み）
  • Python 3 が使えること（4.5 のデコーダで使う）
  • この章の出力はすべて shop_slot を get で消費しながら採取している

4.1　メッセージ型の一覧

pgoutput が出すメッセージは、すべて先頭1バイトの型で始まる。 プロトコルバージョン4（PostgreSQL 16）で出てくるものは次のとおり。

16進文字メッセージいつ出るか
42BBeginトランザクションの先頭
43CCommitトランザクションの末尾
52RRelationそのテーブルを初めて送るとき
59YType組み込みでない型を初めて送るとき
49IInsertINSERT
55UUpdateUPDATE
44DDeleteDELETE
54TTruncateTRUNCATE
4dMMessagemessages=true かつ論理メッセージが埋められたとき
4fOOrigin複製起点の情報を送るとき
53SStream Startstreaming=true で未コミットの塊を送り始めるとき
45EStream Stop同上、塊の終わり
63cStream Commitストリーミングしたトランザクションのコミット
41AStream Abortストリーミングしたトランザクションのアボート
62bBegin Preparetwo_phase=true の PREPARE
50PPrepare同上
4bKCommit PreparedCOMMIT PREPARED
72rRollback PreparedROLLBACK PREPARED

通常のトランザクションは、図 4.1 の順序で流れてくる。

💡 ヒント 図 4.1 のとおり Relation は接続ごとに1回だけ送られる。受け取る側は relid → 列定義の対応表を 自分で保持しておかないと、2件目以降の Insert を解釈できない。これが CDC ツール実装で最初につまずく点である。

4.2　Relation と Insert

第3章で見た Relation メッセージを、最後まで分解する。

Relation メッセージの分解

00006014        24596      relid
7075626c69 6300 "public"   スキーマ名（NUL 終端）
6974656d73 00   "items"    テーブル名（NUL 終端）
64              'd'        レプリカアイデンティティ = default
0004            4          列数
  01 6964 00       00000017 ffffffff   キー列, "id",       型 23 (int4),  atttypmod -1
  00 6e616d6500    00000019 ffffffff   通常列, "name",     型 25 (text),  atttypmod -1
  00 7072696365 00 00000017 ffffffff   通常列, "price",    型 23 (int4),  atttypmod -1
  00 696e5f73746f636b 00 00000010 ffffffff 通常列, "in_stock", 型 16 (bool)

各列の先頭1バイトはフラグで、01 ならレプリカアイデンティティに含まれる列、 00 ならそれ以外を意味する。いまは主キー id だけが 01 になっている。 この「どの列がキーか」という情報が、次節の UPDATE / DELETE の形を決める。

4.3　Update・Delete と REPLICA IDENTITY

UPDATE と DELETE は「変更後の行」だけでは足りない。購読側がどの行を書き換えればよいかを 特定する必要があるからである。その特定に使う列の集合が REPLICA IDENTITY で、 既定は主キーである。

タプルの直前には、それが何のタプルかを示す1バイトが入る。

16進文字意味
4eNNew — 変更後の行（全列）
4bKKey — 変更前のキー列だけ（キー以外は NULL）
4fOOld — 変更前の行（全列）。REPLICA IDENTITY FULL のとき
⌨️ ハンズオン: REPLICA IDENTITY DEFAULT での UPDATE / DELETE

  1. 3種類の変更を、それぞれ別トランザクションで実行する。

    入力（シェル） 
    psql -d shop -c "INSERT INTO items VALUES (2, 'banana', 80);"
psql -d shop -c "UPDATE items SET price = 95 WHERE id = 2;"   # キーは変えない
psql -d shop -c "UPDATE items SET id = 3    WHERE id = 2;"    # キーを変える
psql -d shop -c "DELETE FROM items WHERE id = 3;"

  2. 4.5 のデコーダに通して読む（デコーダの中身は 4.5 で示す）。

    入力（シェル） 
    psql -d shop -tAc "SELECT data FROM pg_logical_slot_get_binary_changes(
    'shop_slot', NULL, NULL,
    'proto_version','4','publication_names','shop_pub')" \
  | python3 pgoutput_decode.py
    出力 
    BEGIN      final_lsn=0/226A088 ts=2026-08-06T13:33:11.933967+00:00 xid=793
RELATION   24596 public.items identity=d cols=[*id:23, name:25, price:23, in_stock:16]
INSERT     rel=24596 N['2', 'banana', '80', 't']
COMMIT     commit_lsn=0/226A088 end_lsn=0/226A0B8 ts=2026-08-06T13:33:11.933967+00:00
BEGIN      final_lsn=0/226A110 ts=2026-08-06T13:33:12.066699+00:00 xid=794
UPDATE     rel=24596 N['2', 'banana', '95', 't']
COMMIT     commit_lsn=0/226A110 end_lsn=0/226A140 ts=2026-08-06T13:33:12.066699+00:00
BEGIN      final_lsn=0/226A1E0 ts=2026-08-06T13:33:12.109768+00:00 xid=795
UPDATE     rel=24596 K['2', 'NULL', 'NULL', 'NULL'] N['3', 'banana', '95', 't']
COMMIT     commit_lsn=0/226A1E0 end_lsn=0/226A210 ts=2026-08-06T13:33:12.109768+00:00
BEGIN      final_lsn=0/226A288 ts=2026-08-06T13:33:12.152533+00:00 xid=796
DELETE     rel=24596 K['3', 'NULL', 'NULL', 'NULL']
COMMIT     commit_lsn=0/226A288 end_lsn=0/226A2B8 ts=2026-08-06T13:33:12.152533+00:00

読み方のポイントは3つある。

  • キーを変えない UPDATE（xid=794）は N だけ。購読側は新しい行のキー id=2 で 対象行を探せるので、変更前の情報は要らない。
  • キーを変える UPDATE（xid=795）は K と N の両方。 K の id=2 で行を探し、N の内容で上書きする。
  • DELETE（xid=796）は K だけ。キー以外は NULL で埋まっていて、 値は送られない。
⌨️ ハンズオン: REPLICA IDENTITY FULL に変えて比べる

  1. テーブルのレプリカアイデンティティを全列に変える。

    入力（psql -d shop） 
    ALTER TABLE items REPLICA IDENTITY FULL;
    出力 
    ALTER TABLE

  2. 同じ操作を繰り返す。

    入力（シェル） 
    psql -d shop -c "INSERT INTO items VALUES (4, 'cherry', 300);"
psql -d shop -c "UPDATE items SET price = 330 WHERE id = 4;"
psql -d shop -c "DELETE FROM items WHERE id = 4;"

  3. デコードする。

    出力 
    BEGIN      final_lsn=0/226A4F8 ts=2026-08-06T13:33:12.287438+00:00 xid=798
RELATION   24596 public.items identity=f cols=[*id:23, *name:25, *price:23, *in_stock:16]
INSERT     rel=24596 N['4', 'cherry', '300', 't']
COMMIT     commit_lsn=0/226A4F8 end_lsn=0/226A528 ts=2026-08-06T13:33:12.287438+00:00
BEGIN      final_lsn=0/226A598 ts=2026-08-06T13:33:12.331170+00:00 xid=799
UPDATE     rel=24596 O['4', 'cherry', '300', 't'] N['4', 'cherry', '330', 't']
COMMIT     commit_lsn=0/226A598 end_lsn=0/226A5C8 ts=2026-08-06T13:33:12.331170+00:00
BEGIN      final_lsn=0/226A618 ts=2026-08-06T13:33:12.373631+00:00 xid=800
DELETE     rel=24596 O['4', 'cherry', '330', 't']
COMMIT     commit_lsn=0/226A618 end_lsn=0/226A648 ts=2026-08-06T13:33:12.373631+00:00

  4. 既定に戻しておく（以降の章は DEFAULT 前提）。

    入力（psql -d shop） 
    ALTER TABLE items REPLICA IDENTITY DEFAULT;
    出力 
    ALTER TABLE

Relation メッセージの identity が d から f に変わり、 全列の先頭に *（キー列フラグ）が付いた。その結果 UPDATE には O（変更前の全列）が 付き、DELETE も全列を運ぶようになった。変更前の値が必要な CDC 用途では FULL が有用だが、 WAL とネットワークの量が増えるので、必要なテーブルだけに限定するのが定石である。

⚠️ よくある落とし穴 更新されなかった TOAST 値（外部に追い出された大きな値）は、UPDATE で送られない。 デコード結果では「未変更」を示す種別 u になる。実際に 160,000 バイトの text 列を持つ行の別の列だけを更新すると、次のようになる。
出力 
UPDATE     rel=24676 N['1', 'b', '<unchanged-toast>']
受け取る側は「値が空になった」と誤解してはいけない。この列は変更しないのが正しい扱いで、 どうしても毎回値が欲しければ REPLICA IDENTITY FULL にするか、 そもそも TOAST されない設計にする。

4.5　デコーダを手元に置く

16進を毎回手で分解するのは現実的でないので、小さなデコーダを作っておく。 以下は本ガイドのすべての出力例を作るのに実際に使ったもので、 psql -tAc の出力（1行1メッセージの16進）を標準入力から読む。

pgoutput_decode.py 
#!/usr/bin/env python3
"""pgoutput のメッセージ (16進1行1メッセージ) を読んで内容を表示する最小デコーダ。"""
import sys, struct, datetime

PG_EPOCH = datetime.datetime(2000, 1, 1, tzinfo=datetime.timezone.utc)


class Reader:
    def __init__(self, buf):
        self.b, self.i = buf, 0

    def int8(self):
        v = self.b[self.i]; self.i += 1; return v

    def int16(self):
        v = struct.unpack_from('!h', self.b, self.i)[0]; self.i += 2; return v

    def int32(self):
        v = struct.unpack_from('!i', self.b, self.i)[0]; self.i += 4; return v

    def int64(self):
        v = struct.unpack_from('!q', self.b, self.i)[0]; self.i += 8; return v

    def lsn(self):
        v = self.int64(); return '%X/%X' % (v >> 32, v & 0xFFFFFFFF)

    def ts(self):
        return (PG_EPOCH + datetime.timedelta(microseconds=self.int64())).isoformat()

    def string(self):
        end = self.b.index(b'\x00', self.i)
        v = self.b[self.i:end].decode('utf-8', 'replace'); self.i = end + 1; return v

    def tuple_data(self):
        cols = []
        for _ in range(self.int16()):
            kind = chr(self.int8())
            if kind in ('n', 'u'):
                cols.append('NULL' if kind == 'n' else '<unchanged-toast>')
            else:
                n = self.int32(); v = self.b[self.i:self.i + n]; self.i += n
                cols.append(v.decode('utf-8', 'replace') if kind == 't' else '0x' + v.hex())
        return cols


def decode(msg):
    r = Reader(msg)
    t = chr(r.int8())
    if t == 'B':
        return f"BEGIN      final_lsn={r.lsn()} ts={r.ts()} xid={r.int32()}"
    if t == 'C':
        r.int8(); return f"COMMIT     commit_lsn={r.lsn()} end_lsn={r.lsn()} ts={r.ts()}"
    if t == 'R':
        rel = r.int32(); ns = r.string(); name = r.string()
        ident = chr(r.int8()); ncols = r.int16()
        cols = []
        for _ in range(ncols):
            key = r.int8(); cname = r.string(); typid = r.int32(); r.int32()
            cols.append(('*' if key else '') + f"{cname}:{typid}")
        return f"RELATION   {rel} {ns}.{name} identity={ident} cols=[{', '.join(cols)}]"
    if t in ('I', 'U', 'D'):
        rel = r.int32(); parts = []
        while r.i < len(r.b):
            sub = chr(r.int8())
            parts.append(f"{sub}{r.tuple_data()}")
        names = {'I': 'INSERT', 'U': 'UPDATE', 'D': 'DELETE'}
        return f"{names[t]:<10} rel={rel} " + ' '.join(parts)
    if t == 'T':
        n = r.int32(); flags = r.int8()
        return f"TRUNCATE   flags={flags} rels={[r.int32() for _ in range(n)]}"
    if t == 'M':
        flags = r.int8(); lsn = r.lsn(); prefix = r.string(); n = r.int32()
        return (f"MESSAGE    transactional={bool(flags & 1)} lsn={lsn} "
                f"prefix={prefix} content={r.b[r.i:r.i+n]!r}")
    if t == 'S':
        return f"STREAM START xid={r.int32()} first_segment={r.int8()}"
    if t == 'E':
        return "STREAM STOP"
    if t == 'c':
        xid = r.int32(); r.int8()
        return f"STREAM COMMIT xid={xid} commit_lsn={r.lsn()} end_lsn={r.lsn()} ts={r.ts()}"
    if t == 'A':
        xid = r.int32(); r.int8()
        return f"STREAM ABORT xid={xid}"
    if t == 'b':
        return (f"BEGIN PREPARE prepare_lsn={r.lsn()} end_lsn={r.lsn()} ts={r.ts()} "
                f"xid={r.int32()} gid={r.string()}")
    if t == 'P':
        r.int8()
        return (f"PREPARE    prepare_lsn={r.lsn()} end_lsn={r.lsn()} ts={r.ts()} "
                f"xid={r.int32()} gid={r.string()}")
    if t == 'K':
        r.int8()
        return (f"COMMIT PREPARED commit_lsn={r.lsn()} end_lsn={r.lsn()} ts={r.ts()} "
                f"xid={r.int32()} gid={r.string()}")
    if t == 'r':
        r.int8()
        return (f"ROLLBACK PREPARED end_lsn={r.lsn()} rollback_lsn={r.lsn()} "
                f"prepare_ts={r.ts()} rollback_ts={r.ts()} xid={r.int32()} gid={r.string()}")
    if t == 'O':
        return f"ORIGIN     commit_lsn={r.lsn()} name={r.string()}"
    if t == 'Y':
        return f"TYPE       oid={r.int32()} name={r.string()}.{r.string()}"
    return f"UNKNOWN    type={t!r} raw={msg.hex()}"


for line in sys.stdin:
    line = line.strip()
    if not line:
        continue
    print(decode(bytes.fromhex(line[2:] if line.startswith('\\x') else line)))

使い方は次のとおり。-tAc を付けて、余計な枠線とヘッダを外した16進だけを渡すのがコツである。

入力（シェル） 
psql -d shop -tAc "SELECT data FROM pg_logical_slot_peek_binary_changes(
    'shop_slot', NULL, NULL,
    'proto_version','4','publication_names','shop_pub','messages','true')" \
  | python3 pgoutput_decode.py
出力 
BEGIN      final_lsn=0/226C738 ts=2026-08-06T13:33:56.347901+00:00 xid=809
MESSAGE    transactional=True lsn=0/226C738 prefix=audit content=b'user=42 action=login'
COMMIT     commit_lsn=0/226C738 end_lsn=0/226C768 ts=2026-08-06T13:33:56.347901+00:00
⚠️ よくある落とし穴 このデコーダは SQL 関数の出力（1行1メッセージ）専用である。 pg_recvlogical -f が書いたファイルには pgoutput のメッセージが隙間なく連結されており、 区切りとして足された改行はメッセージ本文中のバイト値 0x0a と区別できない。 ファイルを解析したい場合は、各メッセージの長さを型ごとに計算しながら読み進める必要がある。
