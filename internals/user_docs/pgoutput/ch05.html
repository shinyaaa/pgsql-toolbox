第5章　pgoutput のオプション

🎯 この章のゴール
  • pgoutput の主要オプションを、SQL 関数と pg_recvlogical の両方から渡せる
  • binary / messages / streaming / two_phase / origin の効果を、出力の違いで説明できる
  • 大トランザクションで spill と streaming のどちらが起きているか、統計ビューで判別できる
📋 前提
  • 第4章までの環境（shop_slot、cdc_slot、pgoutput_decode.py）
  • 5.6 では max_prepared_transactions を 0 より大きくするため、サーバの再起動が1回必要
  • 5.5 では logical_decoding_work_mem を一時的に 64kB に下げる

5.1　オプションの渡し方

pgoutput のオプションは、呼び出し方によって書き方が変わるだけで、届く先は同じである。

呼び出し方書き方
SQL 関数pg_logical_slot_peek_binary_changes(slot, NULL, NULL, 'キー', '値', ...)
pg_recvlogical-o キー=値 を並べる
レプリケーションプロトコルSTART_REPLICATION SLOT ... LOGICAL 0/0 (キー '値', ...)
論理レプリケーションCREATE/ALTER SUBSCRIPTION ... WITH (...)（PostgreSQL が変換して渡す）

主要なオプションは次のとおり。

オプション既定効果
proto_versionなし（必須）使うプロトコルバージョン
publication_namesなし（必須）対象パブリケーション名（カンマ区切り）
binaryfalse値をテキストでなくバイナリ表現で送る
messagesfalsepg_logical_emit_message() の内容を送る
streamingfalseコミット前の大トランザクションを分割して送る
two_phasefalsePREPARE 時点で送る
originanynone にすると他ノード由来の変更を送らない

5.2　proto_version

プロトコルバージョンは、使えるメッセージ型の範囲を決める。PostgreSQL 16 が受け付けるのは 4 までである。

proto_version導入増えた機能
1PostgreSQL 10基本のメッセージ型
2PostgreSQL 14ストリーミング（Stream Start / Stop / Commit / Abort）
3PostgreSQL 152相コミット（Begin Prepare / Prepare / Commit Prepared / Rollback Prepared）
4PostgreSQL 16ストリーミング中の並列適用に対応した Stream Abort

サーバが対応していないバージョンを要求すると、起動時にはっきりエラーになる。

入力（psql -d shop） 
SELECT data FROM pg_logical_slot_peek_binary_changes(
    'shop_slot', NULL, NULL, 'proto_version', '9', 'publication_names', 'shop_pub');
出力 
ERROR:  client sent proto_version=9 but server only supports protocol 4 or lower
CONTEXT:  slot "shop_slot", output plugin "pgoutput", in the startup callback

publication_names を忘れた場合も同様に起動時に落ちる。

入力（psql -d shop） 
SELECT data FROM pg_logical_slot_peek_binary_changes(
    'shop_slot', NULL, NULL, 'proto_version', '4');
出力 
ERROR:  publication_names parameter missing
CONTEXT:  slot "shop_slot", output plugin "pgoutput", in the startup callback
💡 ヒント CONTEXT: 行に output plugin "pgoutput" と出るのが目印である。 ログにこの形のエラーが出ていたら、pgoutput に渡されたオプションを疑えばよい。

5.3　binary

既定では、すべての値がテキスト表現（output function の結果）で送られる。 binary=true にすると、型ごとのバイナリ表現（send function の結果）になる。

⌨️ ハンズオン: binary の有無を比べる

  1. 1件入れて、まず既定（テキスト）で見る。

    入力（シェル） 
    psql -d shop -c "INSERT INTO items VALUES (9, 'grape', 450);"
psql -d shop -c "SELECT data FROM pg_logical_slot_peek_binary_changes(
    'shop_slot', NULL, NULL, 'proto_version','4','publication_names','shop_pub');"
    出力（Insert の行のみ抜粋） 
    \x49000060144e0004740000000139740000000567726170657400000003343530740000000174

  2. 同じ変更を binary=true で取り直す。

    入力（psql -d shop） 
    SELECT data FROM pg_logical_slot_get_binary_changes(
    'shop_slot', NULL, NULL,
    'proto_version','4','publication_names','shop_pub','binary','true');
    出力（Insert の行のみ抜粋） 
    \x49000060144e0004620000000400000009620000000567726170656200000004000001c2620000000101

違いは列の種別バイトと値の表現である。

列binary=falsebinary=true
id=974 長さ1 39（文字 "9"）62 長さ4 00000009（int4 の 9）
name='grape'74 長さ5 67726170 6562 長さ5 67726170 65（text は同じ）
price=45074 長さ3 343530（文字 "450"）62 長さ4 000001c2（int4 の 450）
in_stock=true74 長さ1 74（文字 "t"）62 長さ1 01（bool の true）

種別バイトが 74（'t' = テキスト）から 62（'b' = バイナリ）に変わっている。 0x1c2 は 450 なので、確かに int4 のバイナリ表現である。

⚠️ よくある落とし穴 binary=true は受け取る側が同じ型のバイナリ表現を解釈できることを前提にする。 エンディアンや型の内部表現はバージョン間・アーキテクチャ間で必ずしも同一ではないため、 異機種間の論理レプリケーションや自作クライアントでは false（既定）が安全である。 性能を稼ぎたい同一構成のノード間でのみ有効にする。

5.4　messages

4.4 で見たとおり、pg_logical_emit_message() で埋め込んだ内容は messages=true のときだけ流れる。既定は false なので、 CDC でアプリケーション文脈を運びたいなら明示的に有効化する必要がある。

入力（シェル）— pg_recvlogical の場合 
pg_recvlogical -d shop --slot=cdc_slot --start \
  -o proto_version=4 -o publication_names='shop_pub' -o messages=true \
  --endpos="$LSN" -f /tmp/msg.bin
💡 ヒント 論理メッセージはパブリケーションと無関係に流れる。テーブルを1つも含まない パブリケーションでも、messages=true なら Message メッセージは届く。 逆に言えば、パブリケーション設定で論理メッセージを絞ることはできない。

5.5　streaming

既定では、pgoutput はコミットされるまで何も送らない。 そのため巨大なトランザクションでは、変更をサーバ側のメモリに溜め込み、 logical_decoding_work_mem を超えるとディスクに書き出す（これを spill と呼ぶ）。 streaming=true にすると、コミットを待たずに途中経過を送り出せる。図 5.1 の違いである。

⌨️ ハンズオン: spill と streaming を比べる

  1. 差が出やすいよう、しきい値を最小の 64kB に下げる（再起動不要）。

    入力（psql） 
    ALTER SYSTEM SET logical_decoding_work_mem = '64kB';
SELECT pg_reload_conf();
    出力 
    ALTER SYSTEM
 pg_reload_conf
----------------
 t
(1 row)

  2. テーブルを空にし、スロットも空にしてから始める。

    入力（シェル） 
    psql -d shop -c "TRUNCATE items;"
psql -d shop -tAc "SELECT count(*) FROM pg_logical_slot_get_binary_changes(
    'shop_slot', NULL, NULL, 'proto_version','4','publication_names','shop_pub')"

  3. streaming なしで受けるスロットを作り、1本目の大きなトランザクションを流す。

    入力（シェル） 
    pg_recvlogical -d shop --slot=big_slot --create-slot -P pgoutput

psql -d shop -c "BEGIN;
INSERT INTO items SELECT g, 'bulk-'||g, g*10 FROM generate_series(100, 3000) g;
COMMIT;"

  4. 次に streaming ありで受けるスロットを作り、2本目を流す。 順序が重要で、この作り方だと big_slot は2本とも、 stream_slot は2本目だけを見ることになる。あとで統計を比べるときの前提になる。

    入力（シェル） 
    pg_recvlogical -d shop --slot=stream_slot --create-slot -P pgoutput

psql -d shop -c "BEGIN;
INSERT INTO items SELECT g, 'bulk2-'||g, g*10 FROM generate_series(5000, 8000) g;
COMMIT;"

  5. stream_slot を streaming=true で受け取る。

    入力（シェル） 
    LSN=$(psql -d shop -tAc "SELECT pg_current_wal_lsn();")
rm -f /tmp/stream.bin
pg_recvlogical -d shop --slot=stream_slot --start \
  -o proto_version=4 -o publication_names='shop_pub' -o streaming=true \
  --endpos="$LSN" -f /tmp/stream.bin

  6. 先頭と末尾を見る。

    入力（シェル） 
    od -A d -t x1z /tmp/stream.bin | head -3
od -A d -t x1z /tmp/stream.bin | tail -4
    出力 
    0000000 53 00 00 03 2b 01 0a 52 00 00 03 2b 00 00 60 14  >S...+..R...+..`.<
0000016 70 75 62 6c 69 63 00 69 74 65 6d 73 00 64 00 04  >public.items.d..<
0000032 01 69 64 00 00 00 00 17 ff ff ff ff 00 6e 61 6d  >.id..........nam<
...
0159184 00 00 05 38 30 30 30 30 74 00 00 00 01 74 0a 45  >...80000t....t.E<
0159200 0a 63 00 00 03 2b 00 00 00 00 00 02 33 f9 b0 00  >.c...+......3...<
0159216 00 00 00 02 33 f9 e0 00 02 fb 5f b6 6a 9c be 0a  >....3....._.j...<
0159232

  7. big_slot のほうは streaming なしで消費する。

    入力（psql -d shop） 
    SELECT count(*) FROM pg_logical_slot_get_binary_changes(
    'big_slot', NULL, NULL, 'proto_version','4','publication_names','shop_pub');
    出力 
     count
-------
  5907
(1 row)

  8. 統計を比べる。

    入力（psql -d shop） 
    SELECT slot_name, spill_txns, spill_count, spill_bytes,
       stream_txns, stream_count, total_txns
  FROM pg_stat_replication_slots
 WHERE slot_name IN ('big_slot', 'stream_slot');
    出力 
      slot_name  | spill_txns | spill_count | spill_bytes | stream_txns | stream_count | total_txns
-------------+------------+-------------+-------------+-------------+--------------+------------
 big_slot    |          2 |          14 |      879398 |           0 |            0 |          2
 stream_slot |          0 |           0 |           0 |           1 |            7 |          1
(2 rows)

  9. 終わったらしきい値を戻す。

    入力（psql） 
    ALTER SYSTEM SET logical_decoding_work_mem = '64MB';
SELECT pg_reload_conf();

読み方は明快である。big_slot は見えていた 2 トランザクションで 14 回・約 880KB をディスクに書き出した（spill_*）のに対し、 stream_slot は spill が 0 で、代わりに 見えていた 1 トランザクションを 7 つの塊に分けて送っている（stream_count = 7）。 od の出力でも、先頭が 53（Stream Start）、末尾が 45（Stream Stop）→ 63（Stream Commit）になっている。

⚠️ よくある落とし穴 spill_bytes が大きいスロットは、デコード時にディスク I/O を大量に発生させ、 レプリケーション遅延の原因になる。pg_stat_replication_slots で spill_txns が増え続けているなら、logical_decoding_work_mem を上げるか streaming を有効にすることを検討する。
💡 ヒント streaming は SQL 関数経由でも効く。同じ大トランザクションを 'streaming','true' 付きで peek すると、メッセージの先頭バイトの内訳は次のようになった。
入力（シェル） 
psql -d shop -tAc "SELECT data FROM pg_logical_slot_peek_binary_changes(
    'shop_slot', NULL, NULL,
    'proto_version','4','publication_names','shop_pub','streaming','true')" \
  | cut -c1-4 | sort | uniq -c | sort -rn
出力 
   3001 \x49      Insert
      7 \x53      Stream Start
      7 \x45      Stream Stop
      1 \x63      Stream Commit
      1 \x52      Relation
Begin / Commit ではなく Stream Start / Stop / Commit で囲まれているのが、ストリーミングされた証拠である。

5.6　two_phase

既定では、2相コミットの PREPARE TRANSACTION の時点では何も送られず、 COMMIT PREPARED のときに通常のトランザクションとしてまとめて届く。 two_phase=true にすると、PREPARE の時点で送られるようになる。

⌨️ ハンズオン: 2相コミットを流す

  1. max_prepared_transactions を有効にする（既定 0 のままでは PREPARE TRANSACTION が使えない）。再起動が必要。

    入力（psql → シェル） 
    psql -c "ALTER SYSTEM SET max_prepared_transactions = 10;"
pg_ctlcluster 16 main restart
psql -tAc "SHOW max_prepared_transactions;"
    出力 
    10

  2. 5.5 で入れた大量の行を片付ける。この後で id = 902 を使うが、 5.5 の bulk-902 と衝突するため、先に空にしておく。

    入力（psql -d shop） 
    TRUNCATE items;
    出力 
    TRUNCATE TABLE

  3. two_phase 対応のスロットを作る。スロット作成時に決める点に注意する。

    入力（シェル） 
    pg_recvlogical -d shop --slot=tp_slot --create-slot -P pgoutput --two-phase
psql -d shop -c "SELECT slot_name, plugin, two_phase
                   FROM pg_replication_slots WHERE slot_name='tp_slot';"
    出力 
     slot_name |  plugin  | two_phase
-----------+----------+-----------
 tp_slot   | pgoutput | t
(1 row)

  4. トランザクションを PREPARE する（まだコミットしない）。

    入力（psql -d shop） 
    BEGIN;
INSERT INTO items VALUES (902, 'two-phase-demo', 700);
PREPARE TRANSACTION 'tx3';

  5. この時点で覗くと、すでに変更が届いている。

    入力（シェル） 
    psql -d shop -tAc "SELECT data FROM pg_logical_slot_get_binary_changes(
    'tp_slot', NULL, NULL,
    'proto_version','4','publication_names','shop_pub','two_phase','true')" \
  | python3 pgoutput_decode.py
    出力 
    BEGIN PREPARE prepare_lsn=0/2341378 end_lsn=0/2341470 ts=2026-08-06T13:35:17.091437+00:00 xid=816 gid=tx3
RELATION   24596 public.items identity=d cols=[*id:23, name:25, price:23, in_stock:16]
INSERT     rel=24596 N['902', 'two-phase-demo', '700', 't']
PREPARE    prepare_lsn=0/2341378 end_lsn=0/2341470 ts=2026-08-06T13:35:17.091437+00:00 xid=816 gid=tx3

  6. コミットすると、確定を知らせる短いメッセージだけが来る。

    入力（psql -d shop → シェル） 
    psql -d shop -c "COMMIT PREPARED 'tx3';"
    出力 
    COMMIT PREPARED commit_lsn=0/2341470 end_lsn=0/23414A8 ts=2026-08-06T13:35:17.227394+00:00 xid=816 gid=tx3

  7. ロールバックした場合も確認しておく。

    入力（psql -d shop） 
    BEGIN;
INSERT INTO items VALUES (903, 'abandoned', 1);
PREPARE TRANSACTION 'tx4';
ROLLBACK PREPARED 'tx4';
    出力（デコード結果） 
    BEGIN PREPARE prepare_lsn=0/2341538 end_lsn=0/2341630 ts=2026-08-06T13:35:17.357109+00:00 xid=817 gid=tx4
PREPARE    prepare_lsn=0/2341538 end_lsn=0/2341630 ts=2026-08-06T13:35:17.357109+00:00 xid=817 gid=tx4
ROLLBACK PREPARED end_lsn=0/2341630 rollback_lsn=0/2341668 prepare_ts=... rollback_ts=... xid=817 gid=tx4

グローバルトランザクション ID（gid）がそのまま運ばれているので、 受け取る側は同じ gid で自分の側の PREPARE を作り、COMMIT PREPARED を待つ、という 分散トランザクションが組める。

上の tx4 の例で INSERT が見えないのは、PREPARE と ROLLBACK PREPARED を 続けて実行してから読んだためである。受け取る側が PREPARE の時点で読んでいれば、 INSERT は届いている。実際に、PREPARE 直後に一度読み、 その後ロールバックしてもう一度読むと、こうなる。

出力（PREPARE 直後に読んだとき） 
BEGIN PREPARE prepare_lsn=0/2885758 end_lsn=0/2885850 ts=... xid=879 gid=tx9
RELATION   24596 public.items identity=d cols=[*id:23, name:25, price:23, in_stock:16]
INSERT     rel=24596 N['950', 'rb-test', '1', 't']
PREPARE    prepare_lsn=0/2885758 end_lsn=0/2885850 ts=... xid=879 gid=tx9
出力（ROLLBACK PREPARED 後に読んだとき） 
ROLLBACK PREPARED end_lsn=0/2885850 rollback_lsn=0/2885888 prepare_ts=... rollback_ts=... xid=879 gid=tx9

つまり受け取る側は、いったん適用した PREPARE を後から取り消せる必要がある。 これが 2相コミットを扱う CDC 実装の難しいところである。

⚠️ よくある落とし穴 two_phase はスロット作成時の属性である。既存スロットに対して -o two_phase=true だけ付けても、スロットが 2相対応で作られていなければ PREPARE 時点では届かない。 pg_replication_slots.two_phase が t になっているかを必ず確認すること。

5.7　origin

origin は「どこ由来の変更を送るか」を決める。既定の any はすべて送り、 none は複製起点を持たない変更、つまりこのノードで直接行われた変更だけを送る。

用途は双方向レプリケーションでの変更の無限ループ防止である。A→B と B→A の 両方向にサブスクリプションを張ると、A で INSERT した行が B に渡り、B ではそれが「B での変更」として また A に返ってくる。両方向を origin = none にすると、複製で入ってきた変更は転送されなくなる。

入力（購読側 psql） 
ALTER SUBSCRIPTION shop_sub SET (origin = none);
出力 
ALTER SUBSCRIPTION

この設定が pgoutput にどう渡るかは、第7章 7.3 で発行側のログを見ながら確認する。

✅ チェックポイント
  • proto_version を 9 にするとエラーになり、CONTEXT に pgoutput と出るのを確認した
  • binary=true で列の種別バイトが 74 から 62 に変わるのを確認した
  • pg_stat_replication_slots で spill と stream の違いを読み取れた
  • two_phase 対応スロットで、PREPARE の時点で変更が届くのを確認した
